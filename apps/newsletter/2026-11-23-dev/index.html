자체 호스팅과 테스트 검증

자체 호스팅 GitHub의 새 릴리스 후보와 코딩 에이전트가 만든 테스트의 품질을 살펴봅니다. 공통 질문은 하나입니다. 도구가 늘려 주는 검사를 실제 신뢰로 바꾸려면 무엇을 따로 확인해야 할까요?

11월 23일자. 자체 호스팅 GitHub의 새 릴리스 후보와 코딩 에이전트가 만든 테스트의 품질을 살펴봅니다. 공통 질문은 하나입니다. 도구가 늘려 주는 검사를 실제 신뢰로 바꾸려면 무엇을 따로 확인해야 할까요?

개발 소식

GitHub Enterprise Server 3.23 릴리스 후보. GitHub가 11월 20일 발표했습니다. Projects에서는 논리 연산과 괄호로 필터를 조합할 수 있게 됐고, GitHub Secret Protection을 쓰는 환경에서는 외부 연결 없이 서버 CPU에서 비정형 비밀 정보를 찾는 기능을 공개 프리뷰로 소개했습니다. 버전 업데이트 PR을 열기 전에 패키지 게시 후 기본 3일을 기다리는 Dependabot 변경도 포함됩니다. 릴리스 후보와 프리뷰는 운영 적용을 확정하는 신호가 아닙니다. 공식 변경 사항

운영에서 볼 점. 예를 들어 인터넷과 분리된 조직은 탐지 요청을 외부로 보낼 필요가 없는 대신, 자기 장비에서 검사 시간과 오탐 처리량을 책임져야 합니다. 소수의 저장소를 대상으로 탐지 속도, 사람이 확인해야 할 경보 수, 예외 정책 일치 여부를 확인한 뒤 확대하는 편이 좋습니다. 버전 업데이트 대기 기간은 자동 버전 교체에 숨을 고르는 장치이지 패키지의 무결성을 보증하는 장치는 아닙니다.

자체 호스팅이라는 조건이 바꾸는 운영 비용

서버 안에서 비밀 정보 탐지 모델을 실행하면 경보 판정에 필요한 자료를 외부 모델로 보내지 않아도 됩니다. 반면 서버는 기존의 코드 검색, PR, 자동화 및 여러 작업과 CPU 시간을 나눠야 합니다. 새 기능을 처음부터 모든 저장소에 켜면 생산성이 좋아졌는지, 단순히 검색이 느려진 것인지 원인을 분리하기 어렵습니다. 운영과 동일한 크기의 저장소 중 민감도를 대표하는 소수만 골라 제한된 시간에 실행하고, 변경 전후 피크 CPU·작업 대기·PR 반응 시간을 같은 시간 구간에서 비교하는 편이 낫습니다. 장애를 재현하려고 실제 비밀 정보를 의도적으로 넣을 필요는 없습니다. 지원되는 모의 토큰이나 접근 권한이 전혀 없는 시험 문자열을 별도 환경에서 쓰면 됩니다.

가상의 팀이 두 설정을 비교해 보겠습니다. 기준 설정은 검토해야 할 경보 20건 중 독립적으로 확인해 둔 시험 항목 18건을 잡아냅니다. 프리뷰를 더한 설정은 50건을 만들고 시험 항목 23건을 잡습니다. 표식이 붙은 항목이 25건이라고 하면 이 시험 세트에서 시험 항목 검출은 72%에서 92%로 올랐고, 사람이 검토할 건수는 30건 늘었습니다. 추가로 포착한 5건을 놓치면 생길 비용과 추가 분류 시간을 같이 판단해야 합니다. 시험 표식 밖의 경보는 실제 비밀일 수도 있으므로 남은 27건이 모두 오탐이라고 단정해서도 안 됩니다. 민감한 도구일수록 검증용 값의 성격과 실제 경보 검토 범위를 분리해야 수치의 의미가 살아납니다.

기다리는 규칙과 검증하는 규칙

Dependabot의 기본 유예는 레지스트리에 갓 올라온 버전을 바로 적용하지 않게 하는 시간 규칙입니다. 예를 들어 월요일 정오에 나온 버전이 기본 3일 정책을 적용받고 별도 예외가 없다면, 목요일 정오 전에는 일반 버전 업데이트 PR 후보로 잡지 않는다는 식입니다. 그동안 추가 검사가 실행된다는 말은 아닙니다. 출처와 버전 고정, 서명 확인, 팀의 회귀 테스트는 별개로 필요합니다. 또 기능 소개가 일반 버전 업데이트를 대상으로 하는 만큼, 긴급 보안 업데이트까지 항상 같은 시각에 밀린다고 추정하지 않는 편이 좋습니다. GHES 릴리스 후보 공지

자동 대기와 담당자 승인도 기능이 다릅니다. 대기는 초기 검토가 끝날 시간을 주지만, 리뷰어가 무엇을 확인할지는 정해 주지 않습니다. 팀이 작은 시간 규칙을 추가한다면 기다림에 대응하는 작업을 하나 정할 수 있습니다. 예컨대 설치 출처와 라이선스가 기존 후보와 같은지, 잠금 파일이 예상 범위를 넘어 바뀌지 않았는지, 버전을 명시해 개발 환경과 배포 환경에서 같은 테스트가 실행되는지 확인합니다. 릴리스 후보 시험도 이런 검증 절차를 먼저 갖춰 놓을 때 실제 운영 판단으로 이어집니다.

프리뷰를 운영 승인에 쓰기 전에

검사 자체를 필수 조건으로 설정하면 탐지 정확도뿐 아니라 사용할 수 있는 시간도 중요해집니다. 검사 서비스가 밤마다 잠깐 느려져도 경보를 참고만 하는 단계라면 큰 문제가 아닐 수 있지만, 모든 PR의 병합을 검사 성공에 묶은 뒤에는 탐지와 무관한 변경까지 대기하게 됩니다. 정해진 시간에 응답하지 않으면 일시적으로 관리자 검토로 바꾸는 절차와, 그 예외를 나중에 정리하는 방식이 필요합니다. 그러한 장애 시험은 인터넷 연결이나 모델 신뢰도를 점검하는 것과 다른 종류의 검증입니다.

설치 전후 수치를 측정할 때, 경보가 늘어서 검토가 더 쉬워지는 역설도 보고할 수 있습니다. 예를 들어 중복 경보가 같은 위치에 묶여 표시된다면 50건이 실제 검토 작업 50번으로 이어지지 않을 수 있습니다. 반대로 20건 중 18건이 서로 다른 종류의 예외를 요구하면 리뷰 시간이 크게 늘어납니다. 접수부터 최종 판정까지의 사람 시간은 경보 수와 별도로 재는 편이 정확합니다. 프리뷰는 출시 일정만 알아보는 구간이 아니라, 같은 기능을 두고 운영 정책에 어떤 선택지가 실제로 필요한지를 알아내는 구간입니다.

주목할 논문

코딩 에이전트가 직접 쓴 테스트는 얼마나 믿을 수 있나. Pasternak 등의 프리프린트는 11월 16일 공개됐습니다. 세 코딩 에이전트가 사용한 테스트는 전통적인 커버리지 지표에서 사람 테스트를 앞섰지만, 프로젝트가 커질수록 품질이 떨어졌고 테스트 수가 많다는 요인도 있었습니다. 언어를 넘나드는 테스트 변환은 전체 평균이 괜찮아 보여도 사례별로 안정적이지 않았습니다. 벤치마크에 사용된 에이전트 구성에서 나온 결과이지, 어떤 팀의 테스트를 대체해도 된다는 결론은 아닙니다. 논문 원문

에이전트가 작성한 테스트의 빈칸을 찾으려면

테스트 생성의 성과는 실행한 줄 수, 통과 여부, 실패를 발견하는 능력, 읽고 유지하는 비용으로 나눠 볼 수 있습니다. 패키지에 오류 경로가 많다면 에이전트가 이전에 한 번도 실행되지 않았던 입력을 찾는 것만으로도 도움이 됩니다. 그런데 반환값을 검사하지 않고 실행이 끝났는지만 확인하면, 줄은 지나갔지만 버그를 걸러내지 못합니다. 반대로 조건 한 개를 자세하게 검증한 작은 테스트는 숫자로 표시되는 커버리지를 거의 올리지 못해도 실제 제품 결함을 잡을 수 있습니다. Pasternak 등 원문

가상의 명세에서 도서 대출은 ‘기한 이전의 갱신은 허용하나 기한 당일과 이후는 거절’이라고 합시다. AI가 만든 테스트 20개가 다른 사용자의 대출 케이스를 빠짐없이 방문하면서, 모두 기한 이틀 전만 검사할 수 있습니다. 기존 테스트 5개 중 정확히 한 개가 기한 당일을 확인한다면 경계 비교식이 틀렸을 때 기존 묶음이 이깁니다. 반면 사용자 구분 정책을 변경하는 문제에서는 AI의 입력 다양성이 오류를 더 빨리 드러낼 수도 있습니다. 자동 생성 테스트와 기존 테스트의 구실이 무엇인지 기능별로 비교해야 결론을 얻을 수 있습니다.

번역한 테스트는 원래 계약을 보존해야 합니다

다른 언어로 옮긴 테스트가 실행된다는 사실과, 같은 규칙을 검증한다는 사실은 다릅니다. 예를 들어 원본이 오류의 정확한 종류와 복구 후 저장 상태까지 요구하는데, 옮긴 버전이 아무 오류나 발생하면 통과하도록 단순해졌다면 둘은 다른 오라클입니다. 양쪽 테스트를 정상 구현에서만 실행하면 두 버전 모두 녹색이므로 차이가 드러나지 않습니다. 일정한 입력에서 잘못된 오류 종류를 내는 구현과, 상태를 그대로 두지 않는 구현을 따로 만들어 두 테스트가 모두 거절하는지 보면 계약이 빠져나갔는지를 확인할 수 있습니다.

자동 번역의 비용을 따질 때는 몇 개가 문법적으로 실행 가능한지와, 실패한 것을 사람이 고치는 데 얼마나 걸리는지, 옮기는 과정에서 사라진 단언이 얼마나 되는지를 따로 적는 편이 좋습니다. 테스트 파일을 100개 만들었다고 해서 검증 작업이 새로 100개 생겼다고 볼 수 없습니다. 이름과 입력만 달리하면서 같은 조건을 반복한 테스트가 많다면 실패 정보도 겹칩니다. 같은 크기로 맞춘 비교와, 실제로 팀이 검토할 전체 산출물 규모의 비교를 둘 다 제시하면 자동 생성의 이득과 유지 부담을 한 숫자에 섞지 않을 수 있습니다.

오늘의 개발 개념

테스트 오라클. 실행 결과가 맞는지 판정하는 기준입니다. 커버리지는 코드가 지나갔는지 알려 주지만 기대 결과가 맞는지는 알려 주지 않습니다. 예를 들어 예약 시스템에서 월말을 넘어가는 예약을 시험할 때, 새 구현이 반환한 시각을 그대로 기대값에 복사하면 해당 분기를 실행하면서도 계산 오류는 놓칠 수 있습니다. 시간대 규칙이나 독립적인 표를 기대값의 근거로 쓰면 테스트는 구현과 다른 쪽에서 판단합니다.

활용과 한계. 자동 생성 테스트는 경계 입력과 예외 경로를 넓히는 데 쓰고, 사용자에게 중요한 규칙은 요구사항에서 만든 독립 검증으로 보강할 수 있습니다. 수정 중 에이전트가 본 테스트와 최종 판정에만 쓰는 테스트를 분리하면 무엇을 일반화했는지 보기 쉽습니다. 다만 독립 테스트도 규칙 자체를 잘못 해석할 수 있으므로, 실패 수만 보지 말고 올바른 다른 구현을 부당하게 거부하지 않는지도 확인해야 합니다. 패치 검증 근거를 분류한 기술보고서

핵심: 자동으로 늘어난 검사는 검증의 재료입니다. 신뢰도는 검사 결과를 무엇과 비교했는지에 달려 있습니다.

오라클 만들기 구현보다 작은 규칙에서 시작합니다

예약 서비스에서 현지 시각 하루가 바뀌는 조건을 예로 들겠습니다. 새 구현이 고른 시간대를 그대로 읽고 그 결과가 다시 출력되는지만 검사하면, 잘못된 시간대도 일관성 있게 통과할 수 있습니다. 이 위험을 줄이는 한 방법은 별도 규칙표에 입력과 기대 시각을 적어 두고 새 코드가 그 표를 재생산하도록 만드는 것입니다. 테스트에 사용하는 기준표는 서비스의 새 계산식에서 복사한 값이 아니라, 서비스가 지원한다고 선언한 시간대 자료와 명세를 기준으로 작은 케이스만 독립해 만든 것입니다.

정답을 매번 계산하기 어렵다면 항상 유지되어야 할 관계를 검사할 수 있습니다. 예를 들어 유효한 시간 변환의 범위 안에서 현지 시각을 표준 시각으로 바꾼 뒤 같은 규약으로 되돌리면 원래 시각과 일치해야 합니다. 다만 같은 잘못된 상수를 양방향에서 사용하면 그 잘못도 상쇄됩니다. 그래서 관계 테스트와 독립 기준값 테스트의 역할은 다릅니다. 일광 절약 시간 전환처럼 시각이 중복되거나 사라지는 경우에는 원래 시각을 유일하게 복구할 수 있다는 조건도 적용할 수 없습니다. 이러한 경계는 오라클의 오류와 프로그램의 오류를 구분하려면 반드시 명시해야 합니다.

가상 비교에서 테스트 묶음 A와 B가 모두 80%의 줄을 실행하지만, A는 사람이 심은 10가지 대표 오류 중 2개, B는 7개를 잡았다고 합시다. B가 이 시험에서는 더 나은 판정 근거입니다. 그러나 삽입한 오류 중 실제로 존재할 수 없는 예가 많다면 수치는 과장됩니다. 실제 회귀 기록에서 추출한 표본과 작고 해석하기 쉬운 가상 변형을 나눠 기록해야, 업무에 중요한 사례가 얼마나 대표됐는지 볼 수 있습니다.

승인 단계에서 확인할 것

실제 PR에서 에이전트가 구현과 테스트를 모두 제출한다면, 리뷰어가 먼저 코드의 줄 수보다 요구사항 한 가지가 어떤 테스트에서 독립적으로 판정되는지 보아야 합니다. 시행 순서는 새 구현 없이 실패하는 사례를 확인하고, 고친 구현에서 통과한 뒤, 의미는 맞지만 접근법이 다른 구현도 부당하게 거절하지 않는지 점검하는 것입니다. 독립 테스트가 권한 있는 검사라고 해서 불변의 정답이라는 뜻은 아닙니다. 규칙이 바뀌면 기대값의 근거도 명시적으로 갱신되어야 합니다.

운영 도구 평가도 같은 문제로 돌아옵니다. 자체 호스팅 프리뷰를 평가할 때는 기능이 켜졌는지와 조직이 중요한 경보를 놓치지 않는지가 다릅니다. 자동 생성 테스트도 파일이 만들어졌는지와 잘못된 동작을 거절하는지가 다릅니다. 검토의 마지막 한 단계는 산출물이 있다는 표시를 보는 데서 그치지 않고, 팀이 합의한 정답의 근거가 무엇이며 어떤 실패를 잡아낼 수 있는지 확인하는 일입니다.
