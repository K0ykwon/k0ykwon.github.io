의료 근거 검색과 QL-VLM을 사례로, 근거를 고르는 과정과 잠재 추론의 계산 비용을 분리해 읽습니다.

이 글의 흐름
최신 AI 소식주목할 만한 논문오늘의 개념: 추론 단계와 단계당 비용

AI가 답변을 만들 때 비용이 드는 곳은 두 군데입니다. 모델 밖에서 관련 자료를 찾는 비용과, 찾은 정보를 가지고 모델 안에서 다음 단계를 계산하는 비용입니다. 이번에는 OpenAI가 공개한 의료 근거 검색 설정으로 첫 번째를, 시각·언어 모델의 내부 추론을 줄인 QL-VLM 논문으로 두 번째를 살펴봅니다. 두 사례는 서로 독립적이며, 한쪽에서 잘 된 일이 다른 쪽의 성능을 보장하지 않습니다.

최신 AI 소식

OpenAI API의 의료 근거 검색 설정

OpenAI는 11월 24일 API 릴리스 노트에서 의료용 모델 설정을 공개했습니다. 예시로 든 GPT-6.2 Astra 의료 설정은 API에서 사용할 수 있는 모델 구성입니다. Responses API 요청에서 해당 구성을 지정하고 웹 검색을 활성화하면 전용 의료 검색 색인을 사용할 수 있습니다. API 조직이 사용하며, 별도의 ChatGPT for Healthcare 워크스페이스가 필요하지 않다고 명시돼 있습니다. 11월 24일 릴리스 노트 · 제품 안내

검색 색인은 모델이 참고할 문서를 찾아오는 경로입니다. 제품 안내는 근거를 찾아 비교하고 인용과 함께 정리하는 용도를 들지만, 설정을 적용하는 것만으로 인용의 정확성이나 판단의 적절성이 검증됐다는 뜻은 아닙니다. 설정 접근 권한만으로 보호 대상 의료정보를 보낼 수 있는 것도 아닙니다. 제품 안내는 그런 정보를 처리하기 전에 적용 가능한 계약과 계정·도구 설정 요건을 충족해야 한다고 안내합니다.

작동 여부를 비교하려면 개인정보가 없는 검증용 질문부터 사용할 수 있습니다. 공개 문서 A와 B에 같은 수치가 있지만 조사 대상과 시행 연도가 다르다고 가정해 보죠. 모델이 두 문서를 찾았는지, 각각의 수치를 올바른 대상과 연도에 연결했는지, 인용한 문장이 주장 전체를 뒷받침하는지를 나눠 채점합니다. 문서를 찾지 못한 오류와 문서는 찾았는데 조건을 빼먹은 오류는 고칠 곳이 다릅니다. 첫 번째는 검색 범위나 검색어를, 두 번째는 문서 활용과 답변 형식을 점검할 단서입니다. 이 검증은 응답 품질 평가의 예시이며 의료 판단을 자동화하는 기준은 아닙니다.

검색 성공과 사용 허가를 별개로 기록한다

하나의 설정이 허용하는 검색 범위와 조직이 허용하는 데이터 처리는 다른 문제입니다. 테스트 질문에 실제 기록이 섞이지 않도록 공개 근거와 합성 입력만 쓰고, 배포 때는 어떤 도구에 원문이 전달되는지 별도 목록으로 남길 수 있습니다. 또한 인용 링크가 있다는 이유만으로 근거라고 세지 않습니다. 공개 검증에선 링크가 열리는지, 문서 버전이 맞는지, 링크 안의 문장이 구체적 주장까지 뒷받침하는지를 따로 확인합니다. 예를 들어 40문항 중 36건에서 필수 문서를 찾았는데 30건에서만 올바른 비교를 했다면, 나머지 여섯 건은 검색 실패가 아니라 회수한 근거를 사용하지 못한 사례입니다. 숫자는 이 차이를 설명하기 위한 가상 예입니다.

주목할 만한 논문

QL-VLM은 중간 설명과 한 단계당 계산 비용을 함께 줄였다

Li 등의 11월 19일 arXiv 프리프린트는 이미지를 보며 답하는 시각·언어 모델에 양자화와 내부 벡터 추론을 결합합니다. 중간 설명을 자연어로 출력하는 방식은 다음 문장을 쓰기 전에 여러 토큰을 순차적으로 생성합니다. 잠재 추론은 그 자리를 연속적인 내부 벡터 몇 개로 바꿉니다. 따라서 출력 문장이 짧은 것과 모델 내부 단계 자체가 적은 것은 다릅니다. QL-VLM은 실험에서 내부 단계 또한 여섯 개로 고정했고, 그 단계를 실행하는 계산의 정밀도도 낮췄습니다. 논문 원문

단순히 벡터를 반올림하면 현재 값만 조금 틀리는 데서 끝나지 않습니다. 다음 단계의 어텐션에서 어떤 사진 영역이나 이전 힌트를 꺼낼지가 달라질 수 있습니다. 예를 들어 이미지에서 두 용기의 눈금을 비교할 때, 관심이 눈금에서 옆의 글자로 아주 조금 옮겨가도 다음 계산 결과는 크게 달라질 수 있습니다. 반대로 정답과 관련 없는 정보의 수치 오차는 더 커도 영향이 적을 수 있습니다. 연구가 보존하려는 것은 모든 숫자의 균일한 정밀도보다는 후속 단계에서 필요한 정보를 계속 읽을 수 있는 경로입니다.

첫 번째 방법 DGQ는 회전 위치 표현이 적용되는 키를 쌍 단위로 보고, 벡터의 크기와 방향을 고려한 비균일 코드북을 사용합니다. 똑같이 제한된 비트 수 안에서 데이터가 민감하게 반응하는 영역에 표현점을 더 효과적으로 배치하는 아이디어입니다. 두 번째 DPD는 고정밀 교사 모델을 두고, 낮은 정밀도의 학생이 최종 답변 분포뿐 아니라 중간 벡터와 해당 벡터가 어텐션으로 읽어내는 정보에도 맞춰 학습하도록 합니다. 학습은 데이터셋별 고정밀 체크포인트에서 시작했고, 논문 설정에서는 양자화 인지 학습을 한 에폭 수행했습니다. 출력 헤드와 추론 투영은 부동소수점으로 남았습니다.

같은 모델에서 기준선을 어떻게 고르나

비교표는 질문에 따라 세 가지로 읽힙니다. 기존 자연어 추론을 대체할 수 있는지 묻는다면 70.50%와 90.43%를 봅니다. 이미 내부 벡터 추론을 사용한다면 79.97%와 90.43%가 더 직접적입니다. 같은 4비트 예산 안에서 제안한 방법의 가치를 보려면 50.10%와 90.43%를 비교해야 합니다. 마지막 차이는 40.33%p로, 기준 정확도에 대한 상대 개선율과는 다른 수치입니다. 모두 같은 시험이라도 비교 질문이 바뀌면 무엇을 증명한 것인지가 달라집니다.

학습에 사용한 과제와 다른 과제로 옮겼을 때의 결과도 확인할 만합니다. 논문은 ScienceQA-IMG로 학습된 체크포인트를 별도의 대상 과제 튜닝 없이 MMStar와 MMMU-MC에서 시험했습니다. 2B 4비트 QL-VLM은 MMStar에서 44.27%로 고정밀 잠재 추론의 43.28%보다 높지만, MMMU-MC에서는 31.18%로 32.24%보다 낮습니다. 이 작은 비교만으로 범용적인 우열을 판단할 수는 없습니다. 배포 대상이 훈련 과제와 멀어질수록 별도의 평가가 필요하다는 점이 중요합니다. 논문 표 1·2 및 실험 절

같은 데이터셋에서 RTX PRO 6000으로 잰 답변당 평균 실행시간은 자연어 중간 추론의 3.20초에서 0.50초로 줄었습니다. 약 6.4배라는 수치는 자연어 중간 추론 대비입니다. 이미 내부 벡터를 쓰는 고정밀 비교군 대비 추가 개선은 1.60배였습니다. 지원되는 저정밀 연산은 CUDA 커널, 나머지는 BF16 연산을 사용해, 다른 GPU나 모바일에서 같은 속도를 기대할 근거는 아닙니다. 또 2B 모델의 M³CoT에서는 QL-VLM 4비트가 41.77%로 고정밀 잠재 추론 44.16%에 못 미쳤습니다. 좋아진 결과와 손해를 본 과제가 함께 있습니다.

4비트에서 줄어드는 메모리의 범위

단순 계산으로 가중치 20억 개만 놓고 보면 16비트는 약 4GB, 4비트는 약 1GB입니다. 그러나 이것은 모든 가중치가 해당 비트 폭으로 빈틈없이 담긴다고 가정한 십진 근사입니다. 양자화된 값에 대응하는 스케일과 코드북이 필요하고, 일부 모듈은 높은 정밀도를 유지하며, 실행 중엔 활성값과 캐시, 이미지 처리 버퍼도 씁니다. 가중치 저장량이 4분의 1이라고 전체 피크 메모리가 4분의 1이라는 뜻은 아닙니다. 지연 역시 비트 수만으로 정해지지 않습니다. 커널이 압축값을 읽고 정밀도를 바꾸는 비용과 GPU 사용률에 따라, 같은 포맷이 짧은 단건에서 유리해도 긴 입력이나 높은 배치에서 이득이 달라질 수 있습니다. 논문 실험 조건

오늘의 개념: 추론 단계와 단계당 비용

출력 토큰 수만으로 빠르다고 판단하기 어려운 이유

답이 짧아도 검색이나 이미지 인코딩에 시간이 많이 들 수 있고, 화면에 나타나지 않는 중간 계산이 길 수도 있습니다. 반대로 눈에 보이는 중간 문장을 줄일 때도, 첫 단계에서 읽은 증거와 마지막 답변 사이의 연결을 어떻게 평가할지가 남습니다. 실측 응답 시간은 입력 처리, 도구 대기, 순차적 내부 추론, 답변 생성, 서비스 오버헤드로 분해해서 보는 게 좋습니다. 분리 집계가 불가능한 API는 총 지연과 도구 실행 로그만으로 확인 가능한 범위를 표시할 수 있습니다.

가상의 서비스가 문서를 찾는 데 800ms, 본문을 처리하는 데 300ms, 모델이 답을 계산하는 데 900ms를 쓴다고 합시다. 모델 부분만 세 배 빨라져도 총 시간은 2초에서 1.4초가 됩니다. 사용자가 느끼는 개선은 약 1.43배입니다. 같은 600ms 절감을 하더라도, 검색 결과를 너무 공격적으로 줄여 핵심 문서가 빠진 경우와 내부 연산을 효율화한 경우는 품질의 원인이 전혀 다릅니다.

서비스의 응답 시간이 평균 1.4초가 됐더라도, 사용자 경험은 느린 꼬리 구간의 영향을 받습니다. 검색이 자주 타임아웃을 일으키면 평균은 나아져도 느린 요청들의 지연은 그대로일 수 있습니다. 응답 첫 부분까지 걸린 시간과 전체 완료 시간도 서로 다릅니다. 한 문장을 빨리 띄워 주는 UI가 내부 계산을 빨리 끝냈다고 볼 수 없는 것처럼, 긴 설명까지 기다리는 도구에서는 총 시간이 더 직접적인 지표입니다.

두 가지를 동시에 최적화하려면 입력 질문을 고정하고, 검색 문서 집합과 모델 설정을 한 번에 하나씩 바꿔 비교할 수 있습니다. 검색을 비교할 때는 필수 근거 검색률과 출처가 실제로 지원하는 주장 비율을, 모델을 비교할 때는 동일한 자료에서 답변 정확도와 지연 분포를 봅니다. 비용도 별도로 봐야 합니다. 메모리에 저장되는 모델 크기, 요청당 연산량, 실제 기기가 소비하는 시간, 외부 검색 호출 비용은 서로 다른 숫자입니다. 내부 단계와 비트 폭을 줄이는 방법이 효율을 개선하더라도, 검색 호출 횟수가 늘거나 요청당 동시 처리 수가 줄면 운영 비용이 내려가지 않을 수 있습니다. 벤치마크에서는 단일 답변 시간을, 서비스에서는 같은 품질 기준에서 초당 완료 요청 수와 지연을 함께 기록하는 편이 유용합니다.

출처의 질이 중요한 분야에서는 찾은 근거를 그대로 표시하고 검토자가 열 수 있게 하는 편이, 내부 추론을 장문으로 풀어 쓰게 하는 것보다 검증에 직접적인 도움이 될 수 있습니다.

어떤 병목부터 줄일지 정하는 실험

가상의 배포에서는 같은 이미지와 문항으로 실시간 단건, 소규모 묶음, 대규모 묶음을 나눠 잴 수 있습니다. 단건에서는 처음으로 답을 볼 때까지 걸리는 시간을, 묶음에서는 같은 메모리로 제한 시간 안에 완료한 건수를 비교합니다. 이미지 크기와 출력 길이도 기록해야 지연 변화가 입력 조합 차이 때문인지 가려낼 수 있습니다. 내부 벡터의 단계 수와 비트 폭을 둘 다 바꾸면 어느 변경이 품질 손실을 만들었는지 모르므로, 하나를 고정한 비교군도 둡니다. 정확도가 무너지면 전체 비트를 원상복구하기 전에 표 읽기나 작은 개체처럼 성능이 특히 떨어진 유형부터 분리해 봅니다. 이렇게 해야 절감한 시간과 다시 사람이 검토해야 할 일을 같은 서비스 단위에서 비교할 수 있습니다.

가령 기준 모델과 경량 모델을 각각 200문항에서 비교하면서, 기준 모델만 맞힌 문항과 경량 모델만 맞힌 문항을 따로 세어 보겠습니다. 두 모델이 모두 160문항을 맞혔다고 해도 각각 다른 15문항에서 실패했다면, 운영 위험이 같다고 보기 어렵습니다. 특히 답이 숫자로만 표시되는 표, 희미하게 인쇄된 소수점, 이미지와 텍스트가 서로 충돌하는 자료를 따로 묶으면 같은 정확도 뒤에 숨어 있던 문제를 찾을 수 있습니다. 이 예시 수치는 논문 결과가 아닙니다. 정확도 하락을 발견하면 배포에서 더 정밀한 경로로 넘길 수 있는 입력 특성이 있는지까지 확인합니다. 특성을 미리 구별하지 못하면, 두 모델을 섞는다는 아이디어가 검증 비용과 지연만 늘릴 수도 있습니다.
