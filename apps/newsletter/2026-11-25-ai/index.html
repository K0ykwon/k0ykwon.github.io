Anthropic이 Claude Opus 4.5 API의 종료 일정을 공개했습니다. 권장 대체 모델인 Opus 5.5로 넘어갈 때 API 요청이 성공하는지만 확인하면 실제 사용자 경험의 변화를 놓칩니다. 같은 사실을 답하더라도 출처를 제대로 붙이는지, 자료에 없는 내용은 답하지 않는지까지 비교해야 합니다. 최근 공개된 후학습 연구는 왜 최종 정답률 하나로 그 차이를 알아채기 어려운지 보여줍니다.

최신 AI 소식

Claude Opus 4.5 종료 일정과 Opus 5.5 이전

Anthropic은 11월 23일 Claude API에서 Opus 4.5의 지원 종료를 예고했습니다. 예정일은 2027년 1월 22일입니다. 날짜가 들어간 claude-opus-4-5-20251101과 짧은 ID claude-opus-4-5가 모두 대상이며 권장 대체는 claude-opus-5-5입니다. 5.5는 9월 22일에 출시된 모델이므로 이번 소식은 새 모델 발표가 아니라 구 모델의 종료 공지입니다. 다른 클라우드에서 제공하는 Claude의 수명 주기는 해당 플랫폼 기준을 별도로 확인해야 합니다. 공식 종료 공지

공식 사양상 Opus 5.5는 100만 토큰 문맥을 지원하고 표준 최대 출력은 12만 8천 토큰입니다. Claude API의 기본 요금은 백만 입력 토큰당 4달러, 출력 토큰당 20달러이며, 적응형 추론은 항상 켜져 있고 깊이는 effort로 조절합니다. 가령 캐시나 별도 도구 비용을 제외하면 입력 2만, 출력 2천 토큰은 0.12달러입니다. 이 계산은 처리된 토큰 수가 같다고 가정한 단가 예시입니다. 같은 프롬프트라도 생성이 길어지거나 도구 호출이 늘면 건당 비용과 대기 시간은 달라집니다. 모델 사양 · 이전 가이드

업무에서 변경을 확인할 때는 모델 이름이 들어간 코드 한 줄보다 호출 경로부터 살펴볼 만합니다. 대화 서비스, 배치 작업, 장애 시 폴백은 같은 모델 ID를 서로 다른 설정으로 쓸 수 있습니다. 예전 모델이 살아 있을 때 두 버전을 나란히 평가하면, 새 모델에 맞춰 설정부터 바꾸더라도 어떤 변화가 모델 때문이고 어떤 변화가 설정 때문인지 비교할 기준을 남길 수 있습니다. 단, 같은 입력을 넣었다고 모델의 내부 연산량까지 같아지는 것은 아니므로 실제 응답 속도와 비용도 따로 기록해야 합니다.

어떤 설정을 우선 고정해야 하나

서비스에 연결된 모델은 대화 엔드포인트 하나로 끝나지 않습니다. 화면에 답을 보내는 경로와 문서에서 값을 뽑아 데이터베이스에 적는 경로는 같은 모델이라도 다른 실패를 냅니다. 대화에서는 몇 문장 더 길어지는 문제가 주로 사용자의 대기 시간을 늘립니다. 반면 값 추출 작업에서 같은 변화가 일어나면, 예전에는 빈 문자열이던 자리에 설명문이 붙어 레코드 형식 전체를 깨뜨릴 수 있습니다. 먼저 사용자가 보는 기능 단위로 호출 경로를 정리하고 모델 이름, 설정, 출력의 계약을 나눠 기록하는 것이 좋습니다.

이전 전후 동작을 보는 실험은 두 번으로 나눌 수 있습니다. 한 번은 같은 호출 환경과 고정된 자료를 넣어 두 모델의 기본 동작을 비교합니다. 이후 실제 배포하려는 설정을 적용해 출력 길이와 재시도까지 합친 작업당 비용을 다시 잽니다. 5.5의 effort는 추론 깊이를 제어하는 설정이므로, 이를 바꿨다면 변경 전후를 같은 기준으로 채점해야 합니다. 구 모델과 값 이름이 같아 보이더라도 내부 계산량이 같다는 뜻은 아닙니다. 버전 차이와 추론 설정의 영향을 모두 알려면 새 모델에서 두 설정을 별도의 비교군으로 남기는 편이 낫습니다. 모델 이전 가이드

가령 한 달 1만 건에서 모든 요청이 캐시·도구 없이 0.12달러라는 가상의 조건이면 모델 비용은 1,200달러입니다. 그중 400건이 형식이나 근거 실패로 정확히 같은 비용의 재시도 1회를 필요로 한다면 48달러가 추가됩니다. 같은 모델이라도 제일 비싼 경로가 몇 번 반복되는지에 따라 비용은 달라집니다. 비교표에는 첫 응답 단가 외에 하나의 업무 결과를 확정하기까지의 총 호출 수와 완료 시간을 넣습니다. 정지한 구 모델을 교체한 뒤 되돌리는 것은 현실적인 복구 옵션이 아닐 수 있으므로, 독립적인 대체 경로도 종료 전에 시험해 두어야 합니다.

주목할 만한 논문

최종 답이 맞아도 잘못된 사실을 학습할 수 있다

Atmakuru와 Goyal이 11월 19일 공개한 프리프린트는 모델이 강화학습 과정에서 스스로 만든 사실 오류를 나중에 더 자주 재현하는지 조사했습니다. QuALITY와 TriviaQA를 써서 6개 공개 모델의 학습을 분석했습니다. 각 답변의 중간 서술에서 틀린 원자적 사실을 추출하고, 그 사실이 등장한 전후 체크포인트의 재현 점수를 추적했습니다. 비교군에는 잘못된 서술이 만들어졌지만 학습 신호를 받지 않은 경우를 뒀습니다. 논문 원문과 표 1

실험의 핵심은 틀린 답변 자체에 보상했다는 이야기가 아니라는 데 있습니다. 한 번의 생성에서 최종 답을 맞혔지만 그 앞에서 관련 없는 틀린 전제를 제시할 수 있습니다. 결과에만 보상을 주는 GRPO에서는 최종 답의 품질을 기준으로 생성 전체의 학습 가중치를 배정합니다. 그러면 같은 줄기에 들어 있던 틀린 전제가 올바른 최종 답과 함께 강화될 여지가 생깁니다. 저자들은 이후 모델이 바로 철회했던 잘못된 서술에서도 암기 효과를 관찰했습니다.

표 1에서 학습 중 강화된 잘못된 사실의 평균 재현 점수는 4.83포인트 올랐고, 학습 신호가 없는 비교군은 0.17포인트 올라갔습니다. 이 숫자는 평가에 사용한 사실의 재현 점수 변화이지, 서비스의 전체 환각률이 그만큼 오른다는 뜻은 아닙니다. 두 지식 과제와 공개 모델 실험에서 드러난 메커니즘이며, Anthropic 모델의 학습이나 품질을 검증한 연구도 아닙니다. 실험 방법과 한계

잘못된 문장을 집어내는 법과 실제 채점의 단위

논문이 보는 실패는 서로 모순되는 단락 중 하나를 잘못 선택했다는 수준으로 끝나지 않습니다. 오답 서술이 무엇을 가리키는지를 짧은 사실 주장으로 쪼개면 같은 주장이 나중에 다른 문장으로 다시 나왔는지 살필 수 있습니다. 예를 들어 설명을 위해 만든 가상 질문을 보겠습니다. “내부 안내에서 사무실 이전 날짜는 4월 8일이다”라고 시작해도, 중간에 “건물은 지난해에 완공됐다”는 근거 없는 문장을 붙이면 최종 날짜만 보는 채점기는 정답으로 처리합니다. 나중에 건물이 언제 완공됐는지를 다른 말로 물었을 때 모델이 같은 가짜 정보를 지지하는지가 별도 관심사입니다.

이 비교에서는 사실 전후의 어떤 모델을 쓰는지와 무엇을 대조군으로 두는지가 중요합니다. 훈련을 더 돌린 뒤 틀린 사실을 더 자주 말했다는 결과만으로는 원래 모델이 알고 있던 정보인지, 같은 주제의 다른 학습 데이터 때문인지 구별하기 어렵습니다. 그래서 연구는 후학습에서 나온 오류와 그것이 결과적으로 학습 신호를 받았는지를 추적합니다. 틀린 사실이 만들어졌으나 학습 신호를 받지 않은 경우와 비교하면 적어도 “나중의 모든 변화”와 “해당 결과를 강화한 조건의 변화”를 구분할 수 있습니다. 다만 무엇을 사실로 뽑느냐, 평가 질문을 어떤 표현으로 만드는지에 따라 집계에는 차이가 남습니다. 이 검증의 목적은 특정 업데이트에 따른 재현 가능성이지, 모든 사용자 요청의 정확성 순위를 정하는 것이 아닙니다. 원문 평가 방법

이 문제를 완전히 피하려고 중간 설명의 문장을 전부 검증할 수도 있지만, 설명에 필요한 외부 지식까지 확인하려면 추가 검색과 사람이 필요합니다. 사실 검증 예산을 어디에 쓸지 정한다면 최종 답을 바꾸는 전제, 결과를 다른 사람이 따라야 하는 조건, 출처에 없는 단정을 우선하겠습니다. 틀린 사실을 한 번 썼으나 문장 내에서 명시하고 철회한 사례와, 같은 오류를 출처 없이 끝까지 사실처럼 남긴 사례도 제품 평가에서는 구분해야 합니다. 둘 다 훈련 중에 어떤 신호를 받았는지를 연구하는 데는 관심 대상이지만 사용자가 받은 결과에서의 영향은 다릅니다.

오늘의 개념: 모델 교체와 사실 검증

최종 정답률과 근거에 맞는 답을 분리하기

회사 안내문에서 ‘출장비 신청 금액의 상한’과 ‘신청 마감일’을 묻는다고 합시다. 구 모델과 신모델이 모두 올바른 금액을 말해도, 둘 중 하나가 다른 부서의 규정을 인용하거나 원문에 없는 마감일을 덧붙일 수 있습니다. 금액만 채점하면 둘 다 통과합니다. 사람이 실제로 따라야 할 답은 금액, 적용 범위, 마감, 출처가 함께 맞아야 합니다. 그중 어떤 정보가 반드시 있어야 하는지, 없어야 하는지를 채점표에 명시하면 평균 점수 뒤에 숨는 실패를 찾을 수 있습니다.

비교 세트는 자료에 답이 있는 질문뿐 아니라 자료가 없어서 유보해야 하는 질문, 개정 전후 문서가 함께 있는 질문을 포함할 수 있습니다. 쌍으로 비교할 때는 동일한 문서 버전과 도구 설정을 사용하고, 정답·형식 적합·인용의 실제 뒷받침·적절한 유보를 각각 기록합니다. 고위험 유형의 실패가 늘었다면 평균 정답률이 높아져도 해당 유형만 검토 대상으로 분리할 수 있습니다. 응답에 드러난 사실과 인용을 평가하는 방법이라, 모델의 비공개 추론 기록을 요구할 필요도 없습니다.

오프라인 비교 뒤에는 작은 범위에서 새 모델을 관찰할 수 있습니다. 외부에 실제로 보내거나 상태를 바꾸는 도구라면 두 모델로 작업을 중복 실행하는 대신, 같은 입력에서 나오는 실행 계획만 비교하거나 쓰기를 막은 환경을 사용합니다. 이후 실제 전환에서 확인할 것은 API 오류율, 응답 길이, 비용뿐 아니라 새 모델이 예전에는 피하던 특정 오류를 만드는지입니다. 이전의 목표는 모든 답변을 옛 모델과 똑같게 만드는 것이 아니라, 사용자에게 중요했던 품질 기준을 모델 ID가 바뀐 뒤에도 지키는 것입니다.

평균 점수가 좋아도 이전을 멈출 수 있다

가상 실험에서 답이 있는 질문 120건, 원문이 없는 질문 50건, 개정 전후를 골라야 하는 질문 30건을 같은 규칙으로 채점해 봅시다. 신모델이 첫 그룹에서 구 모델보다 12건을 더 맞히고 나머지 두 그룹에서 3건씩 더 실패했다면, 전체 맞힌 문항 수는 6건 늘었습니다. 그러나 원문이 없으면 반드시 유보해야 하는 서비스라면, 유보 그룹의 3건 악화만으로 먼저 전환을 멈출 만합니다. 기준을 실험 전에 적어 두면 결과를 본 뒤 유리한 평균으로만 결정을 정당화할 수 없습니다.

각 답변에서 모든 문장이 맞을 필요와 문항에서 정확히 요구한 것을 샅샅이 전달할 필요는 별개입니다. 자동 평가를 만든다면, 출처 링크가 붙은 비율, 링크 안 문장이 주장을 뒷받침한 비율, 답변에 꼭 포함되어야 하는 필수 조건이 있는 비율을 서로 다른 분모로 나눕니다. 출처가 둘 이상이면 권위만 보지 말고 게시 시점과 적용 범위가 맞는지도 확인합니다. 모델이 문서를 열었다고 주장하는 것에 의존하지 말고, 외부 자료를 실제로 열 수 있는 검토 환경을 준비해야 합니다. 소량의 사람이 판정한 샘플로 자동 채점과의 불일치도 기록하면 채점에 드는 비용을 설명할 수 있습니다.

실제 전환의 첫 단위는 조직 전체가 아니라 한 경로일 수 있습니다. 읽기 전용 요약으로 시작해 문제가 없을 때만 알림 생성이나 레코드 저장처럼 부작용이 있는 기능을 붙입니다. 재현 가능하게 남길 기록도 최종 출력, 사용 모델 ID, 공개 가능한 입력 버전, 도구 결과와 시간 정도면 됩니다. 내부 추론 전체를 받아야 하는 설계라면 비교 가능성도 개인정보 관리도 오히려 나빠질 수 있습니다. 모델 교체가 좋은 변화인지 알려면 구 모델을 그대로 닮았는지보다, 실제 사용자에게 필요한 사실을 빠뜨리거나 부풀리지 않는지부터 살펴야 합니다.

문장보다 질문 쌍을 남겨야 다시 비교할 수 있다

규정이 바뀌기 전 문서와 바뀐 뒤 문서를 함께 제공한 상태에서, 현재 시점의 질문과 과거 시점의 질문을 쌍으로 만들 수 있습니다. 같은 액수를 답해도 한쪽은 맞고 다른 쪽은 틀리도록 만들면, 모델이 익숙한 수치를 반복하는지 아니면 날짜를 근거에 연결하는지 드러납니다. 문서의 위치나 순서도 반대로 바꿔 보세요. 답이 마지막 문서를 무조건 따라간다면 그 행동은 최신 규정을 이해한 것과 다릅니다. 이런 쌍을 따로 표시해 두면 모델이 또 바뀌더라도 같은 오류 유형을 다시 확인할 수 있습니다.
