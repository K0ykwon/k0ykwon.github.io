AI가 파인튜닝을 맡으면, 누가 성능을 검증하나?

Inkling 2 Mini 공개와 Unsloth Studio 업데이트에서 출발해, 모델이 자기 답으로 배우는 연구와 파인튜닝 플랫폼 선택, 실제 개선을 가려내는 실험 설계를 읽습니다.

이 글의 흐름
최신 AI 소식주목할 만한 논문오늘의 개념: 미세조정과 검증

Thinking Machines는 Inkling 2 Mini의 가중치를 공개했고, Unsloth는 이 모델을 로컬에서 실행하는 도구를 업데이트했다. 같은 모델을 내 컴퓨터에서 실행하는 것과, 내 데이터로 다시 학습시키는 것은 어디서 갈릴까? 두 소식에서 출발해 모델이 자기 답으로 배우는 연구를 살펴보고, 실제로 성능이 좋아졌는지 판별하는 실험까지 설계해 본다.

최신 AI 소식

Inkling 2 Mini: 같은 층을 반복해 계산하는 공개 모델

Thinking Machines Lab은 11월 20일 Inkling 2 Mini의 가중치를 Apache 2.0으로 공개했다. 텍스트와 이미지를 입력받아 텍스트를 생성하는 모델이다. 저장된 층은 24개지만, 가운데 12개 층을 토큰마다 세 번 적용한다. 앞뒤 6개 층은 한 번씩 지나가므로 실제 층 적용 횟수는 48회다. 서로 다른 층의 가중치를 48개 저장하는 대신 같은 가중치로 계산을 반복하는 방식이다. 개발사 발표에서 반복 계산은 여러 단계를 잇는 추론에 도움이 됐지만, 이미 학습한 사실을 꺼내 답하는 문제에서는 효과가 제한적이었다. 공식 발표 · 모델 카드

이 반복은 한 번의 추론 안에서 일어난다. 같은 층을 더 거친다고 가중치가 업데이트되거나 다음 대화까지 학습이 남는 것은 아니다.

Unsloth Studio: 로컬에서 실행하고, 지원 모델은 학습까지

Unsloth Studio는 로컬에서 모델을 실행하고, 학습을 지원하는 모델은 데이터셋을 골라 미세조정할 수 있는 도구다. Inkling 2 Mini의 경우 Unsloth가 공개한 4비트 GGUF 중 하나인 UD-Q4_K_M의 파일 크기는 16.61GB다. 파일 크기는 전체 실행 메모리가 아니다. 문맥을 저장하는 KV 캐시와 실행 환경의 메모리도 필요하다. 11월 23일 베타는 모든 전문가 가중치가 GPU에 들어가는 조건에서 프롬프트 처리가 최대 1.9배 빨라졌다고 보고했고, 추측 디코딩을 적용했을 때의 개선은 1.15~1.19배로 따로 제시했다. 같은 기준에서 모든 장비가 1.9배 빨라진다는 결과는 아니다. Unsloth 베타 릴리스 · GGUF 모델 카드 · Studio 가이드

여기서 눈여겨볼 구분이 있다. Inkling GGUF가 로컬에 올라간다는 말은 실행이 가능하다는 말이다. 그 체크포인트로 Studio에서 LoRA를 학습할 수 있다는 보장은 아니다. 추론과 학습의 차이를 보여 주는 사례가, 같은 모델 계열의 Inkling 2 Small을 이용한 다른 실험이다.

Inkling 2 Small이 학습한 것은 자기 자신이 아니었다

Thinking Machines Lab은 Inkling 2 Small에 별도의 Qwen3.5-4B 모델을 시계열 예측에 맞게 튜닝하는 일을 맡겼다. 입력은 과거 값의 나열이고, 출력은 다음 시점의 값이다. 날씨나 위키백과 페이지 조회 수처럼 성격이 다른 시계열을 다뤘다. 같은 입력을 여러 번 샘플링해 얻은 예측의 중앙값이 실제 값에 가까워야 했고, 예측값의 퍼짐도 실제 불확실성과 맞아야 했다. 점예측 하나를 잘 내는 것보다 까다로운 조건이다. Thinking Machines Lab 발표와 데모 기록

Inkling이 한 일은 답안을 써주는 데서 끝나지 않았다. 채점 코드를 작성하고, 학습 예제와 방법을 바꾸고, 지도 미세조정(SFT)과 강화학습(RL)을 실험하며 실패를 디버깅했다. 실제 학습 연산은 Tinker에서 수행했다. 개발사는 4.5시간, Tinker 사용료 426달러로 내부 과제의 예측 점수가 두 배 이상 올랐다고 보고했다. 이 수치는 예측 오차가 모든 시계열에서 절반이 됐다는 뜻도, 사람보다 비용이 적게 든다는 뜻도 아니다. 발표에 나온 과제와 평가 방식에 한정된 점수이며, 426달러는 명시된 Tinker 사용료다. 다른 방법으로 같은 목표에 도달하는 데 드는 총비용은 별도 비교가 필요하다. 실험 설명과 프롬프트

이 사례의 역할을 나누면 선명해진다. Inkling은 실험을 운영한 에이전트, Qwen은 학습된 모델, Tinker는 학습을 실행한 플랫폼이다. 그래서 이것을 ‘에이전트가 주도한 파인튜닝’이라고 부르는 편이 정확하다. Inkling이 자기 가중치를 바꾼 시연은 아니다.

주목할 만한 논문

STaR: 정제된 답을 학습 데이터로 바꾸는 법

모델에게 “방금 답을 다시 검토해 봐”라고 했더니 오답이 정답으로 바뀌었다고 하자. 그 세션에서는 좋아졌지만, 검토 내용 없이 새 요청을 보내면 똑같이 틀릴 수 있다. 추론 때 받은 문맥만 달라졌고, 모델이나 어댑터의 가중치는 그대로이기 때문이다. Self-training은 그런 교정의 일부를 학습 데이터로 만들어 다음 요청에도 남기려는 시도다.

대표적인 예인 STaR는 먼저 몇 개의 풀이 예시를 보여주고, 모델이 문제의 풀이와 답을 여러 개 생성하게 한다. 답이 맞은 풀이를 학습에 사용한다. 처음 틀린 문제에는 정답을 알려준 상태로 풀이를 다시 만들게 하는 단계도 있다. 이렇게 모은 풀이로 미세조정하고 과정을 반복한다. 이때 정답 힌트는 학습 예제 수집용이다. 최종 시험에서 정답을 보여주고 문제를 풀게 하면 측정의 의미가 사라진다. STaR 논문

간단한 예로 표에서 결제 금액을 합산해 JSON으로 돌려주는 모델을 생각해 보자. 문제 하나에 답을 네 번 만들게 하고, JSON 형식뿐 아니라 실제 합계와 증빙 행 번호까지 프로그램으로 대조한다. 합계가 맞아도 관계없는 행을 근거로 적은 답은 버린다. 통과한 답 중 사실상 같은 풀이가 여러 개라면 하나만 남긴다. 어떤 입력에서 통과 예제가 전혀 나오지 않는지도 따로 기록한다. 그 구간은 반복 생성으로 채우기보다 사람이 예시를 추가하거나 검증 규칙을 점검할 후보가 된다.

정답 검사가 어려운 과제에서는 모델에게 자체 채점을 맡기는 접근도 있다. 예를 들어 Self-Rewarding Language Models는 모델이 판정자로 답변을 채점하고, 그 점수에서 만든 선호 쌍으로 반복 학습했다. 다만 ‘모델이 5점을 줬다’는 기록은 실제 정답을 확인한 것과 다르다. 생성기와 판정기가 같은 오류를 자연스럽다고 받아들이면, 데이터가 늘어날수록 그 오류가 더 단단해질 수 있다. 모델 판정은 후보를 줄이는 보조 장치로 쓰고, 배포 판단에는 별도 규칙 검사나 사람 평가를 남기는 것이 좋다. Self-Rewarding Language Models

학습법은 달라도 채점기가 약하면 같은 곳에서 막힌다

SFT는 고른 예제의 목표 답변을 더 잘 재현하도록 학습한다. 반면 RL은 현재 모델이 생성한 답변에 보상을 주고, 높은 보상을 얻는 답변이 더 자주 나오도록 업데이트한다. 앞의 JSON 예제로 보면, SFT는 검증을 통과한 예시를 따라 쓰게 하고, RL은 학습 중 나온 후보를 채점해 성공한 패턴을 강화한다. 검증 가능한 답안이 충분하면 SFT 한 번으로 기준선을 만드는 편이 단순하다. RL은 그 기준선에서 더 나아갈 이유가 있고, 반복 샘플링과 채점에 쓸 예산이 있을 때 비교할 만하다.

두 방법 모두 채점 규칙의 빈틈을 그대로 물려받는다. 합계만 검사하면 모델은 우연히 맞은 답도 학습할 수 있다. 흔한 입력만 검사하면 드문 단위나 환불 행에서 성능이 나빠져도 평균에 묻힌다. 모델이 만든 예제 중 성공한 것만 채택할 때도 비슷한 문제가 생긴다. 모델이 이미 잘하는 쉬운 문제가 더 많이 살아남기 때문이다. 그래서 통과율 외에 실패한 입력의 종류와 채택된 데이터의 분포까지 기록해야 한다. 다음 라운드에서 어느 입력을 더 모을지 결정하는 근거가 된다.

오늘의 개념: 미세조정과 검증

Tinker: 학습 루프를 코드로 제어하고 GPU는 맡긴다

Tinker에서는 지원 모델의 LoRA 학습 클라이언트를 만들고, 어떤 예제를 넣어 어떤 손실로 학습할지 코드로 정한다. SDK에는 기울기를 계산하는 단계와 그 기울기를 적용하는 단계가 따로 있고, 중간 체크포인트에서 답을 샘플링하거나 학습을 재개할 수 있다. 같은 데이터에 여러 학습률을 적용하거나, 생성·채점·학습을 여러 차례 반복하는 실험에 유리하다. 결과를 밖에서 쓰려면 체크포인트 내보내기와 실제 서빙 엔진에서 해당 모델의 어댑터를 읽을 수 있는지까지 확인해야 한다. 학습 클라이언트 · 체크포인트 내보내기

Inkling 2 Mini는 Tinker 문서 기준 학습 문맥이 64K 또는 256K이고, 두 옵션 모두 샘플링 문맥은 최대 1M이다. 64K 옵션의 학습 단가는 백만 토큰당 0.75달러, 샘플 출력 단가는 0.50달러다. 예를 들어 100만 학습 토큰과 100만 샘플 출력 토큰을 쓴다면 두 항목만 합쳐 1.25달러다. 샘플에 넣는 입력 토큰, 평가, 재시도, 반복 학습은 이 예시에서 빠져 있다. 특히 한 문제에서 네 번 생성하거나 여러 체크포인트를 비교하면 샘플링과 검증 사용량이 빠르게 늘어난다. 실험 전에는 모델의 문맥 길이보다 라운드별 최대 호출 수와 비용 한도를 먼저 정해 두는 편이 좋다. 공식 모델·요금표

Unsloth Studio: 내 장비에서 데이터를 보고 바로 실험한다

Unsloth Studio는 지원 모델과 데이터셋을 GUI에서 선택해 학습하고 결과를 비교하는 진입점을 제공한다. 소량의 예제를 넣어 데이터 형식이 맞는지 점검하고, 짧게 학습한 체크포인트가 기대한 방식으로 답하는지 확인하기 좋다. LoRA는 원본 가중치를 고정하고 작은 보정 행렬을 학습한다. QLoRA는 여기에 원본 모델을 저정밀로 저장하는 방식을 결합해 메모리 부담을 줄인다. 그래도 문맥 길이와 배치 크기가 커지면 중간 계산값과 학습 상태에 메모리가 더 필요하다. 모델을 띄울 수 있다는 것과, 원하는 길이로 학습시킬 수 있다는 것은 별도로 확인해야 한다. Studio 가이드 · QLoRA 논문

로컬 학습의 첫 확인 항목은 모델 아키텍처, 학습용 체크포인트, 학습기가 지원하는 방식과 필요한 메모리다. 따라서 첫 자체 실험이라면 이미 로컬 학습이 확인된 작은 모델로 검증 절차를 만들고, Inkling을 훈련 대상으로 삼아야 할 때는 문서에 명시된 Tinker 경로부터 비교하는 것을 권한다. 중간 선택지로는 Hugging Face AutoTrain처럼 학습 레시피를 구성하는 도구도 있다. 어떤 플랫폼을 쓰든 첫 번째 실행은 전체 데이터가 아니라 소량으로 시작해, 어댑터 저장과 재로딩까지 확인하는 편이 안전하다. Unsloth GGUF 모델 카드 · Tinker Inkling 가이드 · AutoTrain SFT 문서

튜닝 효과를 판별하는 네 가지 비교군

첫째, 비교할 기준선이다. 같은 기반 모델을 대상으로 ① 원본, ② 같은 입력에 프롬프트만 개선한 모델, ③ 사람이 만든 소량의 검증 예제로 SFT한 모델, ④ 외부 검증을 통과한 합성 예제로 SFT한 모델을 비교한다. ③과 ④에서는 가능하면 학습 예제 수나 토큰 수를 맞춘다. 실제 서비스 후보를 비교할 때는 각 방식이 같은 처리 시간과 비용 제약을 충족하는지도 본다. 프롬프트만 개선해도 같은 결과가 나온다면 학습과 배포 비용을 추가할 이유가 줄어든다.

둘째, 학습에 섞이지 않는 문제다. 학습·개발·최종 평가 데이터를 실험 전에 분리한다. 문장만 바꾼 같은 문제나 같은 표의 일부 행이 양쪽에 들어가면 점수가 부풀 수 있다. 표 예제는 문서나 템플릿 단위로, 시계열은 예측 기준일 이후의 값을 학습 때 사용할 수 없도록 시간 순서로 나눈다. 개발용 문제로는 설정을 고를 수 있지만, 최종 평가의 정답이나 결과를 다시 학습 루프에 넣지 않는다. 에이전트가 평가 코드를 작성했다면 별도 검토자가 표본을 손으로 채점해 규칙이 원래 목표를 반영하는지도 확인한다.

셋째, 성공과 중단의 기준이다. 예를 들어 표 작업이라면 합계 정확도, 근거가 없는 행을 지어낸 비율, 형식 오류율을 따로 본다. 숫자가 있는 값을 지어내는 실패를 형식이 개선된 것으로 덮지 않는다. 시계열이라면 중앙값의 오차와 예측구간의 실제 포함률을 함께 확인하고, 단순한 이전값 기준선과도 비교한다. 개발셋에서 연속 두 라운드 개선이 없거나, 사전에 잡은 예산을 넘을 것으로 보이면 중단한다. 기록에는 모델 버전, 데이터 구분, 채점기 버전, 채택률, 생성·검증·학습 비용을 남긴다. 그래야 다음 개선이 새 학습 때문인지 채점 기준을 바꾼 효과인지 구분할 수 있다.

Inkling 데모에서 가져갈 만한 건 에이전트가 사람 대신 학습 버튼을 눌렀다는 사실보다, 하나의 목표를 두고 데이터·가설·학습 결과를 연결해 반복했다는 점이다. 반대로 사람이 놓지 말아야 할 권한은 성공 기준을 정하고 마지막 시험지를 지키는 일이다. 규모가 작은 팀이라면 먼저 검증 가능한 과제 하나와 손으로 확인한 예제 몇 개를 정하면 된다. 그 채점기로 원본 모델도 시험해 보고, 검증을 통과한 합성 예제를 모아 한 번만 학습해 보자. 개선이 확인되면 그때 두 번째 라운드와 플랫폼 확대를 결정해도 늦지 않다.
