문맥 창은 한 번의 요청에서 모델이 참고할 수 있는 범위를 말합니다. 긴 보고서 전체가 들어간다는 것은 여러 부분을 같은 요청에 제공할 수 있다는 뜻이지, 필요한 문장을 모두 찾거나 서로 충돌하는 조항을 정확하게 대조한다는 뜻은 아닙니다. 예를 들어 400쪽 계약서에서 특정 날짜를 찾아내는 문제와, 계약 변경 전후의 예외 규칙이 일관되는지 증명하는 문제는 입력 길이가 같아도 요구하는 답이 다릅니다. 전자는 해당 구절과 인용 위치가 주된 정답이고, 후자는 빠뜨린 조항이 없는지까지 평가해야 합니다.

Neon 공식 API 가격표는 과금 출력에 thinking 토큰이 포함되고 입력 캐시가 암묵적 방식이라고 설명합니다. 캐시된 입력 단가가 낮아도, 문서를 저장해 두었다는 이유만으로 호출마다 그 단가가 적용되는 것은 아닙니다. 비용 사례를 만들 때는 전체 토큰 수와 실제로 캐시 적중 처리된 토큰을 나눠야 합니다. 결과가 짧아도 내부 추론이 더 길 수 있으므로 화면에 보인 문장만 세어 출력 요금을 추정하는 일도 피해야 합니다.

가격표 숫자를 적용한 가상 사례입니다. 문서 입력 60,000토큰이 전부 비캐시이고 가시 출력 1,000토큰, thinking 출력 2,000토큰을 사용했다면 입력 0.18달러와 출력 0.045달러로 총 0.225달러입니다. 같은 요청에서 입력의 40,000토큰이 캐시 적중한 경우에는 일반 입력 0.06달러, 캐시 입력 0.006달러, 출력 0.045달러로 0.111달러입니다. 도구 비용과 세금은 빼고 모델 토큰만 산출한 예입니다. 두 값의 차이는 실제 캐시 적중이 있었을 때의 차이이지, 단가가 낮은 항목으로 전체 입력을 바꿔 계산할 수 있다는 뜻이 아닙니다.

모델 점수와 작업 방식의 차이

긴 문서를 계속 다루는 팀이라면 입력을 무작정 짧게 만드는 것보다, 어떤 내용이 반복되고 어떤 내용이 요청마다 바뀌는지 먼저 볼 수 있습니다. 매번 본문 앞에 같은 표준 매뉴얼이 들어가고 질문과 변경 자료만 바뀌는 환경은 반복 입력이 많습니다. 반대로 문서와 정책 버전이 수시로 바뀌면 입력을 재사용하기 어렵거나, 예전에 처리한 사항을 틀리게 가져오는 것이 더 큰 문제일 수 있습니다. 작업의 구체적인 구조를 적지 않은 채 모델 가격이나 전체 점수만 비교하면, 다른 조직에서 기록한 승자가 그대로 맞을 가능성은 낮습니다.

흐름의 큰 걸음과 시간당 연산은 다릅니다

한 토큰씩 내는 방식에서는 문장 뒤부분을 쓰기 전 앞부분을 기다립니다. 반면 마스크된 위치 여러 개를 보고 그 후보들을 함께 다듬는 방식은 한 번의 갱신에서 서로 떨어진 위치가 바뀔 수 있습니다. 다만 처음에 후보를 한꺼번에 내면 문장의 앞뒤 관계가 맞지 않을 수 있으므로 중간 표현을 반복해서 정제할 필요가 있습니다. 흐름 지도는 한 시점에서 조금 다음으로 이동하는 작업을 여러 번 하는 대신, 더 멀리 떨어진 시점의 상태를 바로 예측하는 방식으로 읽을 수 있습니다.

자기 조건화는 현재의 입력만 보는 것이 아니라, 이전 정제에서 얻은 예측도 다음 갱신에 다시 사용하는 접근입니다. 이전 생각을 그대로 복사한다는 뜻은 아닙니다. 예를 들어 ‘현지 시각’이라는 앞부분과 뒤의 ‘14시’가 서로 맞지 않을 때, 이전 후보 두 개를 보고 둘 중 한쪽 표현을 바꿔 일관된 문장으로 만들 수 있다는 직관입니다. 학습된 모델이 실제로 어떤 후보를 고치는지는 별도 분석이 필요합니다. 논문은 이 자기 조건화 반복과 시간축의 흐름 단계를 다른 축으로 보고, 두 종류의 반복을 각각 압축하는 목표를 사용합니다. 생성 퍼플렉서티가 낮다는 말의 범위

생성 퍼플렉서티는 출력이 평가 언어 모델에서 얼마나 자연스럽거나 예측 가능하게 읽히는지에 관한 값입니다. 논문 결과에서 2단계에서 4단계로 바꾸며 93.66에서 73.86으로 내려갔다는 것은 저자들이 지정한 조건에서의 비교입니다. 독자의 문서에서 근거를 대거나, 계산 답을 맞히거나, 전후의 등장인물이 같은 인물인지 지키는 일은 이 값만으로는 평가되지 않습니다. 반복적이고 흔한 문장이 높은 확률을 받을 수도 있으므로 출력의 다양성과 후반 장문의 일관성은 평가 문항을 달리해 확인해야 합니다.

이 접근을 서비스 후보로 본다면 출력 길이가 같은 샘플끼리 묶고 가벼운 요청과 구조적 제약이 있는 요청을 나눕니다. 예를 들어 자연스러운 한 문단 쓰기와 숫자 열 개를 정확히 복사한 표 만들기는 실패의 정의가 다릅니다. 2단계 또는 4단계라는 설정을 고르기 전에 인정할 만한 실패율과 사용자에 보이는 대기 시간의 기준을 먼저 정할 수 있습니다. 이렇게 해야 연구의 정제 단계 비교와 상용 모델의 가격표 비교를 서로 독립적인 근거로 사용할 수 있습니다.

빠르게 끝난 답과 검증되어 끝난 답을 따로 기록합니다

여러 공급자의 모델을 옮겨 비교할 때는 먼저 같은 업무를 작은 단위로 정의합니다. 문서에서 최대 세 값을 뽑는 서비스라면 ‘세 값이 모두 일치하고 근거 위치가 유효할 때만 성공’인지, 두 값까지 맞으면 사람이 세 번째를 채우는 것이 허용되는지 정합니다. 성공의 정의가 바뀌면 가격표가 같아도 성공당 비용은 달라집니다. 문서 원본, 문서 제공 방식, 검색을 허용할지, 도구 실패 시 재시도를 허용할지까지 고정할수록 결과를 비교하기 쉽습니다.

가상 과제 100건에서 한 모델의 첫 답 75건이 검증을 통과하고, 재시도한 25건 가운데 10건이 추가로 통과한다고 합시다. 최종 성공은 85건이고 호출은 125번입니다. 모델과 도구에 총 8.50달러가 들었다면 자동 성공당 비용은 0.10달러입니다. 남은 15건을 사람이 끝내는 데 각 2달러가 든다면 최종 업무가 100건 모두 완료되는 기준의 총비용은 38.50달러, 건당 0.385달러입니다. 첫 숫자는 자동 경로의 효율, 둘째는 사람 부담까지 포함한 운영 비용입니다. 두 기준을 섞으면 저렴한 모델로 바꿨더니 검수 비용이 더 커진 이유가 감춰집니다.

실패 분모를 없애지 않습니다

첫 답과 재시도 답의 지연을 하나로 합한 평균만 보고 선택하면, 가장 늦어지는 작업을 놓칩니다. 간단한 문항 90개가 빠르면 몇 개의 긴 작업이 두 번씩 멈춰도 평균값은 괜찮을 수 있습니다. 전체 처리률과 함께 p95 완료 시간, 시간 초과 및 검증 실패 건수, 사람이 넘겨받아야 하는 건수를 따로 보여 주면 왜 어떤 배포가 더 안정적인지 드러납니다. 샘플이 100개보다 훨씬 적다면 꼬리 지연은 몇 건에 의존한다는 점도 밝혀야 합니다.

마지막으로 모델 가격이나 버전이 바뀌어도 이 비교 방식을 유지할 수 있게 원시 기록을 남깁니다. 모델 호출 비용과 검색·저장 비용을 각각 적고, 출력에서 발견한 문제를 입력 누락, 근거 불일치, 실행 실패처럼 구분합니다. 정보가 처음부터 없어서 답할 수 없는 문제는 더 비싼 모델로 여러 번 다시 써도 해결되지 않을 수 있습니다. 가능한 요청을 빠르게 처리하고 어려운 요청을 잘 가려내는 선택은, 모델 한 건의 요금을 낮추는 것보다 전체 업무를 적은 비용으로 끝내는 데 더 도움이 될 때가 있습니다.

어떤 비용을 줄일지에 따라 평가표도 달라집니다

지난달 구매 기록을 비교하는 서비스에서 세 상황을 나눠 볼 수 있습니다. 첫째, 같은 보고서를 반복해서 묻는 요청은 입력을 재사용할 기회가 큽니다. 둘째, 보고서 종류는 같지만 매번 다른 회사의 문서를 받는 요청은 겉보기 길이가 비슷해도 이전 입력이 그대로 재사용되지 않습니다. 셋째, 회사 이름만 들어오고 보고서가 빠진 요청은 추론을 늘려도 확인할 근거가 생기지 않습니다. 각각의 수요를 모르고 모든 요청에 캐시 할인을 적용하거나, 실패 문항을 모두 다시 실행하면 예산을 잘못 잡을 수 있습니다.

경로를 고를 때에는 사실 확인이 쉬운 것과 어려운 것을 분리하는 것도 좋습니다. 행 합계처럼 기계적으로 다시 계산할 수 있는 값은 모델의 가시 답변을 빠르게 검사한 뒤 부족한 경우에만 비싼 경로로 보낼 수 있습니다. 반대로 서술형 판단의 타당성은 값의 형태만 읽어서는 알기 어렵습니다. 검증기가 틀린 답을 성공으로 잘못 승인하면, 처리 비용이 낮아지는 대신 사람에게 오류가 전달됩니다. 그러므로 재시도 정책과 검증 기준을 바꾼 시점도 모델 버전만큼 중요합니다.

개발팀이 한 번에 바꿀 수 있는 것이 하나라면, 먼저 무엇이 병목인지 살펴봅니다. 보고서 머리말을 반복해 전달하는 비용인지, 긴 후처리 대기인지, 초기 출력의 근거 부족인지에 따라 최선의 선택은 다릅니다. 반복 입력을 줄이는 실험과 재시도 비용을 줄이는 실험을 따로 설계하면, 한 설정에서 얻은 절약이 다른 서비스 환경에서도 재현되는지 판단하기 쉬워집니다.
