브라우저 추론과 Local first 설계

브라우저에서 모델을 실행하는 기술과 데이터를 사용자가 직접 소유하는 설계는 서로 다른 문제를 해결합니다. 전자는 계산을 어디에서 수행할 것인가, 후자는 서비스가 사라져도 사용자가 작업을 계속할 수 있는가에 관한 문제입니다. 오늘은 ExecuTorch WebGPU의 새 소식을 출발점으로, 두 질문을 하나의 개발 프로젝트에서 어떻게 연결할지 살펴봅니다.

이 글의 흐름
최신 Dev 소식오늘의 개발 개념브라우저 배포를 검증하는 방법오늘 해볼 작은 점검이번 호의 결론

브라우저에서 모델을 실행하는 기술과 데이터를 사용자가 직접 소유하는 설계는 서로 다른 문제를 해결합니다. 전자는 계산을 어디에서 수행할 것인가, 후자는 서비스가 사라져도 사용자가 작업을 계속할 수 있는가에 관한 문제입니다. 오늘은 ExecuTorch WebGPU의 새 소식을 출발점으로, 두 질문을 하나의 개발 프로젝트에서 어떻게 연결할지 살펴봅니다.

최신 Dev 소식

ExecuTorch가 PyTorch 모델의 브라우저 GPU 실행 경로를 공개했습니다

PyTorch는 11월 10일 ExecuTorch WebGPU 백엔드를 소개했습니다. PyTorch 모델을 torch.export로 내보내 .pte 파일로 만들고, WebAssembly 런타임과 브라우저의 WebGPU를 통해 실행하는 방식입니다. 발표에는 소형 언어 모델뿐 아니라 이미지 분할, 깊이 추정, 음성 인식 등 여러 종류의 데모가 포함됐습니다. 개발자가 주목할 변화는 모델을 브라우저에 배포하기 위해 반드시 다른 프레임워크의 포맷으로 옮겨야 하는 것은 아니라는 점입니다. PyTorch 발표

발표된 성능은 조건을 붙여 읽어야 합니다. Apple M1 Pro의 Chrome에서 양자화된 Llama 3.2 1B와 Qwen3 0.6B를 비교했을 때, ExecuTorch의 WebAssembly CPU 경로보다 프리필은 4∼7배, 디코드는 2∼10배 빨랐습니다. CUDA 서버보다 빠르다는 결과가 아닙니다. 또한 비교 양쪽의 활성값 표현도 같지 않습니다. WebGPU 쪽은 FP32 활성값, CPU 쪽은 동적 8비트 활성값을 사용했습니다. 이 수치는 특정 실행 경로의 개선을 보여 주지만, 모든 모델과 기기의 속도를 예측하는 배율로 사용할 수는 없습니다. 벤치마크 조건

실행 경로를 이해하면 실패 지점이 보입니다

전체 흐름을 간단히 쓰면 다음과 같습니다.

PyTorch 모델
→ torch.export
→ 실행 그래프와 백엔드에 위임할 연산 결정
→ .pte 파일
→ WebAssembly 런타임
→ WebGPU 연산
→ 브라우저의 결과 표시

여기서 중요한 것은 “파일 변환 성공”과 “실제 장치 실행 성공”이 다른 단계라는 점입니다. 공식 문서에 따르면 현재 WebGPU 분할기는 Vulkan 분할 경로를 재사용하며, 더 좁은 WebGPU 런타임의 지원 범위를 독립적으로 모두 검증하지는 않습니다. 따라서 내보내기가 끝났다고 호환성 확인까지 끝난 것은 아닙니다. 백엔드 자체도 실험적 단계입니다. WebGPU 구조와 현재 제약

지원 여부는 conv, add 같은 연산 이름만으로 결정되지 않습니다. 텐서 차원, 형태, 배치 방식, 자료형도 중요합니다. FP16 경로에는 장치의 shader-f16 지원이 필요하며, 동적 형태는 내보내기 때 지정한 최대 크기를 기준으로 버퍼를 확보합니다. 입력 상한을 지나치게 크게 잡으면 작은 입력을 넣어도 메모리 부담이 커질 수 있다는 뜻입니다. 연산 호환성 문서

개발 관점에서는 모델 전체를 한 번에 이식하기보다, 최소 입력과 대표 입력, 최대 입력을 따로 시험하는 편이 좋습니다. 예를 들어 이미지 모델이라면 “224 픽셀 입력에서 잘 됐다”는 결과를 “가변 해상도를 지원한다”로 확대하지 말고, 실제로 허용할 해상도 집합을 먼저 정하는 것입니다. 이는 특정 백엔드의 기능 설명이 아니라, 브라우저 배포에서 실패 범위를 좁히기 위한 실험 설계입니다.

오늘의 개발 개념

Local first는 오프라인 캐시보다 넓은 개념입니다

오프라인 캐시는 네트워크가 끊겼을 때 일부 기능을 유지하는 방법입니다. 반면 Local-first는 사용자의 기기에 있는 데이터가 실질적으로 유용한 작업본이 되도록 설계하는 방향입니다. 서버는 협업과 동기화를 도울 수 있지만, 사용자가 자신의 작업에 접근하는 유일한 관문이어서는 안 된다는 문제의식입니다.

Martin Kleppmann과 동료들의 Local-first software: You own your data, in spite of the cloud는 이 관점을 체계적으로 정리한 기반 논문입니다. 웹 글은 2019년 4월, 학술회의 논문은 Onward! 2019에서 발표됐습니다. 최신 논문이 아니라 오늘의 기술을 해석하는 데 유용한 고전으로 선정했습니다. 저자들은 오프라인 작업, 여러 기기에서의 접근, 협업, 장기 보존, 사용자 통제를 함께 추구하며 CRDT를 유력한 구현 기반으로 논의합니다. 모든 서비스를 로컬화하자는 주장은 아니며, 은행이나 전자상거래처럼 중앙 시스템이 잘 맞는 서비스와는 범위를 구분합니다. 논문과 전문

로컬 추론과 Local first를 구분해야 합니다

다음 두 제품을 가정해 봅시다.

첫 번째 제품은 모델을 브라우저에서 실행하지만, 분석 결과는 서버 계정에만 저장합니다. 계정에 접근하지 못하면 결과를 다시 열 수 없습니다. 계산은 로컬이지만, 작업의 보존과 접근은 여전히 서버에 종속돼 있습니다.

두 번째 제품은 계산 일부를 서버에 맡기더라도, 입력과 결과를 문서화된 형식으로 내려받을 수 있고 별도의 뷰어에서 다시 열 수 있습니다. 완전한 Local-first 제품이라고 단정할 수는 없지만, 적어도 사용자의 결과물 이동성과 보존성은 더 강합니다.

이 비교가 말하는 것은 단순합니다. 계산 위치, 저장 위치, 데이터 소유 가능성은 따로 평가해야 합니다. “온디바이스 AI”라는 설명만으로 자동으로 데이터 보존성과 상호운용성까지 확보되는 것은 아닙니다.

동기화의 어려움은 충돌을 없애는 것이 아니라 의미를 보존하는 데 있습니다

개념을 이해하기 위한 예시로, 두 사람이 오프라인에서 같은 모델의 설명을 수정하는 상황을 생각해 볼 수 있습니다. 한 사람은 이름을 바꾸고, 다른 사람은 입력 형태를 수정합니다. 서로 다른 필드라면 두 변경을 모두 살리는 것이 자연스럽습니다. 하지만 두 사람이 같은 필드를 서로 다르게 고쳤다면 무엇을 보여 줄지 결정해야 합니다.

CRDT가 다루는 핵심 중 하나는 복제된 데이터들이 변경을 교환한 뒤 일관된 상태에 도달하도록 하는 것입니다. 그러나 데이터의 수렴이 연구 결과의 의미적 타당성을 보장하지는 않습니다. 예를 들어 입력 형태만 갱신되고 그 입력에 의존하는 측정 결과가 그대로 남으면, 자료구조는 정상이어도 보고서는 모순될 수 있습니다.

브라우저 배포를 검증하는 방법

처음부터 모든 모델을 웹에서 실행하려고 하기보다는, 지원 범위가 분명한 작은 모델 하나로 시작하는 것이 좋겠습니다. 목표도 “GPU에서 돌아갔다”가 아니라 “사용자가 결과를 얻고 다시 활용할 수 있다”로 잡습니다.

  1. 정답 기준을 먼저 남깁니다. 동일한 입력에 대한 기존 PyTorch 출력과 전처리 조건을 저장합니다. 양자화를 적용했다면 양자화 전후 차이와 브라우저 실행 차이를 섞지 않고 따로 봅니다.

  2. 실행 시간을 분리합니다. 최초 모델 다운로드, 초기 준비, 첫 추론, 반복 추론 시간을 각각 기록합니다. 한 번만 쓰는 방문자에게는 반복 추론 속도보다 최초 사용 시간이 더 중요할 수 있습니다.

  3. 장치 실패를 제품 흐름에 넣습니다. WebGPU 지원 부족이나 메모리 부족을 사용자에게 설명하고, 분석 결과 열람처럼 가능한 기능은 유지합니다.

  4. 결과를 내보내고 다시 읽습니다. 생성된 분석 파일을 새 세션에서 열어 같은 구조와 측정 조건이 나타나는지 확인합니다.

여기서 첫 번째와 네 번째를 통과하지 못하면, 실행 데모는 만들었어도 재사용 가능한 연구 도구를 만들었다고 보기는 어렵습니다.

결과 파일을 모델 식별 정보와 함께 보존하기

예를 들어 “지연 시간 12ms”라는 값 하나만 저장하면 나중에 비교하기 어렵습니다. 어느 장치에서, 어떤 배치 크기로, 준비 과정을 포함했는지, 몇 번 실행했는지를 알아야 숫자가 의미를 가집니다. 모델의 표시 이름만 같고 가중치나 전처리가 달라도 다른 실험일 수 있으므로, 이름과 실제 산출물의 식별 정보도 분리하는 편이 안전합니다.

이 설계는 브라우저 실행 여부와 별개로 유용합니다. 오늘은 GPU 서버에서 측정하고 다음 달에는 브라우저에서 측정하더라도, 같은 조건과 다른 조건을 명확히 비교할 수 있기 때문입니다.

오늘 해볼 작은 점검

새 기능을 추가하기 전에 기존 분석 결과 하나를 내보낸 뒤 네트워크를 끊고 새 작업 폴더에서 다시 열어 보세요. 이때 다음 세 가지를 확인하면 됩니다.

  • 모델 구조와 입력 조건을 다른 사람도 해석할 수 있는가?

  • 측정 결과가 어느 모델과 실행 조건에 속하는지 알 수 있는가?

  • 원래 웹페이지 없이도 결과를 다시 읽거나 다른 도구로 옮길 수 있는가?

이 점검에서 막힌 부분은 “캐시를 조금 더 추가할 문제”일 수도 있지만, 파일 형식이나 데이터 의존 관계를 다시 설계해야 하는 문제일 수도 있습니다. 먼저 구분하면 불필요한 기능 개발을 줄일 수 있습니다.

이번 호의 결론

ExecuTorch WebGPU는 PyTorch 모델을 사용자에게 전달하는 선택지를 넓힙니다. Local-first는 전달된 도구와 결과를 사용자가 얼마나 오래, 얼마나 독립적으로 사용할 수 있는지 묻습니다.
