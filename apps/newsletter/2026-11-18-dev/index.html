실행 환경 비교와 캐시 비용

코딩 에이전트의 성능은 모델 이름 하나로 결정되지 않습니다. 같은 모델이라도 어떤 도구를 쓰고, 실패한 명령을 어떻게 재시도하며, 긴 작업 기록을 얼마나 유지하느냐에 따라 결과와 비용이 달라집니다. 오늘은 GitHub의 실행 환경 비교 기능과 에이전트 에너지 추정 연구를 연결해, 모델 바깥의 설계까지 포함한 성능 측정을 살펴봅니다.

코딩 에이전트의 성능은 모델 이름 하나로 결정되지 않습니다. 같은 모델이라도 어떤 도구를 쓰고, 실패한 명령을 어떻게 재시도하며, 긴 작업 기록을 얼마나 유지하느냐에 따라 결과와 비용이 달라집니다. 오늘은 GitHub의 실행 환경 비교 기능과 에이전트 에너지 추정 연구를 연결해, 모델 바깥의 설계까지 포함한 성능 측정을 살펴봅니다.

최신 개발 소식 실행 환경을 나란히 비교하는 벤치마크

GitHub는 11월 17일 Copilot 벤치마크 사이트에 에이전트 실행 환경인 harness 비교 화면을 공개 미리보기로 추가했습니다. Copilot CLI, Claude Code, Codex CLI를 같은 모델과 추론 강도로 맞춰 비교합니다. 정확히 대응되는 모델의 medium 설정만 포함하며, 다른 모델을 억지로 짝지은 결과는 제외합니다. 해결률과 작업당 평균 비용, 반복 실행의 변동, 짝지은 차이의 근사 95% 부트스트랩 구간을 함께 보여줍니다. 과학 연구 작업을 다루는 Terminal-Bench-Science 0.1도 추가됐습니다. 공식 발표

이 변화의 의미는 단순한 순위표 확대가 아닙니다. 엔진이 같은 자동차도 변속기와 제어 방식에 따라 연비가 다르듯, 모델을 둘러싼 프로그램도 성능의 일부입니다. 다만 공급자가 운영하는 벤치마크이고, 선택된 과제와 설정의 비교입니다. 한 화면에서 앞선 도구가 모든 저장소와 모든 개발 업무에서 우세하다는 뜻은 아닙니다.

오늘의 개발 개념 캐시 적중과 작업 비용

저장한 계산도 다시 읽어야 한다

자기회귀 언어 모델은 다음 토큰을 만들 때 앞선 문맥을 참조합니다. KV 캐시는 이전 토큰에서 계산한 attention의 key와 value를 저장해 반복 계산을 줄입니다. 새 토큰을 생성할 때 과거 토큰의 표현을 처음부터 다시 만들지 않아도 되는 것입니다. 하지만 새로운 query가 과거의 key 및 value를 이용하는 과정까지 사라지는 것은 아닙니다. Hugging Face의 KV 캐시 설명

따라서 “입력 토큰 대부분이 캐시에서 왔다”와 “문맥 처리 비용이 거의 없다”는 다른 말입니다. 캐시는 계산을 재사용하는 장치이지, 문맥을 무료로 만드는 장치가 아닙니다. 긴 문맥은 저장 공간과 읽기 작업을 요구합니다. 실제 비용은 모델 구조, 캐시 구현, 배치 크기와 하드웨어에 따라 달라지므로, 토큰 수만으로 전력량을 바로 환산하면 안 됩니다.

숫자를 어떻게 세느냐가 결론을 바꾼다

다음은 원리를 위한 가상 예시입니다. 10번의 요청이 각각 2,000개의 새 입력 토큰과 18,000개의 캐시 입력 토큰을 사용하고, 요청마다 500개를 출력한다고 가정합시다. 새 입력은 합계 20,000개지만, 캐시 읽기는 180,000개이고 출력은 5,000개입니다. 출력만 세면 5,000개, 새 입력까지 세면 25,000개, API가 보고한 모든 종류를 합하면 205,000개가 됩니다.

세 값 중 하나를 고르는 문제가 아니라, 서로 다른 양을 재고 있다는 점이 중요합니다. 각 종류의 처리 비용이 같지 않으므로 205,000개를 모두 동일한 단가나 동일한 에너지 계수에 곱하는 것도 정확하지 않습니다. API 청구액, 실제 실행 시간, 전력 소비량은 별도의 지표로 기록해야 합니다. 캐시 요금 할인율은 사업자의 가격 정책이지 물리적 에너지 절감률 자체가 아닙니다.

주목할 논문 Re Reading Is Not Free

11월 16일 제출된 이 프리프린트는 10주 동안의 AI 보조 개발 기록에서 42개 세션과 752개 작업 에피소드, 약 10억 토큰을 분석했습니다. 저자들은 API 보고 토큰의 94.8%가 캐시 문맥 읽기였고, 출력 토큰 하나당 약 260개의 캐시 토큰을 읽었다고 보고합니다. 여기서 비율은 해당 기록의 토큰 구성이지 전체 개발자나 모든 제품의 평균은 아닙니다. 논문 원문

저자들의 캐시 인지 추정기는 약 250 kWh, 비교한 출력 기반 추정기는 약 10 kWh를 산출했습니다. 약 25배 차이는 전력계로 확인한 소비량 차이가 아니라 추정 방식 사이의 차이입니다. 논문도 긴 캐시 문맥에서 두 추정기 모두 검증되지 않았다고 밝힙니다. 각 작업을 새 문맥으로 시작하면 추정량이 약 60% 감소하는 분석 역시 잃어버린 정보를 다시 찾는 비용을 더하지 않은 반사실적 계산입니다. 이를 그대로 실제 절감률로 약속할 수 없습니다. 방법과 한계

이 연구가 주는 실용적 경고는 “캐시를 쓰지 말라”가 아닙니다. 관찰된 토큰 기록과 그 기록에서 유도한 물리량을 구분하라는 것입니다. 성능 수치가 좋더라도 측정 경계가 다르면 서로 다른 실험을 비교하게 됩니다.

일반적인 활용과 평가 기준

개발 조직에서 도구를 비교할 때는 같은 과제 묶음, 같은 시간 예산, 같은 성공 판정 기준을 먼저 정하는 것이 좋습니다. 그다음 성공한 작업 수뿐 아니라 실패한 작업에 쓴 비용과 재실행 횟수도 포함합니다. 성공 사례만 남기면 가장 비싼 실패들이 통계에서 사라집니다.

예를 들어 가상의 도구 A가 100건 중 80건을 100달러에 해결하고, B가 100건 중 85건을 150달러에 해결했다면, 해결률은 B가 높지만 총비용을 성공 건수로 나눈 값은 A가 1.25달러, B가 약 1.76달러입니다. 어느 도구가 적합한지는 실패를 사람이 보완하는 비용과 처리 시간까지 고려해야 합니다. 이는 순위를 정하는 실제 실험 결과가 아니라 평가 지표가 답하는 질문을 구별하는 예시입니다.

긴 문맥을 유지하는 설계는 재검색을 줄이는 대신 반복 읽기를 늘릴 수 있고, 작업을 잘게 나누는 설계는 문맥을 줄이는 대신 연결 정보를 잃을 수 있습니다. 어느 쪽이 낫다는 고정된 답보다 전체 작업의 성공률과 총비용을 함께 측정하는 것이 중요합니다.

오늘의 결론

에이전트 성능은 모델, 실행 환경, 문맥 관리와 측정 방식이 함께 만드는 결과입니다. 같은 모델을 맞춰 비교하는 일과 캐시 비용을 구분해 세는 일은 결국 같은 원칙을 따릅니다. 무엇을 고정하고 무엇을 측정했는지 명확해야 개선을 믿을 수 있습니다.
