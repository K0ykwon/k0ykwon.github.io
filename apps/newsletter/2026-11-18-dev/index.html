최신 개발 소식 실행 환경을 나란히 비교하는 벤치마크

GitHub는 11월 17일 Copilot 벤치마크 사이트에 에이전트 실행 환경인 harness 비교 화면을 공개 미리보기로 추가했습니다. Copilot CLI, Claude Code, Codex CLI를 같은 모델과 추론 강도로 맞춰 비교합니다. 정확히 대응되는 모델의 medium 설정만 포함하며, 다른 모델을 억지로 짝지은 결과는 제외합니다. 해결률과 작업당 평균 비용, 반복 실행의 변동, 짝지은 차이의 근사 95% 부트스트랩 구간을 함께 보여줍니다. 과학 연구 작업을 다루는 Terminal-Bench-Science 0.1도 추가됐습니다. 공식 발표

이 변화의 의미는 단순한 순위표 확대가 아닙니다. 엔진이 같은 자동차도 변속기와 제어 방식에 따라 연비가 다르듯, 모델을 둘러싼 프로그램도 성능의 일부입니다. 다만 공급자가 운영하는 벤치마크이고, 선택된 과제와 설정의 비교입니다. 한 화면에서 앞선 도구가 모든 저장소와 모든 개발 업무에서 우세하다는 뜻은 아닙니다.

도구가 다른데 모델만 맞추면 무엇이 남는가

예를 들어 동일한 버전의 모델에 같은 버그 수정 요청을 준다고 합시다. 하나는 검색부터 시작해 관련 파일만 읽고, 다른 하나는 저장소의 설명서를 읽은 뒤 테스트를 먼저 실행할 수 있습니다. 둘이 같은 코드를 고쳐도 작업 기록의 길이와 새로 발생한 도구 입력은 다릅니다. 실행 환경은 이런 초기 전략을 어떻게 안내하는지, 도구 출력이 길어지면 무엇을 생략하는지, 명령 실패 후 같은 명령을 반복하는지에 차이를 만듭니다. ‘같은 모델’ 비교에서 남는 차이는 오히려 사용자가 실제로 설치할 도구 구성의 차이입니다.

짝지은 비교에서는 모든 과제를 두 도구에 같은 순서로 풀라고 요구하기보다, 과제 하나마다 두 실행 결과를 함께 놓습니다. 가령 작업 100개에서 A가 해결한 55개와 B가 해결한 58개에 큰 교집합이 있다고 가정해 봅시다. A만 성공한 게 10개이고 B만 성공한 게 13개라면 총 해결률 차이는 3%포인트지만 뒤바뀐 과제는 23개입니다. 테스트 구조나 언어 묶음별로 그 분포를 보면 단순 순위에서 보이지 않는 차이를 발견할 수 있습니다. 가상의 숫자로 보는 짝지은 비교이고 GitHub 결과가 아닙니다.

견고한 비교에는 실행 조건도 포함됩니다. 네트워크 허용 범위와 접근 가능한 문서, 시간을 늘렸을 때 얻는 추가 기회가 같지 않으면 도구 사용 정책의 차이까지 점수에 섞입니다. 고정 예산에서의 실험과 도구별 기본값 그대로의 실험을 따로 보면 ‘공정하게 제한을 맞췄을 때’와 ‘설치 직후의 사용 경험’이라는 서로 다른 질문에 답할 수 있습니다.

오늘의 개발 개념 캐시 적중과 작업 비용

저장한 계산도 다시 읽어야 한다

자기회귀 언어 모델은 다음 토큰을 만들 때 앞선 문맥을 참조합니다. KV 캐시는 이전 토큰에서 계산한 attention의 key와 value를 저장해 반복 계산을 줄입니다. 새 토큰을 생성할 때 과거 토큰의 표현을 처음부터 다시 만들지 않아도 되는 것입니다. 하지만 새로운 query가 과거의 key 및 value를 이용하는 과정까지 사라지는 것은 아닙니다. Hugging Face의 KV 캐시 설명

따라서 “입력 토큰 대부분이 캐시에서 왔다”와 “문맥 처리 비용이 거의 없다”는 다른 말입니다. 캐시는 계산을 재사용하는 장치이지, 문맥을 무료로 만드는 장치가 아닙니다. 긴 문맥은 저장 공간과 읽기 작업을 요구합니다. 실제 비용은 모델 구조, 캐시 구현, 배치 크기와 하드웨어에 따라 달라지므로, 토큰 수만으로 전력량을 바로 환산하면 안 됩니다.

숫자를 어떻게 세느냐가 결론을 바꾼다

다음은 원리를 위한 가상 예시입니다. 10번의 요청이 각각 2,000개의 새 입력 토큰과 18,000개의 캐시 입력 토큰을 사용하고, 요청마다 500개를 출력한다고 가정합시다. 새 입력은 합계 20,000개지만, 캐시 읽기는 180,000개이고 출력은 5,000개입니다. 출력만 세면 5,000개, 새 입력까지 세면 25,000개, API가 보고한 모든 종류를 합하면 205,000개가 됩니다.

세 값 중 하나를 고르는 문제가 아니라, 서로 다른 양을 재고 있다는 점이 중요합니다. 각 종류의 처리 비용이 같지 않으므로 205,000개를 모두 동일한 단가나 동일한 에너지 계수에 곱하는 것도 정확하지 않습니다. API 청구액, 실제 실행 시간, 전력 소비량은 별도의 지표로 기록해야 합니다. 캐시 요금 할인율은 사업자의 가격 정책이지 물리적 에너지 절감률 자체가 아닙니다.

가격표와 메모리 예산을 따로 써 보는 법

예시로 한 모델의 문맥에서 토큰 하나가 차지하는 KV 저장량을 128KiB라고 가정해 봅시다. 2만 토큰이면 대략 2.44GiB를 차지합니다. 이는 단순한 가정일 뿐이고, 실제 토큰당 크기는 층 수와 KV 헤드, 데이터형, 저장 구조에 따라 달라집니다. 한 요청의 캐시가 줄면 동시에 여러 요청을 올릴 공간이 늘 수 있지만, 어떤 구현은 공유하는 접두부를 중복 저장하지 않습니다. 고정된 메모리 수치 하나를 특정 서비스의 비용으로 바로 환산할 수 없는 이유입니다.

작업을 여러 번 이어서 요청하는 팀이라면 공통의 고정 프롬프트를 앞에 두고 달라지는 실패 로그를 뒤에 놓는 사례를 떠올릴 수 있습니다. 공통 부분을 재사용하는 정책에서는 새로 계산할 문맥이 줄 수 있습니다. 그러나 도구가 매번 앞쪽에 시각·사람별 식별자·상태를 덧붙이면 문자열상 앞부분이 달라져 재사용되는 길이가 예상보다 짧아질 수 있습니다. 문맥을 요약해 길이를 줄일 때도 이후에 필요한 테스트 근거가 떨어져 나가면 추가 검색과 수정이 늘 수 있습니다. 캐시는 독립적인 버튼이 아니라 프롬프트와 실행 기록을 어떤 순서로 구성하는가의 문제이기도 합니다. 디코딩 단계와 캐시 동작

주목할 논문 Re Reading Is Not Free

11월 16일 제출된 이 프리프린트는 10주 동안의 AI 보조 개발 기록에서 42개 세션과 752개 작업 에피소드, 약 10억 토큰을 분석했습니다. 저자들은 API 보고 토큰의 94.8%가 캐시 문맥 읽기였고, 출력 토큰 하나당 약 260개의 캐시 토큰을 읽었다고 보고합니다. 여기서 비율은 해당 기록의 토큰 구성이지 전체 개발자나 모든 제품의 평균은 아닙니다. 논문 원문

저자들의 캐시 인지 추정기는 약 250 kWh, 비교한 출력 기반 추정기는 약 10 kWh를 산출했습니다. 약 25배 차이는 전력계로 확인한 소비량 차이가 아니라 추정 방식 사이의 차이입니다. 논문도 긴 캐시 문맥에서 두 추정기 모두 검증되지 않았다고 밝힙니다. 각 작업을 새 문맥으로 시작하면 추정량이 약 60% 감소하는 분석 역시 잃어버린 정보를 다시 찾는 비용을 더하지 않은 반사실적 계산입니다. 이를 그대로 실제 절감률로 약속할 수 없습니다. 방법과 한계

이 연구가 주는 실용적 경고는 “캐시를 쓰지 말라”가 아닙니다. 관찰된 토큰 기록과 그 기록에서 유도한 물리량을 구분하라는 것입니다. 성능 수치가 좋더라도 측정 경계가 다르면 서로 다른 실험을 비교하게 됩니다.

전력 추정기의 차이는 어디에서 커지는가

기본적으로 추정기는 토큰 종류별 관찰값에 ‘이 종류의 토큰을 처리할 때 해당 작업이 추가로 소비한다고 놓은 양’을 곱하는 모델입니다. 입력·출력·캐시 읽기를 나누면 청구 항목보다 실험 질문에 잘 맞는 단위를 만들 수 있지만, 계수가 맞다고 자동으로 증명되는 것은 아닙니다. 배치 속에 다른 요청이 들어오거나 공유 메모리로 읽는 경우 같은 양의 토큰이 실제로 같은 추가 전력을 쓴다는 가정도 흔들릴 수 있습니다. 토큰 분해 없이 계산한 값과 분해해서 계산한 값의 차이는 어디를 측정할지 우선순위를 제안할 뿐 정확한 사용 전력을 확정하지 않습니다.

이를 실제로 좁히려면 같은 프롬프트와 출력 길이, 같은 요청률로 실험하면서 접두부 캐시의 적중 여부만 의도적으로 바꿔 봅니다. 가속기 전력만 재는 시험과 서버 및 메모리까지 재는 시험은 경계를 분리합니다. 그다음 대기 중 전력을 따로 측정해 기본 소비량을 어떤 기준으로 배분했는지 적습니다. 최종 작업 결과가 달라지면 전력량뿐 아니라 성공 건당 전력처럼 성과를 분모로 둔 지표도 필요합니다. 논문 원문의 추정 조건 및 한계

일반적인 활용과 평가 기준

개발 조직에서 도구를 비교할 때는 같은 과제 묶음, 같은 시간 예산, 같은 성공 판정 기준을 먼저 정하는 것이 좋습니다. 그다음 성공한 작업 수뿐 아니라 실패한 작업에 쓴 비용과 재실행 횟수도 포함합니다. 성공 사례만 남기면 가장 비싼 실패들이 통계에서 사라집니다.

예를 들어 가상의 도구 A가 100건 중 80건을 100달러에 해결하고, B가 100건 중 85건을 150달러에 해결했다면, 해결률은 B가 높지만 총비용을 성공 건수로 나눈 값은 A가 1.25달러, B가 약 1.76달러입니다. 어느 도구가 적합한지는 실패를 사람이 보완하는 비용과 처리 시간까지 고려해야 합니다. 이는 순위를 정하는 실제 실험 결과가 아니라 평가 지표가 답하는 질문을 구별하는 예시입니다.

긴 문맥을 유지하는 설계는 재검색을 줄이는 대신 반복 읽기를 늘릴 수 있고, 작업을 잘게 나누는 설계는 문맥을 줄이는 대신 연결 정보를 잃을 수 있습니다. 어느 쪽이 낫다는 고정된 답보다 전체 작업의 성공률과 총비용을 함께 측정하는 것이 중요합니다.

성공까지 드는 총비용으로 선택하기

앞서 가상으로 A가 80건, B가 85건을 해결했다고 했습니다. 둘의 비용 차이는 50달러이고 사람에게 남긴 실패는 B가 다섯 건 적으므로, 다른 비용이 같다면 사람이 실패 한 건을 처리하는 비용이 10달러를 넘어가는 지점에서 B의 총비용이 더 낮아집니다. 실제로는 다섯 건이 전부 비슷하지 않을 수 있습니다. 잘못 고쳤는지 알아차리기 어려운 오류 한 건은 수동으로 쉽게 완료할 수 있는 미해결 한 건과 같지 않습니다. 그래서 결과를 ‘해결’과 ‘미해결’로만 분류하지 말고 잘못된 변경, 검증 불가, 제한 시간 초과를 구분하는 것이 유용합니다.

현장에서는 먼저 평소 업무를 대표하는 작은 과제 묶음을 고릅니다. 배포 전 검증이나 저장소 수정처럼 결과를 볼 수 있는 작업을 섞되 모델과 실행 환경, 도구 승인, 지연 상한을 함께 묶어 기록합니다. 동일한 과제에서 도구가 산출한 결과를 평가하는 사람에게 어떤 도구가 만들었는지 알려주지 않으면 평판이 평가에 영향을 덜 미칩니다. 성공 한 건 다음에는 자원을 어느 단계에 썼는지, 실패에는 누가 개입했는지를 남깁니다. 이렇게 몇 차례 비교를 반복하면 전체 문맥을 유지할지 작업 경계마다 새로 시작할지, 비용과 실패의 분포를 보며 정할 수 있습니다.

기록 모델을 고르는 데도 목적이 있습니다. 일간 지출 예측에는 실제 청구용 토큰 분류를 사용하고, 작업 지연 조사에는 첫 토큰이 나오기 전의 시간과 생성 중의 시간을 따로 봅니다. 사내 가속기 장비의 총비용을 비교한다면 유휴 전력을 포함할지, 캐시가 차지한 메모리 탓에 다른 작업이 얼마나 대기했는지도 적을 수 있습니다. 서로 다른 지표를 교차해 보는 작업은 숫자를 늘리기 위한 것이 아니라, 한 기준에서 좋아 보인 변경이 다른 기준에서 비용을 전가하지 않았는지 확인하는 데 필요합니다.

오늘의 결론

에이전트 성능은 모델, 실행 환경, 문맥 관리와 측정 방식이 함께 만드는 결과입니다. 같은 모델을 맞춰 비교하는 일과 캐시 비용을 구분해 세는 일은 결국 같은 원칙을 따릅니다. 무엇을 고정하고 무엇을 측정했는지 명확해야 개선을 믿을 수 있습니다.

다음 실행에서 줄일 항목도 답을 보고 정해야 합니다. 인터페이스 로그만 긴 작업과 모델이 같은 검증을 반복하는 작업은 다른 개선이 필요합니다. 전자에서는 필요한 줄만 돌려주는 도구가 해결책일 수 있고, 후자에서는 어떤 검증을 완료했는지 기록하고 같은 상태를 재사용하는 방법이 효과적일 수 있습니다.
