자동화 검증과 재현 가능한 빌드

빌드 성공과 기능 정확성은 왜 다를까. GitHub Actions의 변화와 재현 가능한 빌드의 조건을 살펴봅니다.

이 글의 흐름
최신 개발 소식주목할 논문 Vibenix오늘의 개발 개념 Hermetic build와 재현 가능한 빌드오늘의 결론

빌드가 성공했다는 말은 생각보다 좁은 의미입니다. 파일을 만들었다는 뜻일 수 있지만, 그 파일이 원하는 기능을 수행하는지, 다음 주에도 같은 파일을 만들 수 있는지, 다른 컴퓨터에서도 출처를 확인할 수 있는지까지 보장하지는 않습니다. 오늘은 GitHub Actions의 최근 변경과 자동 패키징 연구를 통해 자동화의 종료 조건을 어떻게 설계할 것인가를 살펴봅니다.

이번 주 개발 공지와 가까워진 변경 일정, 최근 한 달의 연구 중 실제 개발에 영향을 주는 내용을 골랐습니다. 오늘의 초점은 코드에서 산출물을 생성하는 자동화의 재현성과 검증 경계입니다.

최신 개발 소식

GitHub Actions의 실행 정책 변경이 가까워졌다

GitHub는 11월 2일 공지에서 공개 저장소의 pull_request_target 이벤트를 12월 2일부터 기본 차단한다고 밝혔습니다. 적용 정책에서 명시적으로 허용하는 경우는 예외입니다. 다음 일시 차단 시험은 11월 16일 16시부터 18시 UTC, 한국시간 11월 17일 새벽 1시부터 3시입니다. 비공개·내부 저장소와 GitHub Enterprise Server는 이 공지의 적용 대상이 아닙니다. 공식 공지

pull_request_target은 기본 저장소의 맥락에서 실행되어 비밀정보에 접근할 수 있습니다. 여기에 외부 fork의 코드를 가져와 실행하면, 검증받지 않은 코드가 권한 있는 실행 환경에 들어오는 문제가 생깁니다. 따라서 실패가 보인다고 이벤트 전체를 다시 허용하기보다, 해당 workflow가 단순 라벨 작업인지 외부 코드를 실행하는 테스트인지 먼저 나눠야 합니다. 이 위험과 차단 이유는 GitHub가 직접 명시한 내용입니다. 동일 공지의 변경 이유

ARM32 실행 지원 종료와 의존성 잠금

11월 12일 공지에 따르면 GitHub Actions hosted runner의 Windows·Linux ARM32 작업 실행 지원은 12월 8일까지 종료됩니다. ARM64 전체가 종료되는 것이 아닙니다. ARM32 산출물을 만드는 프로젝트라면 실행 아키텍처와 크로스 컴파일 대상을 구분해야 합니다. 공식 공지

재현성 측면에서는 10월 28일 정식 제공된 workflow dependency lockfile도 주목할 만합니다. .github/workflows/actions.lock으로 Action과 전이 의존성을 특정 커밋에 묶으면서 workflow 안의 읽기 쉬운 태그 표기는 유지할 수 있습니다. Free와 Team을 포함한 지원 플랜에서 사용 가능하고, 개별 workflow부터 도입할 수 있습니다. Dependabot의 해당 Action 업데이트는 잠금 항목도 함께 갱신합니다. 잠금은 예상하지 못한 변경을 막는 장치이지, 잠근 코드가 안전하다는 인증은 아닙니다. 공식 발표

정책을 바꾸기 전에 작업의 입력과 권한을 그려 본다

공개 저장소의 변경 요청에 라벨을 붙이는 작업에는 보통 변경 자체를 실행할 이유가 없습니다. 반대로 테스트는 변경된 코드를 실제로 돌리되, 비밀키를 읽거나 저장소에 쓰는 기능을 줄일 수 있습니다. 두 작업을 한 실행 정의에 묶으면 나중에 변경 요청에 작은 안내 댓글을 달기 위해 테스트 전체에 쓰기 권한을 주는 일이 생깁니다. 어떤 입력이 신뢰 경계를 넘는지, 결과를 어디에 써야 하는지 정리하면 실행 정책이 바뀌어도 어느 부분을 분리할지 보입니다. GitHub Actions 보호 가이드

Action 버전을 잠그는 경우에도 절차의 변화를 기록하는 편이 좋습니다. 새 잠금 파일에 누가 검토한 커밋이 들어 있는지, 업데이트 요청이 왔을 때 어떤 테스트를 다시 돌릴지 정합니다. 빌드한 바이너리의 대상이 ARM32라면 컴파일이 되는 것과 실제 기기에서 동작하는 것도 확인을 분리해야 합니다. ARM64 호스트에서 크로스 컴파일하고 의존성까지 잠가도, 대상 기기에 없는 기능을 썼거나 실행에 필요한 라이브러리가 설치되지 않았다면 그 결과만으로 배포를 승인할 수 없습니다.

주목할 논문 Vibenix

패키지 생성보다 실행 후 검증이 중요하다

Martim Monis 등의 Vibenix: Agentic Software Packaging and Maintenance with Nix는 2026년 10월 17일 제출, 10월 26일 수정된 프리프린트입니다. LLM이 Nix 패키지 정의를 만들고, 실제 빌드 오류를 받아 수정하며, 빌드 이후에도 기능을 점검하는 방식입니다. 논문 및 버전 기록

저자 보고에 따르면 Claude Haiku 4.5를 사용한 466개 패키징 과제에서 빌드 성공률은 95.3%였습니다. 하지만 빌드 가능한 패키지 100개를 수동 확인했을 때 초기 기능 정확성은 47%였고, 후속 refinement로 35%포인트 개선됐습니다. 유지보수 과제의 성공률은 87.6%로 보고했습니다. 빌드 성공률과 기능 정확성은 서로 다른 평가이고, 표본도 다릅니다. 이를 단순히 “95.3%의 소프트웨어가 완전히 올바르다”로 읽으면 안 됩니다. 원문 초록과 평가

연구가 보여주는 것은 반복 실행 피드백과 별도 기능 검증의 가치입니다. Nix 과제의 결과를 곧바로 PyTorch 모델 변환이나 전체 웹서비스의 정확도로 일반화할 수는 없습니다. 저자의 벤치마크 보고이며, 이 수치 자체가 독립 재현이나 임의 프로젝트의 안전성을 증명하지도 않습니다. 논문

패키징 실험에서 성공의 분모를 끝까지 유지한다

빌드가 끝났다는 메시지는 설치 뒤 실행되는 명령이 모두 들어 있다는 사실을 보장하지 않습니다. 예를 들어 이미지 변환기 패키지가 생성돼도, 패키지에 도움말만 들어 있고 실제 인코더는 빠졌을 수 있습니다. 실행 명령이 존재하는지부터 체크한 뒤 고정 입력을 변환해 출력 크기를 확인하고, 별도 파일에서 포맷과 픽셀 단위를 다시 확인하는 식으로 검사를 쌓을 수 있습니다. 테스트 입력은 패키지 생성기가 참고한 예제와 분리해야 이미 본 성공 경로만 누락 없이 맞히는 것을 피할 수 있습니다.

가상의 100개 과제 중 90개가 빌드되고, 그중 70개를 실행할 수 있고, 최종 60개가 기능 비교를 통과했다고 합시다. 최종 기준은 처음 과제 기준 60%이고, 빌드 성공분 기준 66.7%입니다. 두 비율의 의미는 다릅니다. 자동 생성기 비교표에서는 처음부터 같은 과제를 모두 유지하고, 실행 가능한 샘플의 별도 수동 분석은 표본 선정 방식까지 밝혀야 합니다. Vibenix 실험에서 빌드와 기능 평가의 구분처럼, 성공 단계를 하나의 숫자로 합치지 않는 편이 개선의 위치를 드러냅니다.

오늘의 개발 개념 Hermetic build와 재현 가능한 빌드

외부 환경을 입력으로 인정할 것인가

Hermetic build는 호스트에 우연히 설치된 도구나 라이브러리에 기대지 않고, 명시적으로 관리되는 입력으로 빌드를 수행하는 접근입니다. Bazel 문서는 격리와 입력의 동일성 식별을 핵심으로 설명합니다. 버전이 다른 시스템 컴파일러, 생성 시각, 빌드 중 소스 트리 변경 같은 요소가 결과를 흔들 수 있습니다. Bazel 공식 문서

재현 가능한 빌드는 같은 소스, 빌드 환경, 명령으로 지정한 산출물을 비트 단위로 똑같이 다시 만드는 성질입니다. 무엇을 산출물로 비교할지도 명시해야 합니다. 로그 전체와 배포용 모델 JSON을 무조건 같은 대상으로 다루면 불필요한 차이가 섞입니다. Reproducible Builds 정의

두 용어는 연결되지만 검증 질문은 다릅니다. 격리는 숨은 입력을 줄이는 수단이고, 재생성한 결과의 비교는 원하는 동일성이 실제로 성립했는지 확인하는 검사입니다. 컨테이너나 잠금 파일 하나를 추가했다는 사실만으로 결과의 동일성을 선언하지 않는 편이 안전합니다.

해시가 다르지만 모델은 같은 예제

아래는 설명을 위한 가상 JSON입니다. 특정 제품의 파일 형식이나 구현을 그대로 옮긴 것은 아닙니다.

{
  "model": "TinyMLP",
  "generated_at": "2026-11-15T10:00:00+09:00",
  "nodes": [{"id": "n1", "type": "Linear"}]
}

같은 모델을 한 시간 뒤 내보내면 generated_at만 달라져도 파일 해시는 달라집니다. 따라서 무엇을 보증하려는지부터 정해야 합니다.

  • 원본 파일의 무결성: 생성된 파일 그대로의 해시를 저장합니다. 복사나 배포 중 바뀌었는지 확인합니다.

  • 모델 내용의 동일성: 생성 시각처럼 의미와 무관하다고 합의한 필드를 제외하고, 정규화 규칙을 적용한 별도 해시를 비교합니다.

  • 실행 의미의 동등성: 같은 입력에 대한 출력 등을 별도 테스트합니다. 파일 해시만으로는 알 수 없습니다.

정규화에서도 조심할 부분이 있습니다. JSON 객체의 키 순서는 정렬할 수 있지만, 신경망의 층 순서나 edge 배열의 순서를 무조건 정렬해 버리면 원래 의미를 바꿀 수 있습니다. 어떤 배열이 집합이고 어떤 배열이 순서열인지 schema가 정해야 합니다. 이 예제에서 중요한 것은 해시 함수의 종류보다 동일하다고 취급할 대상의 정의입니다.

빌드 캐시에도 같은 문제가 숨어 있다

입력과 도구가 정확히 식별되면 같은 작업의 출력을 재사용하기 쉬워집니다. Bazel은 이를 캐싱과 병렬 실행의 이점으로 연결합니다. 반대로 숨은 환경변수가 결과를 바꾸는데 캐시 키에 들어가지 않으면, 오래된 결과를 성공적으로 가져와 버릴 수 있습니다. 빠르게 끝난 빌드가 잘못된 최신성을 숨기는 셈입니다. Bazel의 이점과 문제 진단

숨은 입력은 일부러 바꿔 봐야 드러난다

같은 배포 파일을 두 번 만들었는데 해시가 일치했다고 합시다. 같은 머신의 같은 디렉터리에서 몇 초 간격으로 두 번 실행한 것이라면, 문제를 일으킬 변수를 거의 바꾸지 않은 실험일 수 있습니다. 먼저 일회성 환경에서 작업 디렉터리 이름, 시간대와 언어 환경, 병렬 작업 수를 하나씩 바꿉니다. 둘째로 의존성 다운로드가 끝난 뒤 일반적인 인터넷 접근을 끊어, 빌드가 원격 파일이나 현재 날짜에 조용히 기대는지 봅니다. 셋째로 출력 파일의 구성 목록·개별 파일 해시·압축 메타데이터를 따로 비교합니다. Reproducible Builds의 변동 원인 가이드가 이런 대조의 출발점입니다.

예를 들어 압축 해시가 달라졌는데 풀어낸 바이너리들의 해시는 모두 같다면, 도구 버전부터 바꾸기보다 압축 파일에 담긴 순서와 시간 표기부터 확인하는 것이 빠릅니다. 반대로 압축 안의 실행 파일만 다르면 컴파일러나 절대 경로, 생성 순서를 고립시킵니다. 해시가 같다고 안전한 코드인 것도 아닙니다. 원본이 이미 취약하면 그 코드를 충실하게 다시 만든 것입니다. 재현성의 역할은 배포물과 입력의 관계를 검사하기 쉽게 하는 데 있고, 안전성을 별도 심사 없이 인증하지 않습니다.

캐시를 끈 결과와 켠 결과를 교차 비교한다

개발 중 쓰는 빠른 캐시 경로와 배포용 결과를 비교하려면 첫 실행은 캐시를 비우고, 두 번째는 동일 조건의 캐시를 켜고, 세 번째는 의존성 하나만 바꾼 상태에서 캐시를 켭니다. 첫 두 실행의 산출물이 같고 세 번째에서 해당 출력이 적절히 무효화되면, 캐시 적중과 갱신이 의도대로 움직인다는 근거가 됩니다. 예컨대 40초 빌드가 캐시에서 3초로 줄었어도, 잠금 정의 또는 중요한 환경 입력 변경에 반응하지 않는다면 빨라진 것은 오래된 산출물을 가져오는 경로뿐입니다. 반대로 의미 없는 임시 폴더 경로까지 키에 들어가면, 정확한 결과를 내더라도 공동 캐시의 이득을 잃게 됩니다.

오늘의 결론

자동화가 많아질수록 중요한 것은 실행 횟수가 아니라 실패를 구분하는 능력입니다. 빌드 성공, 기능 정확성, 재현성은 서로 다른 성질입니다. 어떤 검사를 통과했다는 말이 어디까지를 보장하는지 구분해야 자동화 결과를 올바르게 해석할 수 있습니다.

최소한의 자동 검증이라면 새 환경에서 빌드하는 작업, 깨끗한 환경에 결과를 설치해 대표 입력을 실행하는 작업, 서로 다른 실행에서 산출물을 비교하는 작업을 분리합니다. 실패 로그도 구분해 남기면 변경이 패키징에만 영향을 주었는지, 동작 결과까지 바꿨는지 확인하기 쉽습니다. 세 작업을 통과한 빌드라도 사용자 데이터를 다루는 기능에는 별도의 기준이 필요합니다. 검사를 얼마나 많이 붙였느냐보다 배포 승인에 어떤 증거를 요구하느냐가 중요합니다.
