API 교체와 의미 패치 자동화

최신 개발 소식

Copilot 모델 교체가 실제 적용 단계로 이동

GitHub는 11월 16일 Claude Opus 4.8, Claude Opus 5, GPT-5.6 Terra의 지원을 대부분의 Copilot 환경에서 종료했다고 발표했습니다. 권장 대체 모델은 각각 Claude Opus 5.5와 GPT-6.1 Sol 또는 GPT-6 Luna입니다. 단, 개인 연간 구독자의 Opus 4.8 이용과 기존 승인 접근을 통한 Opus 5의 런타임 거절 대체 경로에는 예외가 있습니다. 따라서 ‘모든 곳에서 즉시 사라짐’으로 읽으면 부정확합니다. GitHub 공식 공지, 11월 16일

이 소식이 보여주는 운영상의 문제는 모델 이름 교체와 동작 호환성이 다르다는 점입니다. 출력이 같은 JSON 형식을 따르더라도 판단, 지연, 도구 호출 선택은 달라질 수 있습니다. 모델 교체를 라이브러리 업그레이드처럼 다루려면 기존 입력과 기대 행동을 모은 회귀 테스트가 필요합니다. 성공 사례만 아니라 빈 입력, 불완전한 요청, 권한이 없는 작업도 포함해야 교체가 업무 흐름을 깨뜨리는지 알 수 있습니다.

호환성을 제품명 대신 관찰 가능한 결과로 정의한다

가령 문서 분류에 붙인 모델을 바꿔야 한다고 합시다. 오래된 출력의 어투까지 고정하면 실제로 문제가 없는 변화도 모두 회귀로 보입니다. 반대로 JSON 파싱 성공만 보게 하면, ‘기타’로 몰려서 담당자가 놓친 문의를 탐지할 수 없습니다. 계약을 세 층으로 나눠 적어 두면 이 두 가지 문제를 피할 수 있습니다. 형식 계약은 필수 필드와 허용된 값입니다. 업무 계약은 예를 들어 환불 요청이 배송팀으로 가지 않도록 하는 분류 조건입니다. 실행 계약은 허용된 도구와 사용자 승인의 경계를 뜻합니다. 문장의 모든 토큰까지 같을 필요는 없지만, 이 세 종류의 약속은 새 모델에도 적용됩니다.

순차적으로 비교하는 예에서 200건을 양쪽 모델로 재생하고, 업무 계약 위반과 파싱 실패를 따로 셀 수 있습니다. 두 조건에서 각각 190건을 통과했어도 양쪽이 놓친 열 건이 다르면 교체가 안전하다고 단정할 수 없습니다. 기존에서만 성공한 사례와 새 버전에서만 성공한 사례를 짝으로 봐야 어떤 팀의 작업이 손해를 보는지 드러납니다. 제품 공지의 권장 후속 모델은 교체 후보를 알려 주지만, 업무별 회귀 기준을 제공하는 것은 아닙니다.

주목할 논문

작은 모델이 파일 대신 변환 규칙을 작성한다면

11월 12일 공개된 Mohanned Ahmed의 프리프린트는 과거에 사람이 수정한 드라이버 예시를 바탕으로 작은 로컬 모델이 Coccinelle 의미 패치를 만들도록 합니다. 변경 유형을 나누고, 작은 규칙을 생성하고, 결정적 절차로 문법을 보완한 뒤 컴파일 결과로 수정하거나 거부합니다.

초록과 결과 요약 기준으로 7개 마이그레이션의 122개 평가 변환에서 Qwen2.5-Coder 7B는 직접 프롬프트의 평균 1.0개 성공에서 가이드 구조의 35.3개로 개선됐습니다. Spinfer는 41개, 비교한 프런티어 에이전트는 66개였습니다. 변경한 파일 중 성공한 비율은 로컬 모델 0.74, Spinfer 0.55, 프런티어 에이전트 0.70이었습니다. 0.74는 전체 문제의 74%를 해결했다는 뜻이 아닙니다. 성공은 사람의 수정과 일치하면서 컴파일되는 경우로 정의했습니다. 본문 기여 요약에는 표본 수가 123개로 적힌 부분도 있어, 수치를 재사용할 때 원문·공개 결과의 분모 확인이 필요합니다. 논문 원문

이는 작은 모델이 큰 모델을 전반적으로 대체했다는 결과가 아닙니다. 범용 모델 두 개는 가이드를 넣어도 성과가 낮았고, 여러 선언과 사용부를 함께 바꾸는 유형이 어려웠습니다. 독립 재현 결과가 아니라 저자의 실험 보고이며, 학습 시점 이후 API를 평가한 설계가 일반적인 모든 코드 변경의 성공을 보장하지도 않습니다.

사람의 수정에서 반복 가능한 규칙을 얻는 과정

예를 들어 오래된 드라이버 호출의 마지막 인자가 모든 사람의 수정에서 제거됐다고 해도, 그것만으로 규칙을 만들기에는 정보가 모자랍니다. 어떤 파일은 인자 제거와 동시에 실패 경로에서 정리 함수를 호출하고, 다른 파일은 반환형이 달라져 조건식을 바꿔야 할 수 있습니다. 이때 서로 다른 변환을 뒤섞은 긴 프롬프트와, 먼저 ‘호출만 바뀜’, ‘실패 처리가 바뀜’처럼 범주를 정해 별도 규칙을 제안하는 구조는 검증 비용이 다릅니다. 후자에서는 특정 범주가 맞지 않았을 때 그 규칙만 좁히거나 철회할 수 있습니다.

연구의 접근이 파일 전체를 생성하는 방법과 다른 핵심은 한 번 맞은 변환을 다른 파일에도 적용할 수 있는 작은 산출물을 만든다는 점입니다. 모델이 만든 규칙이 어떤 코드와 일치하는지 먼저 확인하고, 실제로 바뀌는 곳을 검사한 다음, 컴파일로 형식 오류를 걸러냅니다. 여기서 컴파일은 필요한 관문이지만 최종 판정의 전부가 아닙니다. 예컨대 자원 해제 누락은 타입만 맞으면 컴파일될 수 있고, 사람의 패치와 비슷하더라도 부수 효과가 달라질 수 있습니다. 아래처럼 범위마다 증거를 달리 확보해야, 같은 방법을 다른 저장소로 이식할 근거가 생깁니다.

정밀도 0.74를 어떻게 읽을지도 중요합니다. 설명용으로 100곳 가운데 20곳만 바꾸고 15곳을 올바르게 바꿨다면, 수정한 곳에서의 성공 비율은 75%이지만 전체 기준으로 완료한 것은 15%입니다. 반대로 90곳을 바꾸고 그중 60곳이 맞았다면 67%지만 완료한 곳은 60곳입니다. 실패 수정 한 건을 검토하는 비용과, 미처 바꾸지 못한 한 건의 비용이 같지 않으므로 둘 다 적어야 합니다.

함수 이름을 바꾸기 전후의 행동을 관찰한다

가상의 파일 읽기 API가 실패 시 숫자 대신 결과와 상태를 담은 객체를 돌려준다고 합시다. 과거 호출부에서 ‘읽은 길이가 0이면 끝’이라고 판단하던 코드가 새 버전에서는 0바이트와 권한 부족을 구별해야 할 수 있습니다. 자동 수정의 목표가 빌드 통과뿐이라면 객체에서 길이만 꺼낸 뒤 이전 조건을 그대로 남기는 변화도 합격할 수 있습니다. 그러나 실패를 잘못 처리하면 일부 작업은 성공처럼 기록되면서 실제 데이터가 사라집니다. 새 API 문서를 읽은 사람이 정상적인 빈 파일, 권한 부족, 읽기 도중 중단을 각각 어떻게 다루는지 테스트로 표현해야 합니다.

검증 비용도 변환 수에 영향을 줍니다. 한 규칙의 변경이 300곳에 적용됐는데 몇 곳에서 로딩 때만 예외가 난다면 300곳을 동시에 수정해 원인을 찾는 것보다 작은 모듈 단위로 똑같은 시험을 반복하기 쉽습니다. 이때 배치 적용 전에는 원래 상태에서 같은 테스트를 먼저 실행합니다. 기존에도 실패하던 환경과 변환 이후 처음 실패한 환경을 구분해야 잘못된 원인을 고치지 않기 때문입니다. 변환을 국소적으로 시작하는 이유는 모델의 판단 가능성을 낮게 보기 때문이 아니라, 품질 신호가 섞일 때 책임질 수 있는 변경 크기를 유지하려는 것입니다.

컴파일러 기록에는 검토가 끝난 규칙의 버전과 적용된 위치를 남길 수 있습니다. 빌드 옵션이 달라 어떤 코드가 실제로 포함됐는지 별도로 확인해야 할 수도 있습니다. 한 구성에서 똑같다고 증명한 것을 전혀 다른 장치 구성에서도 합격한 것으로 보여 주지 않으면, 수동 검토의 다음 순서가 명확해집니다.

오늘의 개발 개념 의미 패치

문자열이 아니라 코드의 조건을 바꾼다

단순 치환은 old_api라는 글자를 발견하면 바꿉니다. 의미 패치는 ‘이 호출의 결과가 특정 변수에 저장되고, 다음 경로에서 이런 방식으로 사용될 때’ 같은 코드 구조와 조건을 표현합니다. Coccinelle의 예시에는 할당 후 전체 영역을 0으로 초기화하는 패턴을 더 적합한 할당 함수로 바꾸거나, 오류 경로에서 빠진 자원 해제를 찾는 규칙이 있습니다. 다만 중간에 값을 다시 썼는지, 다른 함수가 자원을 소유하게 되었는지에 따라 자동 변환의 타당성이 달라집니다. Coccinelle 공식 예제

다음은 특정 도구의 실행 문법이 아니라 설계 예시입니다.

  1. 파일 여러 개에서 같은 변경의 전후 예시를 수집합니다.

  2. 공통 변환과 예외 조건을 분리합니다.

  3. 규칙이 바꿀 위치를 먼저 목록으로 보여줍니다.

  4. 일부 파일에 적용해 빌드와 행동 테스트를 수행합니다.

  5. 예상 밖의 파일이 바뀌면 범위를 줄이고, 확인된 규칙만 확대합니다.

예를 들어 새 API가 실패 시 예외 대신 오류 객체를 돌려준다면 이름만 바꾸는 패치는 컴파일에 성공해도 오류 경로를 망가뜨릴 수 있습니다. 반대로 모든 경우를 한 번에 처리하려는 규칙은 적용 범위를 지나치게 넓힐 수 있습니다. 적용할 수 없는 사례를 남겨두는 것도 정확한 자동화의 일부입니다.

패턴에 맞는 곳보다 맞지 않아야 할 곳을 먼저 고른다

규칙을 검토하는 간단한 방법은 긍정 예제와 부정 예제를 나란히 놓는 것입니다. 가상의 메모리 할당 코드를 예로 들어, 할당 뒤 버퍼 전체가 0으로 초기화되는 패턴에는 대체 규칙을 기대할 수 있습니다. 버퍼 절반만 초기화하거나, 중간에 버퍼 주소가 다른 곳으로 전달되거나, 할당 실패 시 정리 경로가 달라지는 예제에는 동일 규칙이 작동하면 안 됩니다. 남겨야 할 코드를 문서에 명시해 두면 잘못된 매칭을 컴파일보다 빠르게 찾아낼 수 있습니다. Coccinelle 공개 규칙 예시

구조와 텍스트를 구분하는 것도 필요합니다. 이름이 같아도 현재 영역에서 다른 함수에 바인딩될 수 있고, 이름이 달라도 매크로나 래퍼 뒤에서 같은 API를 호출할 수 있습니다. 규칙을 여러 줄에 걸쳐 쓴다고 해서 문맥 전체를 이해하게 되지는 않습니다. 생략된 경로의 제어 흐름, 변수의 쓰임, 소유권 이동을 어디까지 판별하는지를 명시하고, 도구가 확인할 수 없는 조건은 사람 검토로 남기는 편이 안전합니다.

테스트를 만들 때에는 바꾼 파일만 보고 끝내지 않습니다. 새 API 반환값의 정상·실패 조건을 각각 만들어, 기존 호출자가 기대하던 상태와 같은지 재생합니다. 작은 규칙을 여러 번 적용했을 때 두 번째 적용에서 변경이 없는지도 확인할 수 있습니다. 두 번째에 또 결과가 바뀐다면 한 번의 검토로 끝나지 않고, CI에서 반복 수행하는 과정에서 코드가 계속 흔들릴 수 있습니다.

활용 가능성과 읽는 기준

대규모 API 이동, 반복적인 안전성 수정, 프레임워크 버전 전환에 재사용 가능한 규칙이 유용합니다. 사람은 파일마다 같은 판단을 반복하는 대신 규칙과 예외를 검토할 수 있습니다. 그러나 규칙을 읽을 수 있다는 것과 동작이 증명됐다는 것은 별개입니다.

마이그레이션 결과에서는 성공 건수, 바뀐 파일 중 올바른 비율, 미처리 범위, 실행 중 회귀를 함께 보아야 합니다. 낮은 적용률과 높은 정밀도는 보수적인 보조 도구로 가치가 있을 수 있지만, 작업 전체를 자동 완수했다는 근거로는 부족합니다. 오늘의 핵심은 모델 크기보다 모델이 생성할 대상과 검증 가능한 종료 조건을 먼저 설계하는 것입니다.

승격하기 전의 기록

필요한 입력은 기존 파일 2~3개뿐일 수 있지만, 처음부터 같은 모듈만 모으면 우연히 같은 코드 관례를 일반 규칙으로 채택하기 쉽습니다. 첫 모듈의 예제로 변환을 만들었다면 다른 모듈의 이름·흐름이 다른 예제를 별도 시험으로 남겨 두는 것이 유용합니다. 교체 전후 빌드와 기능 시험이 같은 구성에서 통과하는지, 변경 위치 중 어떤 것은 사람이 판정해야 했는지까지 적으면 이후의 수정도 추적하기 쉬워집니다.

작업이 끝났다는 판단에는 세 가지 경계가 필요합니다. 규칙이 다룬 코드, 이유가 있어 손대지 않은 코드, 아직 조사하지 않은 코드를 분리해야 합니다. 도구가 한 파일에서 멈췄다고 그 파일을 이미 처리한 것으로 적으면 나중에 누락이 드러나도 왜 빠졌는지 알 수 없습니다. 반대로 모르는 곳을 그대로 남기고 그 이유를 적으면 다른 사람이 범위를 넓힐 때 기존 결과를 믿고 이어 갈 수 있습니다.

Copilot처럼 모델을 교체하는 일도 같은 방식으로 볼 수 있습니다. 규칙의 긍정 예제는 새 버전에서도 유지되어야 할 행동입니다. 부정 예제는 허용되지 않은 요청에서 실행을 멈추는 행동입니다. 새 API에 맞춘 코드를 모두 만드는 것과 업무 흐름을 안전하게 이어가는 것은 다른 목표입니다. 직접 테스트할 관찰값을 고르는 편이 더 오래 남는 개선입니다.
