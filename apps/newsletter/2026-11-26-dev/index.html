GitHub 이슈 상태와 변경 이력

GitHub의 이슈 상태와 변경 이력을 사례로 분류, 추적, 권한을 분리해서 설계하는 방법을 살펴봅니다.

이 글의 흐름
최신 개발 소식주목할 만한 논문오늘의 개발 개념

코드 검토에 들어간 이슈를 보드에서 찾는 일은 쉬워졌습니다. 그런데 같은 이슈에 수정 PR 두 개가 연결되어 하나만 합쳐졌다면, 어느 시점에 작업이 끝났다고 할 수 있을까요? GitHub의 이슈 상태와 저장소 보드에서 출발해, 현재 상태와 완료를 판정하는 근거를 어떻게 나눠 관리할지 살펴봅니다.

최신 개발 소식

GitHub 이슈 상태와 저장소 보드 공개 프리뷰

GitHub가 11월 23일 이슈 상태와 저장소 단위 보드를 공개 프리뷰로 소개했습니다. 열린 이슈를 Backlog, Todo, In progress, In review 등으로 구분할 수 있습니다. 완료, 미진행, 중복을 나타내는 상태도 제공됩니다. 저장소에 저장한 이슈 보기를 보드 형태로 바꿔 상태별로 모아 볼 수 있고, 카드를 다른 열로 옮기면 상태가 바뀝니다. GitHub 공개 프리뷰 안내

눈여겨볼 부분은 상태가 사람이 움직이는 카드에만 달려 있지 않다는 점입니다. 공지에 따르면 이슈에 초안 PR을 연결하면 In progress, 해당 PR을 검토 준비 상태로 바꾸면 In review로 이동합니다. 열린 PR을 연결해도 In review로 바뀝니다. 사람에게 이슈를 할당하면 Todo, 에이전트에 할당하면 In progress로 설정되는 규칙도 소개됐습니다. GitHub Project의 상태값이 이슈 상태값과 일치하는 경우 양쪽 변경이 동기화되며, API로도 상태를 읽고 쓸 수 있습니다.

가령 긴급 버그가 리뷰 중인데 담당자를 바꿨다고 해서, 코드가 다시 작성 전 상태로 돌아가는 것은 아닙니다. 반대로 카드가 In review로 이동했다고 해서 검토자가 내용을 읽었다거나 모든 보안 검사가 통과했다는 뜻도 아닙니다. 상태를 트리거로 사용한다면 어떤 사람 또는 자동화가 어떤 사건을 근거로 상태를 바꾸는지 먼저 나눠 보는 편이 좋습니다.

알림에서 보이는 것과 시스템에 기록된 것

GitHub는 11월 24일 별도로 알림 시스템을 12월 1일부터 약 일주일에 걸쳐 이전한다고 공지했습니다. 구독 동작을 더 일관되게 만들려는 변경이며, 새 이슈 보드와는 별개입니다. 이슈의 상태, 변경 이력, 사람이 받은 알림은 서로 다른 자료입니다. 같은 이벤트를 알림으로 못 봤다고 해서 상태 변경이 없었다고 결론 내릴 수 없고, 알림을 받았다고 해서 후속 처리까지 끝났다고 볼 수도 없습니다. GitHub 알림 변경 공지

한 보드를 두 곳에서 편집할 때

가령 제품팀은 이슈를 In review에 두고, 배포팀은 같은 카드를 프로젝트 보드의 Ready for release 열로 옮긴다고 하죠. 앞의 이름과 뒤의 이름은 다른 판단을 담고 있습니다. 공지에서 말하는 동기화는 상태값이 대응하는 경우의 동작입니다. 배포팀의 열을 이슈 상태와 억지로 대응시키면 한쪽에서 정확한 변경이 다른 쪽에서는 잘못된 진척으로 보일 수 있습니다. 두 화면을 같은 상태의 복제본으로 쓸지, 리뷰와 배포라는 서로 다른 사실의 표시로 쓸지 먼저 결정하는 것이 좋습니다. 후자라면 배포 여부는 별도 필드에 두고, 이슈 상태를 배포 성공의 출처로 사용하지 않습니다. 이 구분은 보드가 늘어날수록 효력을 발휘합니다.

주목할 만한 논문

사건 하나가 여러 대상을 바꾸는 과정을 그래프로 읽기

Christfort 등은 11월 24일 Process Science에 공개한 논문에서, 여러 객체에 동시에 걸리는 업무를 이벤트 지식 그래프와 객체 중심 DCR 그래프로 표현했습니다. 전통적인 분석에서는 이벤트마다 하나의 사례 번호를 붙여 순서대로 펼치기 쉽습니다. 대출 신청 한 건처럼 한 객체가 분석의 중심일 때는 유용하지만, 주문 하나가 여러 출고로 분할되고 출고 하나가 여러 주문의 물품을 함께 담으면 단일 번호로는 관계가 사라지거나 사건을 여러 번 세게 됩니다. 논문 원문

이벤트 지식 그래프에서는 출고 사건을 한 번 저장하고 주문·상품·택배 같은 관련 객체에 연결합니다. DCR 그래프는 모든 작업에 동일한 단일 순서를 강제하는 대신, 어떤 작업이 다른 작업의 조건이 되거나 후속 의무를 만들 수 있는지 규칙으로 표현합니다. 예를 들어 택배 하나가 여러 주문과 연결되어 있어도, 각 주문에 필요한 수량만 모두 전달됐을 때만 그 주문을 완료 처리한다는 제약을 기술할 수 있습니다. 이 예시는 원리를 설명하기 위한 것이며 논문의 실험 데이터는 아닙니다.

논문의 두 작업은 다릅니다. 발견은 기록을 보고 어떤 제약이 반복적으로 나타나는지 모델을 만드는 일입니다. 적합성 검사는 이미 정해진 모델과 관찰 기록을 대조해 어디가 맞지 않는지 찾는 일입니다. 이때 정렬은 관찰된 이벤트와 모델상의 행동을 짝짓고, 짝짓지 못한 부분에 비용을 부여합니다. 맞지 않는 흔적이 크다면 실제 규칙 위반일 수 있지만, 기록 누락이나 객체 식별자 오류일 수도 있습니다.

적합성을 점수 하나로만 표시하면 두 오류가 비슷해 보일 수 있습니다. 가령 ‘출고가 관찰됐는데 그 전 결제가 보이지 않았다’고 합시다. 결제 이벤트가 기록에 빠져 모델 쪽에서 한 건을 보충해야 하는 경우와, 결제하기 전에 출고하는 예외가 실제로 허용되지만 모델이 반영하지 못한 경우가 있습니다. 정렬은 차이가 생긴 지점을 보여줄 수 있지만, 원인이 무엇인지는 해당 시점의 정책이나 원본 기록을 확인해야 알 수 있습니다. 그래서 발견에 쓴 기록과 적합성 점검에 쓸 기준은 구별해 관리할 만합니다. 기록에서 자주 발생하는 순서가 회사가 의도한 규칙이라는 보장은 없기 때문입니다.

연구진은 정답 구조를 아는 합성 로그로 발견 방법을 시험하고, 대출 신청 BPIC17과 주문 관리 로그에도 적용했습니다. 적합성 검사에서는 평균 길이 31인 BPIC17 추적에 이벤트 삽입·삭제·순서 교환을 섞었습니다. 노이즈 수준 8개에서 각각 100개 비영점 정렬을 5분 제한으로 비교했고, 제한 안에 완료된 587개 비영점 정렬의 집계에서 불일치 비용이 커질수록 실행 시간도 늘었습니다. 복잡한 업무에서 실시간 상시 감시가 가능하다는 결과로 읽기보다는, 어느 범위까지 자동으로 대조할 수 있는지 보여주는 검증입니다.

비용을 바꾸면 같은 로그의 설명도 달라진다

출고 1건 앞에 결제 기록이 없다고 가정합시다. 형식과 단위가 고정된 가상 예에서, 기록 누락을 보충하는 비용을 1점, 관찰한 출고를 모델에서 설명하지 못하는 비용을 3점으로 둔다면 전자를 택하는 정렬이 더 저렴합니다. 반대로 해당 기간 결제 기록의 완전성을 원장으로 확인했다면 보충 비용을 높일 근거가 생깁니다. 정렬 비용은 어느 설명이 더 자연스러운지 비교하는 도구이지, 사건이 실제로 일어났을 확률이 아닙니다. 운영 보고에서는 숫자뿐 아니라 무엇을 보충하거나 건너뛰었는지 남겨야 다른 사람이 정책을 확인할 수 있습니다.

오늘의 개발 개념

현재 상태와 변경 이력을 분리하기

이슈 화면의 In review는 현재 상태를 빠르게 보여주는 요약입니다. 어떤 사람 또는 서비스가 언제 무엇을 했는지 조사하려면, 그 상태를 만든 사건이 별도로 필요합니다. 예를 들어 한 이슈에 PR A와 PR B가 연결되고, A만 병합된 뒤 이미 낡은 B의 검사 성공 알림이 늦게 도착하는 상황을 생각해 봅시다. 화면에 적힌 상태 한 칸만 갱신하면 A의 병합과 B의 검사 결과가 서로를 덮어씁니다. 이벤트를 PR·커밋·검사 실행의 식별자로 보관하면 늦게 도착한 성공이 어느 커밋에 대한 것인지 확인할 수 있습니다.

여기서 실무 설계는 두 갈래로 나뉩니다. 화면의 상태는 최신 정보로 다시 계산할 수 있는 조회용 모델로 두고, 의사결정에 필요한 기록에는 고유 이벤트 ID, 대상 객체, 대상 버전, 발생 시각, 수신 시각, 사건 출처를 남깁니다. 같은 전달이 다시 들어오면 기존 이벤트 ID를 재사용해 같은 일을 두 번 수행하지 않도록 합니다. 수신 순서가 바뀌면 커밋 식별자나 제공자가 보장하는 버전을 비교하고, 순서를 확정할 근거가 없다면 원본 시스템의 현재 상태를 읽어 대조합니다.

권한이나 배포는 보드 상태보다 더 구체적인 조건으로 묶을 수 있습니다. 예를 들어 승인한 커밋과 배포할 커밋이 같은지, 필수 테스트가 그 커밋에서 성공했는지, 연결된 변경이 모두 반영됐는지 확인합니다. 승인 후 새 커밋이 올라왔으면 새 증거를 기다립니다. 테스트용 데이터에는 중복 이벤트, 뒤늦게 도착한 이전 버전 이벤트, 하나의 이슈에 연결된 복수 PR, 수동 상태 변경을 각각 넣으면 설계가 어디서 무너지는지 볼 수 있습니다.

어떤 기록이면 완료를 설명할 수 있나

예를 들어 배포 전에 필요한 증거가 ‘리뷰 승인 1건, 필수 검사 성공, 대상 커밋 일치’라고 정한 팀은 이를 각각 검증할 수 있습니다. PR이 하나인지 둘인지와 무관하게, 승인·검사·배포 사건에는 어떤 변경에 대한 것인지 식별자가 들어갑니다. 여기서 이슈 번호 하나를 모든 기록의 유일 키로 삼으면 같은 이슈에 연결된 PR의 별개 시도까지 합쳐집니다. 이슈와 PR은 관리 대상이고, 실제로 일어난 사건은 별도 ID를 가진다는 점이 중요합니다.

상황 현재 상태만으로 놓치기 쉬운 정보 확인할 근거
같은 PR에서 테스트 재실행 어느 실행이 지금 커밋에 해당하나 실행 ID, 커밋 ID, 최종 결과
이슈를 보드에서 Done으로 이동 완료가 수동 판단인가, 실제 반영인가 변경 주체, 배포 대상, 반영 시각
승인 후 새 코드 푸시 승인 당시 본 코드와 지금 코드가 같은가 승인 당시 커밋, 현재 커밋
두 PR 중 하나만 병합 나머지도 필요한 변경인가 이슈와 각 PR의 연결 및 역할

이 구조를 작은 규모에서 운영한다면, 수신된 이벤트의 식별자에 고유 제약을 걸고 상태를 갱신하는 일을 같은 데이터베이스 트랜잭션으로 묶을 수 있습니다. 업데이트가 실패하면 두 변경을 함께 되돌리므로, 처리하지 못한 이벤트가 처리 완료로 남는 불일치를 줄입니다. 외부 시스템으로 작업을 보낼 때는 별도의 재시도 전략이 필요합니다. DB에 성공으로 기록됐다고 상대 시스템이 작업을 받았다는 뜻은 아니므로, 상대가 돌려주는 작업 ID나 결과를 다시 확인해야 합니다.

모든 이벤트를 영구 저장하거나 그래프 DB를 도입할 필요는 없습니다. 리포지토리 하나의 내부 상태라면 이벤트 ID가 유일한 테이블과 관련 객체를 붙이는 관계 테이블로 출발할 수 있습니다. 원본 로그에 댓글 내용이나 민감한 변수 값을 복제하지 않고도 승인·검사·반영의 관계를 확인할 수 있는지 먼저 따져볼 만합니다. 소규모 팀에서 보드는 일이 어디에 있는지 빠르게 알려주고, 로그는 왜 거기에 있는지를 복원할 때 힘을 발휘합니다.

완료를 되돌릴 수 있는 상태로 취급하기

완료를 ‘필수 PR이 모두 합쳐지고 배포 확인이 끝난 상태’로 정의한다면, 병합 뒤 되돌리기 커밋이 들어왔을 때 이슈 역시 재확인 대상으로 돌아가야 합니다. 이 경우 최초 완료 시각은 지우지 않고, 취소한 사건과 재완료 시각을 별도로 둡니다. 배포 실패로 재개하는 문제와, 처음부터 병합을 완료로 잘못 표시한 문제를 구분할 수 있기 때문입니다. 작은 실험으로 같은 이력을 순서대로 한 번, 중복과 지연을 섞어 다시 한 번 재생해 보세요. 상태표는 두 실행에서 같아야 하고, 누락된 필수 검사에 대해서는 둘 다 완료를 보류해야 합니다. 다만 배포 결과를 오래 확인할 수 없다면 상태를 계속 기다리게 하는 대신 ‘확인 불가’와 담당자를 남겨 사람의 결정을 열어 두는 편이 낫습니다.

관찰용 지표도 정책과 함께 두면 좋습니다. 예를 들어 완료로 표시된 이슈 50개 중 실제 배포를 확인한 것이 45개이고 필수 검사까지 갖춘 것이 42개라면, 90%와 84%는 각각 서로 다른 계약을 확인한 숫자입니다. 이 가상 사례를 보드 카드의 이동 횟수와 섞으면 품질이 나빠도 처리량이 좋아 보일 수 있습니다. 완료 기준을 바꿀 때는 이전 이력도 그 기준으로 다시 계산 가능한지 미리 확인해 두는 편이 낫습니다.
