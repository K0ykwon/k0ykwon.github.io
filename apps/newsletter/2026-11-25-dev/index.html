GitHub 커버리지와 결함 탐지

GitHub의 커버리지 검증과 결함 탐지 연구로 테스트가 실행한 코드와 잡아낸 오류를 구분합니다.

이 글의 흐름
최신 개발 소식주목할 만한 논문오늘의 개발 개념

GitHub Code Quality의 커버리지 업로드가 이제 지원하지 않는 보고서 형식을 만나면 실패합니다. 예전에는 업로드 단계가 성공해도 PR에 커버리지가 표시되지 않을 수 있었습니다. 작은 변경이지만, 테스트가 통과했는지와 그 테스트를 평가할 자료가 제대로 도착했는지는 별개의 질문이라는 점을 잘 보여줍니다.

최신 개발 소식

GitHub 커버리지 업로드의 형식 검사

GitHub는 11월 23일 upload-code-coverage 액션이 보고서를 Cobertura XML로 검사한다고 발표했습니다. 테스트 러너가 LCOV나 JSON만 내보내는 워크플로는 이제 그 파일을 그대로 전달하면 업로드 단계에서 실패합니다. 러너에서 Cobertura 출력을 켜거나 검증된 변환 단계를 붙여야 합니다. GitHub Code Quality가 활성화된 Enterprise Cloud와 Team에 적용되며, Enterprise Server는 대상이 아닙니다. GitHub 변경 공지

이 변화에는 반대 방향의 개선도 있습니다. 지원 형식이 아닌 파일은 입구에서 거르되, Cobertura 보고서의 일부 행만 깨졌다면 전체를 버리지 않습니다. 줄 번호나 실행 횟수를 해석할 수 없는 행은 건너뜁니다. 따라서 업로드 성공을 곧바로 ‘모든 파일을 집계했다’로 읽으면 안 됩니다. PR 커버리지 기능 자체는 공개 프리뷰이며, 기대하는 업로드마다 상태 검사를 필수로 설정할 수 있습니다. PR 커버리지 공식 문서

예를 들어 단위 테스트와 통합 테스트가 서로 다른 CI 작업에서 커버리지를 만듭니다. 둘 다 테스트에는 통과했지만 통합 테스트 작업의 업로더가 비어 있는 보고서를 받았다면, 단위 테스트 결과만으로 통합 경로까지 실행됐는지는 알 수 없습니다. PR에는 실행 성공, 보고서 생성, 보고서 수집, 집계 정책 통과가 각각 어떤 상태인지 보이는 편이 좋습니다. 실패를 한 군데로 모아버리면, 다음 사람이 테스트 코드를 수정해야 하는지 CI의 파일 경로를 고쳐야 하는지 구별하기 어렵습니다.

또 다른 예는 여러 운영체제에서 생성한 파일 경로입니다. 같은 소스가 한 작업에서는 절대 경로, 다른 작업에서는 저장소 기준 상대 경로로 들어오면 형식 검사를 통과해도 동일한 파일로 합쳐졌는지 확인이 필요합니다. 보고서를 합친 뒤에는 커버리지 수치뿐 아니라 기준 커밋, 포함한 작업과 언어, 파일 수, 실행 가능한 줄 수를 함께 남기면 갑작스러운 증감이 코드 변화 때문인지 수집 범위 때문인지 가려낼 수 있습니다.

집계 범위를 버전처럼 고정한다

PR의 커버리지 숫자가 90%로 바뀌었다면 첫 질문은 분자가 아니라 분모다. 가령 이전 실행은 실행 가능한 1,000줄 중 850줄을 방문했고, 새 실행은 모듈 하나의 보고서를 잃어서 700줄 중 630줄만 집계했다고 하자. 표면의 비율은 85%에서 90%로 뛰지만, 방문 기록이 있는 줄은 220줄 줄었다. 새 테스트가 절반 가까이 실패했을 때와는 다른 진단이 필요하다. 가상의 숫자로 만든 사례지만, 실제 PR에서도 두 결과의 출처와 집계 파일을 확인하지 않으면 이런 변화가 개선으로 보일 수 있다.

팀은 업로드 전에 기준 커밋과 실행 대상을 작은 목록으로 만들 수 있다. 예컨대 API 유닛, 데이터 접근 유닛, API 통합 세 작업이 각각 어느 디렉터리를 담당하는지 고정한다. 집계 산출물에는 실제 도착한 작업 이름과 커밋, 파일 수와 실행 가능 줄 수를 같이 남긴다. 그 결과 업로드가 성공한 경우에도 API 통합 보고서만 누락됐는지 쉽게 볼 수 있다. 반대로 일부 패키지를 새로 빌드에서 제외했다면 줄 수 변화가 기대된 동작이며, 왜 제외했는지 기준 자체를 리뷰에서 확인하면 된다. 보고서는 검사 결과이면서 어떤 것을 검사했는지 다시 확인할 수 있는 증거여야 한다.

Cobertura XML 형식이 맞는다는 것은 최소한 도구가 읽을 만한 자료를 받았다는 뜻이다. 줄 번호가 실제 테스트한 소스 커밋을 가리키는지, 경로 정규화가 올바른지, 모노레포에서 이름이 같은 패키지들이 서로 덮였는지는 구조 검사만으로 보장되지 않는다. 작은 시험 PR에서 일부러 통합 작업의 결과 경로를 바꾼 다음, 테스트 성공과 별개로 어떤 증거가 누락됐다고 표시되는지를 미리 확인하는 것이 좋다. 운영에는 검사가 있는지뿐 아니라 필요한 근거를 잃었을 때 사람에게 무엇이 보이는지가 중요하다.

주목할 만한 논문

커버리지와 결함 탐지력이 다른 이유

Laura Inozemtseva와 Reid Holmes의 2014년 ICSE 연구는 5개 자바 프로그램에서 31,000개 테스트 스위트를 구성해 크기와 커버리지, 결함 감지력의 관계를 비교했습니다. 실험에서 감지력은 실제 장애 전체를 관측한 값이 아니라, 코드에 작은 변형을 넣고 테스트가 그 변형을 잡아내는지로 근사했습니다. 테스트 개수를 통제하면 커버리지와 감지력의 상관은 대체로 낮거나 중간 수준이었습니다. 연구가 비교한 커버리지 종류가 달라져도 이 결론이 크게 달라지지 않았습니다. ICSE 논문 원문

테스트 10개짜리 묶음과 1,000개짜리 묶음만 비교하면 긴 쪽에서 더 많은 코드가 실행되고 더 많은 결함이 걸릴 수 있습니다. 그렇다고 커버리지 비율만으로 어느 테스트가 날카로운지는 알 수 없습니다. 테스트 개수를 비슷하게 두고 비교하는 이유가 여기 있습니다. 같은 수의 테스트가 같은 줄을 지나더라도 하나는 함수 호출이 끝났는지만, 다른 하나는 반환값과 저장 상태까지 검사할 수 있습니다. 둘의 커버리지에 나타나지 않는 차이가 바로 검증 조건입니다.

이 연구를 근거로 커버리지를 없앨 필요는 없습니다. 조사에 사용한 프로그램과 변형 연산은 실제 장애 전체를 재현하지 못하고, 멀티서비스 장애나 동시성 결함에 결과를 그대로 옮길 수도 없습니다. 다만 커버리지 증가는 검사할 기회가 늘었다는 신호이며, 그 기회를 제대로 썼는지는 다른 증거가 필요하다는 해석은 유효합니다. 프로덕션에서 발생한 특정 회귀에는 해당 장애를 재현하는 검증이, 수식이나 조건문 경계에는 작은 변형을 잡는 검증이 더 직접적인 자료가 됩니다.

테스트 스위트 크기를 고정하는 이유

한 프로그램에 T라는 테스트 하나가 있고 그것이 10개 줄을 지나며 1개 변이를 잡는다고 하자. 원래 묶음에 서로 다른 입력을 추가하면, 보통 새로운 줄을 지날 기회와 새로운 결함을 우연히 만날 기회가 동시에 늘어난다. 커버리지와 변이 감지 비율이 함께 오른다고 해서 두 값이 직접 서로를 결정한다는 증거는 아니다. 같은 목적의 테스트 10개씩 두 묶음을 비교하면, 테스트 개수 자체가 주는 기회를 어느 정도 제거한 뒤 단언과 입력의 차이를 살펴볼 수 있다. 이 차이를 제거하지 않으면 커버리지로 결함 탐지력을 대체할 수 있느냐는 질문에 답하기 어렵다.

더 좋은 비교 질문은 ‘같은 크기, 같은 자원 예산의 두 테스트 묶음 중 무엇이 중요 결함을 더 자주 잡는가’다. 앞 문장의 ‘같은 크기’도 모두 같은 비용이라는 말은 아니다. 1ms 수치 단언 하나와 외부 프로세스를 여는 2초 통합 테스트 하나의 실행과 유지 비용은 다르다. 논문의 비교는 커버리지와 감지력의 관계에 관한 근거이며, 실제 팀에서 테스트를 추가할 때의 기대 편익은 런타임, 안정성, 리뷰 수고를 더해야 판단할 수 있다. 연구 원문

결함을 모사하는 변이에도 편향이 있다. 비교 연산자 변경은 분명 의미 있는 작은 틀림이지만, 캐시와 데이터베이스가 서로 다른 시점의 값을 대는 문제는 함수 하나를 바꾸는 정도로 재현되지 않을 수 있다. 따라서 변이 점수가 높다고 장애가 많이 방지됐다고 해석하기보다, 해당 패키지에서 미리 고른 의미 규칙에 얼마나 작은 변형을 견디는지 보는 편이 맞다. 나중에 실제 장애가 생기면 그 유형의 회귀 테스트를 별도로 만들어 수치의 빈자리를 보강할 수 있다.

오늘의 개발 개념

줄 커버리지와 변이 테스트를 함께 읽기

줄 커버리지는 측정 대상 줄 가운데 한 번이라도 실행된 줄의 비율이고, 분기 커버리지는 도구가 정의한 분기 결과 중 얼마나 실행됐는지를 봅니다. 100줄 중 95줄이 실행된 테스트가 있다고 합시다. 주문 취소 요청을 한 적이 있어도 ‘이미 배송됐으면 취소를 거절한다’는 경계를 제대로 검사했는지는 95%만으로 알 수 없습니다. 주문이 아직 발송되지 않은 정상 케이스만 실행해도 함수의 여러 줄에 실행 표시가 붙습니다.

변이 테스트는 이 경계를 고의로 바꾼 작은 코드 변형 하나를 만들고 그 상태로 테스트를 다시 돌립니다. 예를 들어 배송 후 취소를 차단하는 비교식을 반대로 바꿨을 때 기존 테스트가 실패하면 그 변이는 잡힌 것입니다. 모두 통과하면 테스트가 그 조건을 지나지 않았거나, 결과를 확인하지 않았을 수 있습니다. 변이 중에는 어떤 입력에도 원본과 똑같이 동작하는 경우도 있으므로, 살아남은 변이를 전부 실제 결함으로 세면 안 됩니다.

두 도구의 장점은 적용 위치가 다릅니다. 모든 PR에는 형식이 맞는 커버리지 증거가 빠짐없이 생기는지 확인하고, 새 경로가 전혀 실행되지 않은 변경은 검토 대상으로 좁힐 수 있습니다. 변이 테스트는 비교적 비용이 크므로 예를 들어 금액 반올림, 상태 전이, 권한 판정처럼 조그만 식의 차이가 제품 동작을 바꾸는 영역부터 쓰기 좋습니다. 좋은 품질 게이트는 비율을 하나 더 올리는 데서 끝나지 않습니다. 수치가 비었을 때는 수집 문제를, 같은 수치인데도 결함이 남을 때는 테스트의 검증 조건을 보여줍니다.

실행은 했지만 못 잡는 세 가지 상황

주문 취소 기능을 예로 들어 원래 요구사항은 ‘발송 전에는 취소가 성공하고, 발송 뒤에는 저장 상태가 그대로여야 한다’라고 하자. 정상 주문만 실행한 테스트는 발송 뒤로 분기하지 않을 수 있다. 발송 뒤 주문으로 들어가면 그 분기를 지나지만, 응답 코드만 확인해 저장 상태를 몰래 바꿔도 발견하지 못할 수 있다. 마지막으로 테스트가 응답과 저장 상태를 둘 다 확인하더라도 정말 취소됐는지 판단하는 기준 자체가 문서와 다를 수 있다. 첫 문제는 실행 커버리지, 두 번째는 단언의 범위, 세 번째는 오라클의 독립성이다. 셋이 겹치긴 해도 하나를 올리면 나머지가 해결된다고 볼 수 없다.

작은 검토 절차를 적용하면 세 가지가 분리된다. 먼저 발송 전후의 입력을 각각 넣어 변경 구간을 지나가는지 확인한다. 이어 상태를 의도적으로 한 경우만 잘못 쓰는 시험 변형을 만들고 기존 테스트가 실패하는지 본다. 끝으로 요구사항을 작성한 사람이 응답과 상태 변화의 기대 조건이 업무 규칙과 맞는지 확인한다. 코드와 함께 AI가 만든 테스트를 검토할 때도 같은 방식이 통한다. 둘이 같은 잘못된 규칙을 가정하면 함께 통과할 수 있으므로, 적어도 핵심 경계 하나는 요구사항에서 독립적으로 읽어 만든 기준으로 검산한다.

어떤 수치를 배포 차단 조건으로 쓸까

가상의 두 테스트 묶음이 동일하게 중요 모듈 100줄 중 85줄을 방문했다고 하자. 검토자가 대표 변이 12개를 골랐더니 A는 8개, B는 10개를 잡았다. 그중 원본과 의미가 같아 잡을 수 없는 변이 2개가 확인되었다면, 남은 10개를 비교할 때 비율은 각각 80%, 100%다. 아직 동등성 판단이 없는 변이를 빼면 데이터가 유리하게 바뀔 수 있으므로, 무엇을 어떤 이유로 제외했는지까지 결과에 남기면 다음에 그대로 비교할 수 있다. 이 숫자가 말해 주는 것은 선택한 변이 묶음의 차이뿐이다. 서비스 전체에서 B가 항상 낫다고 결론을 내려면 다른 경로와 회귀 기록이 필요하다.

단계마다 실패의 메시지를 다르게 붙이면 검토자가 무엇부터 손댈지 알 수 있다. 예를 들어 PR에는 ‘지원되지 않는 보고서’와 ‘통합 보고서 누락’이 각각 신뢰할 증거가 없다는 상태로 표시되고, 중요한 분기 하나가 전혀 실행되지 않은 경우에는 어떤 파일이 남았는지 보여 준다. 변이 시험은 매 PR에 무조건 돌리기보다, 동작을 결정하는 좁은 코드에서 주기적으로 빌드하거나 위험한 변경에만 붙일 수 있다. 이때 효과는 테스트 수가 얼마나 늘었는지가 아니라, 전에 놓쳤던 대표 실패가 실제로 새 판정에 걸리는지로 확인한다.

처음부터 모든 신호를 차단에 쓰지 않아도 된다. 누락된 보고서를 발견하는 신호를 먼저 안정화하고, 정확히 판단할 수 있는 변경 파일에만 좁혀 조건을 강제한다. 변이에서 살아남은 항목은 자동 거부보다 설명과 리뷰 대상을 만드는 데 먼저 쓸 수 있다. 이미지·운영체제 등 형식 문제가 많은 업무와, 금액이나 상태 전이가 중요한 업무는 필요한 근거가 다르다. 수치 하나로 통일하기보다 검사 결과를 받은 뒤 무엇을 할 수 있는지부터 정하는 편이 유용하다.
