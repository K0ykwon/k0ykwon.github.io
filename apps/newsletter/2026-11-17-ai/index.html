최신 AI 소식

Decider v1.3는 답변 생성보다 선택과 추출에 초점

Perplexity는 11월 12일 Decider v1.3와 Decider Flash v1.3를 발표했습니다. 새 Locate 기능은 지시한 조건에 맞는 원문 구간을 찾아 문자 위치와 점수를 반환합니다. 이것은 자유롭게 문장을 다시 쓰는 요약과 다른 출력 계약입니다. 공식 발표

공식 모델 카드의 Locate 결과는 시작 위치, 끝 위치, 텍스트, 점수로 구성되며, 해당 범위를 원문에서 잘랐을 때 반환 텍스트와 같아야 합니다. Locate는 텍스트 입력을 대상으로 하고, 분류와 추출을 섞으면 별도 forward pass가 필요합니다. 따라서 ‘한 요청’이 곧 ‘한 번의 계산’이라는 뜻은 아닙니다. 모델 카드는 확률값에 의존하는 서비스라면 자체 데이터로 보정할 것을 권고합니다. 공식 모델 카드

예를 들어 배송 문의에서 ‘누락된 상품’을 찾는 시스템은 상품명을 새로 생성하는 대신 원문 위치를 표시할 수 있습니다. 검토자는 바로 주변 문맥을 확인할 수 있고, 원문과 다른 이름을 생성했는지도 기계적으로 검사할 수 있습니다. 그러나 원문에 존재하는 문자열을 골랐다고 해서 올바른 상품을 선택했다는 의미는 아닙니다. 추출의 충실성과 의미 판단의 정확도는 별도로 평가해야 합니다.

원문 위치는 사람이 읽는 문자 수와 항상 같지 않다

추출기를 운영하는 팀은 본문에 같은 표현이 몇 번 나오더라도 어떤 발생 위치를 뜻하는지 알아야 합니다. 예를 들어 ‘필터 누락’이라는 상담 문구가 본문과 이미 처리된 지난 문의 인용문에 둘 다 있다면, 정답 문자열은 같지만 올바른 근거 위치는 다릅니다. 결과 텍스트를 다시 검색해 첫 위치를 조용히 채우는 방식은 이런 오류를 숨깁니다. 시작과 끝 인덱스로 자른 원문이 추출 텍스트와 정확히 일치하는지 검사하고, 인용문을 새 문의에서 제외하기 위해 어떤 범위를 썼는지 남겨야 합니다.

문자 수의 정의도 요청 전후가 같아야 합니다. UTF-8 바이트 수와 문자열의 코드 포인트 수는 다를 수 있고, 일부 언어의 런타임은 UTF-16 코드 유닛으로 위치를 셉니다. 이모지나 조합형 문자가 앞에 있을 때 어긋나는 위치 예제를 따로 시험하면 표시 계층과 모델 입력 계층이 같은 계약을 쓰는지 드러납니다. 원본의 공백을 정규화해 모델에 보냈으면, 원본으로 돌아가는 대응표를 저장하거나 화면에 모델 입력과 같은 본문을 보여 줘야 합니다.

주목할 논문

어떤 문맥이 답에 영향을 줬는가

Christopher Liaw 등의 11월 12일 프리프린트는 leave one out 문맥 기여도를 다룹니다. 입력 일부를 제거했을 때 정해진 출력 측정값이 얼마나 달라지는지 묻는 방법입니다. n개 토큰을 하나씩 제외해 직접 계산하면 n회 평가가 필요합니다. 연구는 안정성 가정 아래, 요청 오차에 따른 평가 횟수로 모든 기여도를 근사하는 스케치 알고리즘과 oracle 모델의 대응 하한을 제시합니다. 실험은 작은 언어 모델 검색 과제와 안정성에 관련된 계수 감소 관찰입니다. 대규모 서비스의 보편적인 속도 향상을 입증한 결과로 확대해서는 안 됩니다. 논문 원문

직관적 예를 들어, 문서 A에는 상품 가격이 있고 문서 B에는 배송일이 있다고 합시다. 답이 ‘배송은 금요일’일 때 B를 제거하면 해당 답의 점수가 크게 줄고 A를 제거하면 거의 그대로일 수 있습니다. 이 변화는 모델이 어떤 문맥에 의존했는지의 단서입니다. 하지만 현실의 배송일이 정말 금요일인지는 별도의 사실 확인 문제입니다.

또한 문서 A와 B가 같은 내용을 중복해서 담으면 하나만 제거해도 답이 유지될 수 있습니다. 개별 제거 효과가 작다고 두 문서 모두 쓸모없다는 결론을 내릴 수는 없습니다. 문맥의 상호작용과 선택한 측정값을 함께 해석해야 합니다.

하나를 가리는 실험과 하나를 남기는 실험

문서 제거 전후의 차이와 그 문서 하나만으로 답할 수 있는가는 별개의 검사입니다. 예를 들어 같은 배송일을 적은 공지 A와 공지 B가 있으면 A를 빼도 B로 답할 수 있고 B를 빼도 A로 답할 수 있습니다. 둘 다 개별 제거 점수는 낮아도 빈 문맥에서라면 아무 근거가 없습니다. 반대로 예전 공지가 ‘목요일’, 최신 공지가 ‘금요일’이라고 쓰면 특정 공지를 지울 때 답이 바뀔 수 있지만, 어느 답이 현실에서 맞는지는 출처의 시점과 품질을 확인해야 합니다.

가상의 점수 예에서 ‘금요일’ 답의 점수가 원문을 모두 넣었을 때 0.8, A를 없앴을 때 0.79, B를 없앴을 때 0.77이라고 합시다. 둘의 제거 효과 0.01과 0.03을 더한 0.04가 함께 제거한 효과라는 보장은 없습니다. 둘을 없앴더니 점수가 0.2가 된다면 공통 정보의 영향은 0.6입니다. 이런 문제는 여러 문서를 한데 보여 주고 유일한 근거를 표시할 때 중요합니다. 후보가 많으면 모든 조합을 다 평가할 수 없으므로, 서로 거의 같은 문서군을 먼저 묶고 실제 판단을 바꾸는 주요 후보에만 더 비싼 시험을 수행할 수 있습니다.

평가 측정값에도 선택이 필요합니다. ‘금요일’ 대체 답의 로짓 또는 정답 문자열의 확률을 고정할 것인지, 아니면 새로 생성한 전체 답이 의미상 달라지는지를 검사할지에 따라 결과가 다릅니다. 확률을 비교하면 답 형태는 고정되지만 도구 호출 여부나 실제 사용자에게 반환된 행동은 별도로 확인해야 합니다. 그 차이가 바로 분석 과정에서 기록할 판단의 단위입니다.

오늘의 AI 개념 확률 보정

정확도와 신뢰도는 왜 다른가

가령 두 분류기가 100개 중 80개를 맞혔다고 합시다. 하나는 모든 답에 99% 확신을 주고, 다른 하나는 평균 80% 정도의 확신을 줍니다. 정답률은 같지만 사용자에게 전달하는 위험 정보는 다릅니다. 확률 보정은 ‘90%라고 예측한 사례들을 모았을 때 실제로 약 90%가 맞는가’를 묻습니다. 단일 답이 맞는지를 보증하는 인증서가 아니라, 사례 집합에 대한 통계적 성질입니다.

Guo 등의 ICML 2017 논문은 현대 신경망의 보정 문제를 연구하고 temperature scaling이라는 간단한 후처리가 여러 분류 데이터에서 효과적임을 보였습니다. 로짓을 양의 온도 T로 나누고 softmax를 적용하는 방식입니다. 후보의 순서는 유지하면서 분포의 뾰족함을 바꾸므로, 보정이 좋아져도 최상위 분류 정확도가 올라가는 것은 아닙니다. 논문

온도와 처리 임계값을 정하는 데이터와 최종 성능을 보고할 데이터는 분리해야 합니다. 시험 데이터에 맞춰 임계값을 조정하고 같은 데이터에서 성능을 자랑하면 실제 운영 성능을 과대평가하기 쉽습니다. 언어, 문서 길이, 질문 유형이 달라지면 한 온도로 모든 하위 집단을 잘 보정하기도 어렵습니다.

신뢰도에 맞춰 자동 처리 범위를 정하기

간단한 예를 들어, 모델 점수가 0.9 근처인 상담 50건에서 실제로 35건만 맞았다면 관측 정확도는 70%입니다. 점수를 액면대로 해석했을 때의 90%와 20%포인트 차이가 납니다. 표본이 적으면 이 차이의 불확실성이 크므로 담당 업무 전체에 그대로 적용하면 안 됩니다. 한국어와 영어, 아무런 인용이 없는 문의와 지난 회신을 길게 포함한 문의에서 표본을 분리하면 어느 조건에서 점수가 실제 기대와 어긋나는지도 확인할 수 있습니다.

임계값을 높이는 것이 언제나 좋지는 않습니다. 가상의 데이터에서 낮은 기준으로 100건 중 80건을 자동 처리해 그중 10건이 틀린 경우와, 높은 기준으로 40건을 처리해 2건이 틀린 경우를 비교해 봅시다. 자동 처리된 요청 중 오류율은 12.5%에서 5%로 줄지만 사람이 확인할 요청은 20건에서 60건으로 늘어납니다. 이 교환을 보려면 자동 처리 비율인 커버리지와 자동 처리된 집합의 오류율인 위험을 함께 그려야 합니다. 어떤 일이든 모델에게 넘겨야 한다는 결론보다, 오류가 특히 비싼 상황을 특정하는 데 도움이 됩니다.

모델이 완벽히 보정되더라도 개별 오판을 미리 모두 찾는 것은 아닙니다. 90%가 맞는 사례군에는 열 건 중 한 건 정도의 오류가 남는다는 뜻입니다. 최상위 후보의 순서를 바꾸지 않는 온도 보정은 과도한 점수 확신을 누그러뜨릴 수 있지만, 순위가 이미 틀린 사례에는 다른 입력 근거 또는 모델 개선이 필요합니다. Guo 등의 원문이 보여 주는 단순한 사후 보정과 업무별 기준을 정하는 과정은 이렇게 이어집니다.

같은 보정 점수라도 놓치는 판단이 다르다

가상의 서비스에서 정답 확률을 80%라고 낸 문의 500건의 전체 정답률이 실제로 80%라고 합시다. 그중 일상적인 배송 문의 400건에서는 360건이 맞고 예외 처리 문의 100건에서는 40건만 맞았다면, 구간 전체는 400 ÷ 500 = 80%로 맞지만 부류별로는 90%와 40%입니다. 평균 보정 결과 하나만 보고 둘 다 자동 처리하면, 복잡한 사례군에서 사용자가 받는 위험 표현은 크게 틀립니다. 자동 처리 기준을 부류마다 따로 나눌 만큼 자료가 없다면 오히려 중요한 부류의 보정을 아직 평가하지 못했다고 밝히는 편이 정직합니다.

평가표는 정확도 하나가 아니라 포맷 검사율, 근거 위치 일치율, 위반 시 사람이 받는 비용을 분리해야 합니다. 적은 비율로 통과한 숫자가 운영을 오도할 수 있으므로 절대 건수도 적습니다. 가령 50건에서 세 번 틀린 집단과 5,000건에서 300번 틀린 집단의 비율은 같지만 관측 불확실성과 운영 부하는 다릅니다. 자료가 바뀔 때에는 이전 주기의 평가 결과를 그대로 덮어쓰지 말고, 변화하기 전과 후의 데이터 및 모델 버전을 남겨 원인을 다시 찾을 수 있게 합니다.

적용을 시작할 때 섣불리 최적 임계값을 하나로 정할 필요는 없습니다. 점수가 매우 높고 규칙으로 검증 가능한 하위 업무만 자동화한 뒤, 사람의 최종 판단과 차이가 생기는 조건을 기록합니다. 그 데이터가 쌓이면 확장할 구간과 사람에게 남길 구간을 실제 사례로 나눌 수 있습니다. 아무 점수도 전달하지 않는 것과 근거 없이 정밀한 확률을 표시하는 것 사이에, 정직하게 불확실성을 알려 주는 선택지가 있습니다.

활용과 한계

문서 분류, 문의 라우팅, 정보 추출에서는 다음 세 결과를 따로 보관하면 실패 원인을 찾기 쉽습니다.

  • 판단: 어떤 범주를 선택했는가.

  • 근거 위치: 어떤 원문 구간을 선택했는가.

  • 보정된 위험: 이 종류의 판단이 실제로 얼마나 자주 틀리는가.

원문 위치는 검토를 돕고, 문맥 기여도는 모델 행동의 분석을 돕고, 확률 보정은 자동 처리 범위를 정하는 데 도움을 줍니다. 세 가지를 함께 쓴다고 오류가 사라지는 것은 아닙니다. 낮은 확신에서는 보류할 수 있어야 하고, 높은 확신에서 틀린 사례도 따로 모아야 합니다. 자동화 품질은 얼마나 많은 답을 냈는지가 아니라, 어떤 오류를 발견하고 사람에게 넘길 수 있었는가까지 포함합니다.

같은 오류를 한 번에 드러내는 검수 예제

택배 상담 한 건에서 고객이 ‘소형 필터가 누락됐다’고 했지만 이전 문의의 ‘대형 필터’가 인용돼 있다고 합시다. 첫째, 근거가 실제 원문의 어떤 문자 범위를 가리키는지 확인합니다. 둘째, 상품 이름을 제외한 같은 내용의 문맥으로 다시 실행해 판단이 바뀌는지 확인합니다. 셋째, 이 종류의 인용 포함 문의에서 해당 점수대의 정답률을 따로 확인합니다. 추출 위치가 정확해도 이전 문의를 골랐다면 두 번째와 세 번째 검사가 필요합니다. 반대로 정답을 냈더라도 원문 범위를 찾지 못했다면 검토자가 답을 확인하기 어렵습니다.

실제 운영에서는 어느 사례를 다시 검토했는지의 기록도 중요합니다. 낮은 점수만 사람에게 보내고 높은 점수는 표본 검토조차 하지 않으면, 높은 점수대의 오판이 데이터에 쌓이지 않아 보정이 잘 된 것처럼 보일 수 있습니다. 높은 점수 구간에서도 작은 무작위 표본을 검토 대상으로 남기면 언어·업무 분포가 바뀐 후의 성능을 점검할 수 있습니다. 처음 모델을 골랐을 때의 보정 수치가 앞으로도 맞다는 가정을 줄이는 방법입니다.
