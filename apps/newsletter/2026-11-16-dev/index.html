Rust never 타입과 상태를 표현하는 타입 설계

프로그램에서 “값이 없다”는 말은 두 가지로 나뉩니다. 작업을 마쳤지만 돌려줄 정보가 없는 경우와, 애초에 정상적으로 값을 돌려주는 경로가 없는 경우입니다. 이 차이를 타입으로 표현하면 오류 처리가 간결해지고, 새 상태를 추가했을 때 빠진 분기를 컴파일러가 찾아낼 수 있습니다.

이 글의 흐름

프로그램에서 “값이 없다”는 말은 두 가지로 나뉩니다. 작업을 마쳤지만 돌려줄 정보가 없는 경우와, 애초에 정상적으로 값을 돌려주는 경로가 없는 경우입니다. 이 차이를 타입으로 표현하면 오류 처리가 간결해지고, 새 상태를 추가했을 때 빠진 분기를 컴파일러가 찾아낼 수 있습니다.

오늘은 Rust 1.100.0의 never 타입 정식 지원을 출발점으로, 타입을 가능한 값의 집합으로 보는 관점과 최근의 집합론적 타입 구현 연구를 연결합니다. 오늘 새로 발표된 소식으로 포장하지 않고, 11월 12일 공개된 언어 릴리스와 2026년 가을 논문을 깊이 읽는 회차입니다.

최신 개발 소식 Rust 1.100.0

느낌표 하나가 표현하는 불가능성

Rust 팀은 2026년 11월 12일 Rust 1.100.0을 발표했습니다. 핵심 변화 중 하나는 never 타입 !를 일반적인 타입 위치에서도 이름으로 사용할 수 있게 한 것입니다. 이전에도 반환형 -> !와 제어 흐름에서 관찰할 수 있었지만, 이제 Result<T, !> 같은 표현이 안정판에서 가능합니다. Infallible도 !의 별칭이 됐습니다. 공식 릴리스 발표

이 릴리스는 2024 이전 edition의 never 타입 fallback도 ()에서 !로 바꿉니다. 대부분 코드에서 드러나지 않지만, 일부 제네릭 결과를 무시하는 코드 등에 영향을 줄 수 있어 단순한 새 문법 추가만은 아닙니다. 같은 릴리스에는 Vec·Box에서 사용할 수 있는 핵심 Allocator API와, drop 시 클로저를 실행하는 DropGuard도 포함됐습니다. Allocator 지원이 모든 컬렉션에 한꺼번에 완성된 것은 아닙니다. 변경 사항과 범위

오늘의 관점에서 흥미로운 부분은 기능 수보다 표현력입니다. 예외가 생길 수 있는 API와 원래부터 오류 값을 만들 수 없는 API를 같은 제네릭 구조 안에서 구분하면, 호출자는 불가능한 오류 분기를 억지로 작성하지 않아도 됩니다.

오늘의 개발 개념 비어 있는 타입과 하나의 값을 가진 타입

unit은 빈칸이 아니라 완료를 나타내는 값이다

Rust의 ()는 필드가 없는 튜플이며 값도 () 하나입니다. 따라서 fn notify() -> ()는 정상 종료할 수 있습니다. 반환값으로 전달할 추가 정보가 없을 뿐입니다. 반면 never 타입에는 값이 하나도 없습니다. unit 공식 설명 · never 공식 설명

가게에서 영수증 없이 결제를 완료한 경우와 가게로 돌아오는 길 자체가 없는 경우를 구분한다고 생각하면 쉽습니다. ()는 “끝났다”는 것을 표현할 자리가 있고, !는 정상 반환할 결과가 없습니다. 따라서 Result<(), E>는 성공해도 별도 데이터가 없는 작업이고, Result<T, !>는 정상적인 반환 결과에 오류 변형이 존재할 수 없는 작업을 표현합니다.

이 구분을 값의 개수로 생각하면 더 분명합니다.

  • bool: 참과 거짓이라는 두 값이 있습니다.

  • (): 정보가 없는 완료 값 하나가 있습니다.

  • !: 값을 만들 수 없습니다.

여기서 마지막 두 타입은 둘 다 작아 보이지만, 제어 흐름에서 맡는 역할은 완전히 다릅니다.

반환하지 않는 분기가 다른 타입과 함께 쓰이는 이유

never 타입의 식은 다른 타입으로 강제 변환될 수 있습니다. 실제 ! 값을 숫자로 바꾸는 연산이 실행되는 것이 아닙니다. 그 경로에서는 값을 넘겨 다음 계산을 계속하는 일이 없으므로, 다른 분기의 결과 타입과 충돌할 값도 없는 것입니다. Rust Reference

아래는 원리를 설명하기 위한 독립적인 예제입니다.

fn read_limit(text: &str) -> u32 {
    match text.parse::<u32>() {
        Ok(value) => value,
        Err(_) => panic!("invalid limit"),
    }
}

Ok 분기는 숫자를 반환합니다. Err 분기는 panic으로 정상 반환 경로를 떠납니다. 이때 중요한 질문은 “panic의 반환값을 숫자로 어떻게 바꾸는가”가 아니라 “숫자가 필요한 지점으로 정상적으로 도달하는 경로가 무엇인가”입니다. 실제 서비스에서는 잘못된 사용자 입력을 panic으로 처리하기보다 오류 값을 전달하는 편이 보통 적절합니다. 예제는 제어 흐름만 설명합니다.

never가 있다고 종료 여부를 모두 판정할 수 있는 것은 아닙니다. 타입에 명시된 계약을 읽는 것과 임의의 프로그램이 언제 종료하는지 알아내는 것은 다른 문제입니다. 또한 Result<T, !>는 정상 반환에서 Err를 만들 수 없다는 뜻이지, 프로세스 강제 종료·메모리 고갈·외부 환경 실패까지 사라졌다는 뜻은 아닙니다.

타입을 가능한 상태의 집합으로 읽기

합집합은 선택지를 모으고 분기는 선택지를 줄인다

TypeScript는 조건문과 타입 가드를 따라 가능한 타입을 더 좁게 추적하는 narrowing을 제공합니다. 예를 들어 string | number에서 숫자인지 검사한 분기는 number, 반대쪽은 string으로 좁혀집니다. TypeScript 공식 안내

그림 대신 간단한 주문 상태를 생각해 봅시다. 주문은 준비 중이거나 발송됐거나 취소됐습니다. 각각 서로 다른 데이터가 필요합니다. 이 셋을 하나의 구조체에 선택적 필드로 모두 넣으면 “취소됐는데 배송 번호도 있음” 같은 모호한 조합을 허용하기 쉽습니다. 상태를 구분하는 태그와 각 상태의 데이터를 함께 묶으면 허용할 조합을 더 직접적으로 표현할 수 있습니다.

아래 코드는 설명용 TypeScript 예제입니다.

type Order =
  | { kind: "preparing"; queue: number }
  | { kind: "shipped"; tracking: string }
  | { kind: "cancelled"; reason: string };

function describe(order: Order): string {
  switch (order.kind) {
    case "preparing": return `Queue ${order.queue}`;
    case "shipped": return `Tracking ${order.tracking}`;
    case "cancelled": return `Cancelled: ${order.reason}`;
    default: {
      const impossible: never = order;
      return impossible;
    }
  }
}

모든 변형을 처리했다면 마지막 분기에 남는 후보가 없습니다. TypeScript 문서는 이런 never 활용을 exhaustiveness checking, 즉 누락된 경우가 없는지 검사하는 방식으로 설명합니다. 주문에 returned 상태를 추가하고 switch를 그대로 두면, 마지막 대입에서 미처 처리하지 못한 타입이 드러납니다. 공식 문서의 never와 전체 경우 검사

이 접근은 결제 흐름, 네트워크 연결 상태, 파서의 결과, UI 로딩 상태처럼 경우의 수가 비교적 명확한 곳에서 유용합니다. “언젠가 런타임 테스트에서 걸리겠지” 대신, 새 변형을 추가하는 순간 처리 누락을 드러내는 장치가 됩니다.

단, 외부 JSON에 타입 이름을 붙이는 것만으로 데이터 검증이 수행되지는 않습니다. 네트워크 경계에서는 실제 입력을 검사해야 하며, 무리한 타입 단언으로 컴파일러를 침묵시키면 상태 모델이 주는 이점을 잃을 수 있습니다. 타입 검사는 전제 안에서 작동하는 도구이지 모든 외부 현실을 자동 검사하는 도구가 아닙니다.

주목할 논문 Implementing Set Theoretic Types

수학적으로 우아한 타입을 실제로 계산하는 문제

Mickaël Laurent와 Kim Nguyễn의 Implementing Set-Theoretic Types는 합집합·교집합·부정을 함께 다루는 타입 시스템의 구현을 연구합니다. 원문은 PACMPL 10권 OOPSLA2, Article 334, 2026년 10월 출판으로 표기되며 DOI는 10.1145/3839466입니다. arXiv 기록의 제출 날짜는 9월 25일이므로 11월 식별자만 보고 이번 주 처음 나온 논문이라고 해석하면 안 됩니다. 원문 PDF · 서지 기록

논문의 중심은 SSTT라는 참조 구현입니다. 모듈형 타입 표현을 제시하고, 부분타입 관계와 타입 변수의 대입을 구하는 tallying 알고리즘을 다룹니다. 기존 CDuce 구현과 비교해 설계 선택과 최적화의 영향을 평가합니다. 이것은 Rust 1.100에 이 알고리즘이 들어갔다는 발표가 아니라, 동적 언어의 복잡한 타입 동작을 일관되게 표현하고 계산하려는 별도의 연구입니다. 원문 서론과 구현 설명

연구를 읽을 때는 표현 가능한 타입의 범위, 제약 해법의 성질, 구현에서의 비용을 구분해야 합니다. 특정 표현이나 벤치마크에서의 개선을 모든 IDE·모든 코드베이스의 속도 향상으로 확대할 수 없습니다. 실용적 타입 검사기는 오류 메시지의 품질, 기존 코드와의 호환성, 응답 지연도 함께 해결해야 합니다.

합집합과 교집합이 다른 질문에 답하는 예제

다음은 집합 관점을 설명하기 위한 가상 API입니다. 입력이 숫자이면 숫자를 반환하고, 문자열이면 문자열을 반환하는 normalize 함수를 생각해 봅시다. (number | string) -> (number | string)만 적으면 입력과 출력의 대응 관계가 흐려집니다. 숫자를 넣어도 문자열이 나올 수 있는 것으로 읽히기 때문입니다.

반면 (number -> number) & (string -> string)이라는 개념적 표기는 두 계약을 동시에 만족한다는 점을 드러냅니다. 이것은 실행 가능한 TypeScript 선언을 그대로 제시한 것이 아니라, 함수 타입의 교집합이 어떤 정보를 담는지 보여주는 표기입니다. 타입 연산을 풍부하게 만드는 이유는 기호를 늘리기 위해서가 아니라 이런 관계를 잃지 않기 위해서입니다.

부정도 비슷합니다. 전체 후보에서 문자열을 제외한 값들을 표현할 수 있으면 “문자열이 아닌 분기”의 정보를 남길 수 있습니다. 그러나 실제 언어가 임의의 타입 부정을 문법과 알고리즘으로 지원하는지는 별도 문제입니다. 집합 비유를 이해했다고 각 언어의 타입 시스템을 동일한 수학적 모델로 취급해서는 안 됩니다.

실무에서 얻을 수 있는 기준

타입을 잘 설계한다는 것은 모든 코드를 복잡한 제네릭으로 바꾼다는 뜻이 아닙니다. API가 허용하는 상태를 줄이고, 의미 없는 조합을 만들기 어렵게 하며, 새 상태가 생겼을 때 수정할 곳을 알려주는 것이 목적입니다.

다음 세 질문이면 많은 설계를 빠르게 점검할 수 있습니다.

  1. 이 함수는 정상 종료하지만 정보만 없는가, 정상적으로 돌아오는 값 자체가 없는가?

  2. 오류가 정말 불가능한가, 현재 구현에서 우연히 발생하지 않는가?

  3. 새 상태를 추가했을 때 기존 분기가 조용히 통과하는가, 누락을 드러내는가?

타입을 더 정밀하게 만들수록 표현식과 오류 메시지는 어려워질 수 있습니다. 공개 API에서는 사용자가 읽고 고칠 수 있는 수준의 단순함도 중요합니다. 특히 예외적인 경로 하나를 제거하려고 일반적인 호출부 전체를 복잡하게 만들었다면, 정확성과 사용성 사이의 비용을 다시 봐야 합니다.

오늘의 결론

이번 Rust 릴리스의 느낌표는 작은 문법 변경처럼 보이지만, “없음”과 “불가능함”을 구별하는 좋은 계기입니다. 타입을 값의 집합과 경로의 계약으로 읽으면, 오류 처리와 상태 모델링이 한결 명확해집니다. 집합론적 타입 연구는 그 직관을 더 넓은 언어 기능에 적용하되, 실제로 계산 가능한 구현으로 만드는 과제를 다룹니다.
