개발 소식 GitHub PR 이벤트 스트림

GitHub는 11월 17일 PR용 Event Streams 프리뷰를 발표했습니다. 클라이언트가 PR을 구독하고 연결을 열어두면 리뷰 제출, 새 커밋, 충돌 발생, 종료·병합, 체크 상태 변경 등을 받아볼 수 있습니다. 공개 웹훅 수신기를 운영하지 않아도 된다는 점이 특징입니다. 발표 기준 모든 플랜이 대상이지만 대기 명단 승인이 필요합니다. GitHub 발표

예를 들어 테스트 실패 후 코드를 고쳐 새 커밋을 올렸다면, 감시 프로그램은 1분마다 PR을 확인하는 대신 이벤트를 받은 시점에 체크 결과를 살펴볼 수 있습니다. 반면 노트북이 잠자기 상태였다가 깨어났다면, 끊긴 동안 알림을 모두 받았다고 가정하지 말고 PR의 최신 상태를 다시 조회하는 편이 안전합니다. 실시간 통지와 누락 없는 전달은 별개입니다.

촉발 신호와 최종 판정은 다른 데이터다

PR에 새 변경이 올라온 것을 시각별로 따라가 봅시다. 오후 2시에 커밋 A의 테스트가 시작되고 2시 1분에 커밋 B가 오면 A에 대해 실행된 테스트 결과가 늦게 도착할 수도 있습니다. 검사 실패 이벤트를 받았다는 사실은 맞지만, 현재 PR이 실패 상태라는 결론은 아직 나오지 않습니다. 이벤트에 들어 있는 대상 커밋과 최신 PR의 커밋을 비교하고, 둘이 다르면 과거 시도에 대한 기록으로만 남겨야 합니다. 이 방법은 메시지가 입력되는 순서에 의존하지 않으므로 자동화가 분산되어 있거나 연결이 끊긴 뒤에도 의미를 유지하기 쉽습니다.

작업 상태를 화면에 보여 주는 프로그램이라면 새 이벤트에서 바로 빨간 아이콘을 표시하기보다, 어느 코드에 대해 어떤 검사가 끝났는지 먼저 적어 두는 편이 낫습니다. PR 마지막 커밋에 해당하는 필수 검사들만 모은 현재 화면과, 이전 시도의 이력을 확인하는 화면은 목적이 다릅니다. A의 실패를 숨기지 않되 B까지 실패로 표시하는 오류를 피할 수 있습니다.

가상 운영표에서 스트림과 주기 조회 비교

서로 다른 PR 60개를 각각 매분 한 번 확인하면 한 시간에 3,600번의 조회가 듭니다. 상태가 실제 바뀌는 이벤트를 같은 시간에 45건 받고 처음 연결할 때만 PR별 최신 상태를 확인하는 가상 조건이라면, 이벤트마다 상태를 한 번 다시 읽어도 시작 조회 60회와 추가 조회 45회로 끝납니다. 이 숫자는 요금이나 GitHub 제한이 아니라, 상태가 거의 안 바뀌는 워크로드에서 빈 조회가 생기는 이유를 설명하는 가정입니다. 짧은 연결 끊김이 많거나, 하나의 변경이 여러 이벤트를 연달아 만들면 조회 수 차이는 좁아질 수 있습니다. 반대로 늦은 응답을 피하려고 주기 조회를 15초로 바꾸면 평균 대기 시간은 줄지만 조회량은 네 배가 됩니다.

이벤트를 도입한 뒤에는 이벤트 도착 지연과 실제로 반영할 정보가 최신 상태로 확인된 때까지를 나눠 재는 것이 좋습니다. 이벤트 받는 속도만 빨라도 현재 상태를 읽는 쪽이 재시도로 밀리면 사용자가 보는 화면은 느리기 때문입니다. 간단하게는 연결이 돌아올 때 재조회 한 번, 아주 가벼운 정기 대조 한 번, 최근 변경을 시간 역순으로 확인하는 로그를 두고 어느 경로가 누락을 메웠는지 기록합니다. 프리뷰의 API 형식이나 가용 범위는 달라질 수 있으므로 이 설명을 기능 보장으로 읽지 않습니다.

주목할 논문 회귀 테스트가 버그를 고정하는 경우

10월 8일 공개된 사전논문은 코드에서 직접 생성한 회귀 테스트가 현재 구현의 잘못된 동작까지 정답으로 간주할 수 있음을 보였습니다. 여러 PR의 결함을 한 코드베이스에 합치는 저자 실험에서는 커밋 이력 끝에서도 83–92%가 생성 테스트에 의해 기대 동작으로 고정됐고, 개발자 테스트가 포착한 결함은 14–30%였습니다. 이 범위는 해당 실험의 결과이지 모든 저장소에서 예상할 수 있는 비율은 아닙니다. 논문 원문

가령 배송비가 ‘5만 원 이상이면 무료’인데 구현이 total > 50000을 검사하면, 현재 결과를 베낀 테스트는 5만 원에서 배송비를 요구하게 됩니다. 이후 올바르게 >=로 바꾸면 그 테스트가 오히려 수정을 막습니다. 자동 생성에는 입력 후보와 경계값 발굴을 맡기되, 예상 결과는 명세나 독립된 예시에서 가져와야 합니다.

테스트 입력과 기대 결과를 별도로 얻는다

이 사례에서 자동 생성이 잘하는 일은 49,999원, 50,000원, 50,001원을 후보로 내는 것입니다. 49,000원이나 60,000원만 고르면 더하기 기호 위치나 경계 비교의 오류를 찾아내기 어렵습니다. 그러나 각각에 붙을 배송비 값은 별개의 문제입니다. 코드를 실행해 나온 숫자를 예상값으로 붙이면 실제 동작을 기록할 수는 있지만 규칙 위반을 알아낼 수 없습니다. 정책에 무료 기준이 명시된 곳을 찾아 기대 결과를 독립적으로 쓰고, 문서가 불완전하다면 담당자가 경계값부터 확인해야 합니다. 같은 자동 생성기여도 그 입력으로 코드만 주었는지 요구사항까지 주었는지에 따라 테스트의 역할이 달라집니다.

가상의 비교에서 구현 복사형 테스트 100개가 현재 코드에서 100개 전부 통과하는 반면, 명세형 테스트 100개에서 96개만 통과했다고 합시다. 실패한 네 개가 각각 요구사항을 정확히 반영한다면 두 번째 묶음이 덜 완성된 것이 아니라 현재 구현이 고칠 점을 더 잘 보여 준 것입니다. 이후 코드 수정으로 네 개가 모두 통과했을 때 이전 복사형 묶음이 새 실패를 만들 수 있습니다. 그 실패는 원래 동작을 바꿨다는 증거이지, 반드시 새 코드가 틀렸다는 증거는 아닙니다.

회귀 테스트를 실제 결함으로 검증하기

검증하려면 정상이라고 합의한 버전과, 의도적으로 조건 하나를 틀리게 만든 버전을 준비합니다. 정상 버전에 대한 거짓 경보와 결함 버전에 대한 누락을 각각 셉니다. 이미 조사했던 결함과 비슷한 것만 골라 두면 알고 있던 규칙에 대한 감도를 재는 것이지 새 결함에 대한 일반성을 재지 못합니다. 경계값, 입력 유형, 날짜처럼 실패 부류가 다른 사례를 한 묶음씩 떼어 내 일부는 나중에만 공개하는 편이 낫습니다. 실제 장애 사례가 적으면 변이 시험이 도움이 되지만, 자동으로 만든 변이가 사용자의 피해나 빈도를 대표한다고 단정할 수는 없습니다.

저자들이 PR 결함을 합친 실험의 단위는 이런 비교에서 중요합니다. 한 프로그램 안에서 결함이 서로 영향을 줄 수 있고, 테스트 작성 시점의 정보도 평가에 영향을 줄 수 있습니다. 보고된 범위가 적용되는 대상은 실험 환경이지 현업의 모든 코드 변경이 아닙니다. 읽는 사람이 바로 써 볼 만한 결론은 생성 테스트를 없애자는 것이 아니라, 어떤 시험은 호환성을 지키고 어떤 시험은 제품 요구를 지키는지 구분하자는 것입니다.

논문의 세 비율은 서로 다른 대상을 센다

저자들이 사용한 것은 SciPy, Qiskit, pandas의 PR 145개입니다. 생성한 테스트 자체를 분모로 보면 현재 결함을 기대 동작으로 고정한 테스트가 8–17%, 결함을 드러낸 테스트가 2.4–4.8%였습니다. 이어서 커밋 여러 개가 진행됐을 때, 앞서 이미 잘못된 동작을 고정했던 테스트 중 여전히 테스트 대상에 영향을 주고 통과한 비율이 83–91%였습니다. 마지막으로 여러 결함을 한 버전에 합치는 실험은 어떤 결함이 여전히 고정되는지를 셉니다. 세 숫자는 각각 어떤 테스트가 생성되는지, 잘못된 테스트가 얼마나 유지되는지, 누적 결함이 어느 정도 남는지 답합니다. 하나를 다른 조건에 그대로 붙이면 논문이 추정하지 않은 전체 결함률을 만들어 내게 됩니다.

이 분모는 새 자동화 정책을 고를 때도 중요합니다. 테스트 변경 승인 절차의 지표를 검사 통과율로만 두면, 현재 코드와 똑같은 결과를 기대한 새 테스트가 가장 손쉽게 높은 점수를 받습니다. 반대로 명세가 불명확해 확인을 요청한 테스트가 실패로 취급될 수 있습니다. 테스트 한 건을 만들 때마다 각각 무엇을 바꾸면 실패해야 하는지, 근거가 제품의 행동인지 현재 코드의 행동인지 별도로 적게 하면 두 경우를 구분할 수 있습니다. 라이브러리 버전 변경에서 네임스페이스가 그대로인지 보는 시험과, 할인 한도에서 결과를 비교하는 시험은 같은 실패 원인 설명을 요구하지 않습니다.

오늘의 개념 멱등 처리

같은 이벤트를 여러 번 처리해도 효과가 한 번과 같도록 설계하는 것을 멱등 처리라고 합니다. 예컨대 같은 커밋의 체크 결과에 대해 외부 알림을 한 번만 보내려면 저장소·PR·커밋 SHA·체크 이름·상태로 중복 키를 만들고, 저장 전에 이미 처리했는지 확인합니다. 여러 작업자가 동시에 움직이면 조회 후 쓰기만으로는 부족합니다. 고유 제약 등으로 중복을 막고, 외부 발송과 상태 기록 사이에 장애가 날 수 있다면 발송 대기 목록과 수신처의 멱등 키를 함께 고려합니다.

이 패턴은 CI 알림, 결제 상태, 배치 작업에도 쓰입니다. 다만 순서 역전까지 해결하지는 않습니다. 오래된 이벤트가 늦게 도착할 수 있으므로 최신 상태를 다시 읽거나 버전을 비교해야 합니다. 통지가 왔다는 사실과 그 통지를 바탕으로 무엇을 해도 된다는 판단은 구분하는 게 핵심입니다.

한 번 처리하는 것과 한 번 전달하는 것

시스템 A가 알림 전송 뒤에 완료를 기록한다고 합시다. 외부 서비스는 알림을 받았지만 응답이 오기 전에 A가 꺼지면, 재시도에서 알림을 다시 보낼 수 있습니다. 완료를 먼저 기록하면 반대로 실제 발송을 하지 못하고도 성공으로 남을 수 있습니다. 데이터 변경과 발송할 항목을 같은 트랜잭션에 저장하고, 별도 작업자가 발송을 재시도하는 발송함 패턴은 기록과 사용자에게 보이는 효과 사이의 차이를 줄이는 방법입니다. 그래도 수신자가 중복 방지 키를 받아 주지 않으면, 전송 여부가 불명확한 순간에는 중복 또는 누락 가능성이 남습니다. 메시지가 외부 경계를 넘으면 로컬 거래 하나가 모든 시스템에 같은 보장을 제공하지는 않습니다.

재연결을 실제로 망가뜨려 본다

한 커밋의 검사 종료를 두 번 입력하고, 다음에는 오래된 검사 결과를 나중에 입력합니다. 마지막으로 메시지를 받은 직후와 외부 알림 뒤에 각각 작업자를 종료하고 재시작합니다. 검증할 것은 재시작 자체의 성공이 아니라, 최신 PR 표시가 맞는지, 사용자에게 같은 결과가 두 번 보였는지, 잘못된 알림이 있었다면 원인을 추적할 수 있는지입니다. 이벤트에서 적절한 행동을 결정하는 코드는 관측과 변화를 분리해, 같은 입력을 다시 흘려보내도 원래 판정을 재현할 수 있도록 두는 편이 좋습니다.

결과를 보고할 때는 연결 살아 있는 비율, 실제 상태와 화면의 불일치 시간, 사용자에게 도달한 중복 수를 나눕니다. 만약 장애가 생겨도 현재 상태를 정확히 다시 가져올 수 있고 사용자에게 잘못된 결과를 보내지 않는다면, 이벤트가 잠시 늦은 것은 운영상 받아들일 수 있습니다. 반대로 연결률이 99.9%여도 가장 바쁜 순간에 중복 발송이 발생하면 중요한 문제는 그대로입니다. 이 비교까지 하고 나면 알림을 빠르게 받는 기능과 믿을 만한 자동화를 구분할 수 있습니다.

반복해서 보이는 경고는 시스템보다 사람을 먼저 무디게 한다

예전에 종료된 PR의 검사까지 매번 알림으로 표시되어 하루에 경고가 30건이지만 새 커밋의 실제 실패는 세 건뿐이라고 가정합시다. 경고 수신 속도를 두 배로 올리는 것보다 오래된 대상의 결과를 분리하는 편이 담당자가 볼 것을 줄입니다. 현재 커밋의 필수 검사가 실패했다는 판정을 먼저 내고 해당 판정 사실을 고유 키로 묶어 한 번의 표시로 만드는 것이 그 방법입니다. 기준이 맞지 않으면 검사 이벤트가 왔다는 사실은 기록하되 담당자에게 새 문제로 알리지 않습니다. 잘못된 것을 놓치지 않았는지는, PR의 최종 검사 결과와 실제 전송 목록을 별도로 대조해 확인할 수 있습니다.
