Node.js 27 알파와 런타임 호환성

Node.js 27 알파와 런타임 업그레이드에서 버전 번호만으로는 알 수 없는 호환성의 경계를 살펴봅니다.

이 글의 흐름
최신 개발 소식주목할 만한 논문오늘의 개발 개념

Node.js 27의 알파 릴리스가 열렸습니다. 라이브러리 개발자는 운영 서버에 새 런타임을 올리지 않고도 다음 버전이 자기 패키지를 깨뜨리는지 검사할 수 있습니다. 문제는 알파에서 발견한 실패가 모두 같은 종류가 아니라는 점입니다. 설치 실패와 실행 결과의 변화, 기대값 자체가 잘못된 경우를 나눌 수 있어야 이 6개월이 유용해집니다.

최신 개발 소식

Node.js 27 알파와 새로운 연간 릴리스

Node.js 팀은 11월 16일 27.0.0-alpha.0.1.1을 공개했습니다. 27 계열부터는 주요 버전이 연 2회에서 1회로 바뀌고, 매 주요 버전이 장기 지원(LTS)을 받습니다. 27의 경우 2026년 10월 알파가 시작되고 2027년 4월에 Current, 10월에 LTS로 넘어가는 일정입니다. 새 방침에서 알파 6개월은 호환성을 깨는 변경도 허용하는 시험 기간입니다. Current 6개월은 새 버전을 안정화하는 구간이고, LTS 지원 기간은 30개월입니다. 예전처럼 홀수 버전이라서 LTS가 되지 않는 일은 없어집니다. Node.js 27 알파 릴리스 · 공식 릴리스 일정

알파와 나이틀리의 차이도 알아둘 만합니다. 나이틀리는 개발 브랜치의 최신 변경을 가까이서 보는 자동 빌드입니다. 알파는 버전이 붙고 서명된 릴리스로, Node.js 팀은 CITGM(Canary in the Gold Mine)으로 npm 생태계의 주요 패키지 테스트를 실행합니다. 이 시험은 런타임 자체 테스트가 성공해도 외부 코드가 실패하는 경우를 앞당겨 발견하려는 것입니다. 다만 명단 밖 패키지나 운영 환경의 조합까지 검증됐다는 뜻은 아닙니다. 특히 프로젝트가 리눅스 ARM이나 다른 libc를 지원한다면 그 배포 조건은 자체 테스트에 있어야 합니다. CITGM 공식 저장소

이번 27 알파는 26의 V8 14.6 대신 V8 15.6을 사용합니다. 공식 소개의 작은 예가 Math.sumPrecise입니다. [0.1, 0.2, 0.3]을 왼쪽부터 단순히 더하면 중간 반올림 탓에 보통 0.6000000000000001이 나옵니다. 같은 목록을 Math.sumPrecise로 합산하면 이 예에서는 0.6이 나옵니다. 새 함수가 누적 반올림 오차를 줄여주지만, 입력이 이미 이진 부동소수점으로 표현됐다는 사실이 달라지지는 않습니다. 금액을 정확히 저장해야 한다면 최소 화폐 단위를 정수로 저장하거나 십진수 타입을 쓰는 설계를 이 함수 하나로 대체할 수 없습니다. 또한 26을 지원하는 라이브러리가 새 내장 함수를 무조건 호출하면 27에서는 통과하고 26에서는 실패합니다. V8 변경 공식 해설

패키지에 네이티브 바이너리가 포함된다면 한 층을 더 보아야 합니다. 자바스크립트에 공개한 함수 이름과 인자가 같아도, 이미 빌드한 바이너리가 새 런타임에서 로드되지 않을 수 있습니다. Node 팀은 네이티브 애드온 ABI를 깨는 변경에 모듈 버전 변경을 수반한다는 방침을 설명합니다. 빌드 도구가 버전에 맞는 사전 빌드 파일을 고를 수 있게 하기 위해서입니다. 반면 안정적인 Node-API만 쓰는 애드온은 지원되는 Node-API 버전 범위에서 런타임 주요 버전 간 ABI 안정성을 기대할 수 있습니다. V8 내부 헤더나 외부 C 라이브러리의 ABI, CPU 아키텍처까지 같은 보장을 받는 것은 아닙니다. Node-API 공식 문서

이를테면 ZIP 변환 패키지가 순수 JS 구현과 네이티브 구현을 모두 제공한다고 가정해 봅시다. 릴리스 환경에서는 빠른 네이티브 구현을 기대하지만, 알파에서 사전 빌드 파일이 없으면 조용히 JS 구현으로 돌아갈 수 있습니다. 출력이 맞으면 단위 테스트는 통과합니다. 그러나 서버 CPU 사용 증가와 처리량 저하는 발생할 수 있습니다. 이 경우 실패 여부만 보는 것보다 어떤 구현이 로드되었는지, 설치 중 소스 빌드를 했는지, 대표 입력의 처리량이 어느 정도였는지를 따로 남기는 편이 낫습니다. 알파는 새 기능을 시연할 공간이면서, 평소의 테스트가 무엇을 놓치는지도 보여주는 공간입니다.

애플리케이션마다 업그레이드 기준이 다릅니다

런타임 자체를 버전별로 배포하는 팀과, npm 라이브러리 하나를 유지하는 팀은 알파를 켜는 이유가 다릅니다. 전자는 운영 이미지의 시작 시간이나 종료 시그널 처리 같은 환경 차이를 찾아야 합니다. 후자는 자기 소스 트리에서 실행되는 테스트보다 소비자가 설치한 결과에서 공개 API가 정상 동작하는지 우선 봅니다. 둘 다 같은 버전 번호에 관심을 가져도 실패를 보고할 때 첨부해야 할 자료가 달라집니다.

주목할 만한 논문

JEST와 자바스크립트 명세의 차등 테스트

JEST는 2021년 ICSE에 발표된 자바스크립트 엔진·명세 차등 테스트 연구입니다. 이름이 같지만 프런트엔드에서 흔히 쓰는 Jest 테스트 러너와는 다른 도구입니다. 차등 테스트는 같은 입력을 여러 구현에 넣어 결과의 차이를 발견하는 방식입니다. 결과 하나하나의 정답을 사람이 작성하기 어려운 컴파일러와 런타임에 특히 잘 맞습니다. 단, 서로 다르다는 사실은 알려줘도 어느 편이 틀렸는지는 별도로 판단해야 합니다. 한 구현이 표준을 잘못 따를 수도, 여러 구현이 같은 오해를 공유할 수도 있습니다. ICSE 논문 소개

연구팀은 N개 엔진에 더해 실행 가능한 형태로 만든 ECMAScript 명세 모델을 비교에 넣었습니다. 생성한 작은 자바스크립트 프로그램을 모델에서 해석하고 얻은 상태를 바탕으로 검증문을 삽입합니다. 그런 다음 실제 엔진에서도 테스트를 실행합니다. 기대 결과마다 손으로 판정식을 쓰는 대신 비교 가능한 검증 프로그램을 만드는 것이 핵심입니다. 언어의 문법과 상태 변화가 단순 계산 결과뿐 아니라 프로퍼티 접근, 예외, 평가 순서에서도 드러난다는 점을 이용합니다. 논문 원문 · 연구팀 구현

가령 객체의 값을 숫자로 바꾸는 메서드가 호출될 때 문자열을 기록하게 만들고, 그 객체들이 들어간 짧은 표현식을 실행해 볼 수 있습니다. 최종 숫자가 같아도 한 엔진에서 기록 순서가 거꾸로라면 두 동작은 동일하지 않습니다. 실제 서비스에서 이런 차이가 보이는 경우는 드물 수 있지만, 변환 중 예외가 발생하거나 코드가 외부 상태를 바꾼다면 차이가 호출자에게 전달됩니다. 올바른 비교 기준은 단순히 최종 반환값 하나가 아니라 명세가 요구하는 관찰 결과입니다.

논문이 보고한 수치는 네 엔진의 결함 44건과 ECMAScript 11 명세의 문제 27건입니다. 네 제품의 상대 품질 순위나 일반 npm 패키지의 호환률을 의미하지 않습니다. 도구가 선택하거나 생성한 입력, 구현한 명세 모델의 범위, 검증문이 관찰하는 상태 안에서 얻은 결과입니다. 모델과 엔진이 다르게 행동하면 그 차이가 출발점이 되고, 결론은 명세 조항과 실제 구현을 확인해야 나옵니다. 여러 버전이 일치한다는 이유로 그 동작을 표준으로 간주하거나, 모델과 다르다는 이유로 즉시 런타임 버그로 분류하는 것 모두 피해야 합니다.

Node.js 알파를 시험할 때도 이 구분이 쓰입니다. 지난 LTS에서 이미 잘못 동작하던 코드를 새 버전이 명세에 맞게 고쳤다면, 단순 스냅샷 비교는 그것을 회귀로 표시합니다. 역으로 둘 다 같은 값만 돌려준다고 해서 새 빌드가 같은 성능과 배포 경로를 제공하는 것은 아닙니다. 차이를 발견하는 테스트와 차이의 의미를 판단하는 자료는 따로 설계해야 합니다.

비교가 가리키는 것은 최소 재현으로 확인합니다

순서 차이를 발견했다면, 두 표현식에 각각 관찰 기록을 남기는 가벼운 객체 두 개만 쓰는 식으로 줄여 봅니다. 그래도 결과가 갈리면 헬퍼, 테스트 러너, UI 프레임워크 없이 설명할 수 있습니다. 반대로 작은 예에서 차이가 사라진다면 변경이 모듈 로딩이나 패키지 조건에 있을 가능성을 배제할 수 없습니다. 줄이는 과정에서 문제가 드러나는 조건까지 삭제하지 않아야 재현이 의미를 갖습니다.

오늘의 개발 개념

버전 매트릭스에서 실패를 읽는 순서

실용적인 시작은 현재 지원하는 LTS를 필수 검사로 유지하고, 알파를 별도의 관찰용 검사로 추가하는 것입니다. 알파가 바뀌었다는 이유로 모든 PR을 막을 필요는 없지만, 실패를 무시해도 된다는 뜻은 아닙니다. 검사에는 실제 런타임 버전과 OS·아키텍처를 남기고, 잠금 파일이 있는 같은 커밋의 의존성을 깨끗하게 설치합니다. npm ci는 package.json과 잠금 파일이 맞지 않으면 갱신하는 대신 실패합니다. 다만 플랫폼 조건이나 빌드 도구가 다른 환경에서 바이너리 결과까지 같다고 보장하지는 않습니다. 런타임을 바꾸는 실험에서는 패키지 관리자 버전도 관측하거나 고정하면 원인 구분에 도움이 됩니다. npm ci 공식 문서

실패는 세 단계에서 볼 수 있습니다.

  1. 설치와 로드. 의존성이 설치되는지, 배포 패키지에서 실제 진입점이 열리는지, 네이티브 바이너리가 선택되었는지 기록합니다. 저장소 내부 경로를 직접 불러오는 테스트는 패키징 이후 파일이 빠지는 문제를 놓칠 수 있으므로, 배포할 tarball 자체를 새 프로젝트에서 열어보는 편이 낫습니다.

  2. 동작과 계약. 정상 입력 하나에 그치지 말고 빈 입력, 잘못된 데이터, 중단된 요청처럼 경계 사례를 함께 넣습니다. 버전 간 출력이 달랐다면 설치 경로, 예외 타입, 반환값, 부수 효과 중 무엇이 바뀌었는지 가장 작은 입력으로 줄입니다. 외부 서비스 호출이나 시간에 의존하는 값은 고정해 비교합니다.

  3. 성능과 자원. 같은 파일, 같은 아키텍처, 같은 워밍업으로 비교합니다. 차가운 시작과 여러 번 호출한 후를 나눠 보고, 단일 최고값 대신 반복 결과의 중앙값이나 꼬리 지연을 남깁니다. p95가 악화되었다면 런타임 내부를 조사하기 전에 네이티브 폴백이나 I/O 경로가 바뀌었는지부터 확인합니다.

예컨대 알파에서만 실패한 로그가 네이티브 모듈을 찾지 못한다고 하더라도, 곧바로 ABI 위반이라고 단정할 수는 없습니다. 새 플랫폼용 바이너리 배포가 아직 없거나, 설치 로직이 프리릴리스 버전을 처리하지 못했을 수 있습니다. 같은 소스를 새 런타임에서 빌드했을 때 성공하는지, 사전 빌드 모듈이 어느 런타임용인지 나눠 보면 다음 조치가 달라집니다. 반대로 성능 차이가 있어도 대표 입력의 경로가 동일하고 반복 측정에서 잡음 범위라면 업스트림 회귀로 보고할 근거가 약합니다.

버전 매트릭스의 모든 조합을 매 PR에서 돌릴 필요도 없습니다. 예를 들어 LTS 두 버전과 알파 한 버전, 운영체제 세 종류, CPU 두 종류를 곱하면 벌써 18개 조합입니다. 모든 조합에 통합 테스트를 넣으면 개발 피드백이 늦어집니다. 변경이 잦은 코드의 기본 테스트는 PR에서 돌리고, 네이티브 모듈 설치와 배포 파일 검증처럼 비싼 조합은 정기 실행으로 옮길 수 있습니다. 대신 배포 때는 실제 지원을 약속한 플랫폼을 확인합니다. 조합을 줄인다면 어떤 범위를 검사하지 않는지도 문서화해야 합니다.

업스트림에 문제를 전달할 때는 “27에서 깨짐”보다, 가급적 같은 파일로 26과 27에서 관찰한 값, OS와 CPU, 기대 동작을 지지하는 명세나 문서, 재현에 필요한 가장 작은 코드가 유용합니다. 작은 코드에서 사라지는 문제라면 실제 배포 tarball 또는 네이티브 폴백이 재현 조건일 수 있으므로, 현상을 지워버릴 만큼 과하게 줄이지는 않습니다. 이러한 기록은 알파에서 발견한 차이가 현재 앱의 의존성 문제인지, 다음 정식 버전까지 영향을 줄 런타임 문제인지 구분하는 데도 도움이 됩니다.

일정을 바꾸는 정책의 가장 실용적인 결과는 새 버전을 더 자주 운영에 넣는 것이 아닙니다. 운영은 검증된 LTS에 두고, 패키지 경계에서 일어나는 변화를 업그레이드 전에 읽을 시간이 생긴다는 것입니다. 알파 검사 한 줄을 추가하는 데서 멈추지 말고, 실패가 설치·동작·성능 중 어디에서 일어났는지 다음 사람이 판단할 수 있게 만드는 편이 그 시간을 더 잘 씁니다.

시험이 오래 걸리면 실행할 때보다 결과를 읽는 시간을 줄입니다

예를 들어 LTS 검사 8분과 알파 검사 12분이 매 PR에서 병렬로 완료된다면 CI 자원은 20분을 쓰고, 두 결과를 다 기다리면 12분이 걸립니다. 알파를 병합 조건에서 제외하면 팀은 8분 뒤 기본 결과를 보고 진행할 수 있습니다. 그렇다고 알파 실패를 지우는 대신, 신규 실패는 먼저 나타난 커밋, 최후 성공 버전, 재실행에서 반복되는지와 함께 기록해 둡니다. 같은 문제로 매일 늘어나는 실패 알림이 따로 한 건으로 묶이면, 알파를 오래 켜 둬도 아무도 읽지 않는 보조 작업이 되지 않습니다.
